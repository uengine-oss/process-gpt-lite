# 일 하나에 작업 폴더 하나 — 메일과 단계 결과를 한곳에, 들어올 때 지도와 견주기

2026-11-24 · 브랜치 `feat/mail-work-folder`(main `ba711af` 위, PR #22 · #23 포함) · 스펙 `openspec/specs/mail-work-folder` · 서버 `server/lib/mailWork.js` · `server/lib/folders/line.js`

## 1. 사용자 결정 (2026-11-24, 말로 한 것)

1. **일 하나에 작업 폴더 하나.** 메일로 일이 시작되면 에이전트들이 「내가 일하는 폴더」로 쓸 폴더가 있어야 한다.
   - 첫 메일부터 그 폴더에 들어가고, 산출물이 거기 쌓인다.
   - 그 맥락이 남아 있어서 다음 단계의 에이전트들이 참고한다.
   - 그래서 열려 있던 물음 「이은 메일을 엔진 단계의 입력으로 줄까」(`docs/mail-thread-flow/design.md` §6)의 답은 「준다, 이 폴더로」다.
2. **저절로 시작하는지는 프로세스의 단계를 따른다.** 메일 카드가 생기는 모든 메일(문서를 요청하는 메일만이 아니라)에서 프로세스를 찾으면, 그 프로세스의 단계대로 한다.
   - 자동: 저절로 시작하고, 첫 일까지 한다.
   - 제안: 시작하기 전에 묻는다(시트의 물음은 이미 있다).
   - 관찰: 시작하지 않는다.
3. **모델 비용은 받아들인다.** 프로세스 지도를 쓰는 회사라면 메일이 들어올 때 프로세스를 찾는 모델 비용을 감수한다. 자동인 프로세스는 첫 일까지 저절로 하는 것이 전제다. 그래서 지도와 견주는 일은 시트를 처음 열 때가 아니라 메일 카드가 생길 때 한다. 결과는 지금처럼 카드에 남긴다.

## 3. 설계

### 3.1 폴더는 어디에 · 이름 · 구성원 · 인스턴스와의 고리

- **보통의 공유 폴더**(`pro_folders`, kind `managed`)를 하나 만든다. 새 테이블은 없다. 폴더 화면 · 변형 · 반영 · 색인 · 공유 · 작업실 · 폴더 도구(`folder_files` · `folder_read`)가 그대로 된다.
- **주인**: 그 메일의 주인(메일함 주인). 자동 시작이면 그 메일함 주인, 시트의 새로 시작 · 잇기면 누른 사람.
- **이름**: 인스턴스 이름(같은 이름이 있으면 ` (2)`). slug 는 `work-<인스턴스 id 끝 12자>`. 설명은 「「<인스턴스>」의 작업 폴더 — 메일과 단계 결과가 모여요」.
- **구성원**: 기본은 주인만이다(`rules.mailWork.shareWithRoles: false`). 폴더에 메일 원문(메일함 주인의 메일)이 들어가는데, 지금까지 메일 문장은 주인 몫으로 두었기 때문이다(지도에도 문장을 남기지 않음). 회사가 켜면 건의 역할을 맡은 사람(`pro_po_cases.bindings`, 에이전트 제외)을 **보기** 로 넣는다. 주인은 폴더 화면에서 언제든 더한다. (2026-11-24 검토에서 기본값을 바꿈 — 처음 구현은 역할을 맡은 사람을 보기로 넣었다.)
- **고리**: 폴더의 `settings.work`에 둔다 — `{instId, instances, caseId, inst, proc, procName, owner, line, dirs, mails[], recorded[]}`. 인스턴스로 폴더를 찾고(`instances ? <instId>`), 없으면 같은 건(`caseId`)의 폴더를 찾아 그 인스턴스를 더한다(건을 옮기면 새 인스턴스가 생긴다 — `run.js moveCase`).
- 카드에는 `source.inst.folder = {slug, name}`을 더한다(시트 · 칩이 폴더로 간다).
- 인스턴스 대화(`pro_threads` kind `process`)에 폴더를 **참고로 붙인다**(`pro_thread_folders` mode `ref`). 거기서 묻는 것은 폴더의 main 을 읽는다(`agent.js`가 `process` 대화에도 `refHint`를 준다). 거기서 「고쳐줘」라고 해도 이 폴더의 변경으로 받지는 않는다(폴더 이름을 말한 경우만).

**만드는 때**: 메일로 인스턴스를 시작할 때(자동 시작 · 시트의 새로 시작 · 마이닝 등록 흐름의 시작)와, 폴더가 없는 진행 중인 인스턴스에 메일을 이을 때(잇기 · 같은 스레드). 「메일이 들어온 일」이면 폴더를 가진다.

### 3.2 메일을 넣는 법

`메일/NN_<YYYY-MM-DD>_<제목>.eml|.md`, 첨부는 `메일/NN_첨부/<파일>`.

- `.eml`: 메일함이 지닌 원문 그대로(Gmail `format=raw`, IMAP source). 데모 메일함은 원문이 없어서 가진 것(보낸 사람 · 받는 사람 · 제목 · 날짜 · 본문)으로 RFC 822 메시지를 만든다(nodemailer MailComposer). 메일함이 더는 그 메일을 갖고 있지 않으면 카드가 아는 것으로 만든다(`partial`).
- `.md`: 읽을 수 있는 판 — `# 제목`, 보낸 사람 · 받는 사람 · 참조 · 날짜(한국 시간) · 첨부(경로) 목록, `---`, 본문. 본문의 줄바꿈은 마크다운으로 보여도 줄로 남는다(줄 끝 공백 두 칸).
- 첨부: 본문 안 그림(inline)은 `.eml`에만 있고, 함께 보낸 파일만 꺼낸다. 이름은 경로 · 예약 글자를 뺀다. 같은 이름은 ` (2)`.
- 번호 `NN`은 main 의 `메일/` 아래 가장 큰 번호 + 1(폴더 잠금 안에서 정한다). 날짜는 메일의 날짜(한국 시간).
- **한 커밋, 그 사람이**: 「메일 NN · <제목>」, 작성자는 메일을 넣은 사람(시작 · 잇기한 사람, 자동이면 메일함 주인). 같은 메일은 두 번 넣지 않는다(`settings.work.mails`의 메일 id).
- 디렉터리 이름은 폴더를 만들 때의 언어로 정해 폴더에 둔다(영어 화면: `Mail/`, `attachments`, `Outputs/`, `result.md`).
- 넣은 뒤 인스턴스 대화에 폴더 칩: 「작업 폴더 ‘…’를 만들고 메일 01 「…」를 넣었어요」 / 「작업 폴더 ‘…’에 메일 02 「…」를 넣었어요」. 누르면 폴더가 열린다. Home 알림이나 메인 채팅에는 덧붙이지 않는다(11-18).

### 3.3 인스턴스 라인 — 단계가 앞 단계의 결과 위에서

폴더의 원칙(에이전트는 main 을 바로 고치지 않고 변형에서, 사람이 반영)을 그대로 둔다. 한 인스턴스의 단계는 **인스턴스 라인 `inst/<id>`** 에 이어 쌓인다(work.js 의 `@previous`와 같은 가지).

- **메일**은 main 에 들어간다(사람이 넣은 것). 라인이 이미 있으면 main 을 라인에 합친다(`line.js syncLine`) — 다음 단계는 라인에서 시작하므로 뒤에 온 메일을 본다.
- **끝난 단계의 결과**(`mailWork.recordDone`): 인스턴스의 작업 항목 중 끝난 것(DONE · SUBMITTED, 취소 아님, 출력 있음)의 출력을 `산출물/NN_<단계>/`에 쓴다 — 이 서버 Storage 의 파일은 내용 그대로, 다른 곳의 링크는 이름 · 주소만, 값은 `결과.md`(한 사람 · 끝난 때 · 파일 · 값). 단계마다 한 커밋, 작성자는 「업무 에이전트」(에이전트 단계) 또는 그 사람(사람 단계 · 사람이 낸 초안). 「요청 접수」 단계는 첫 메일과 같아서 넣지 않는다. 이미 폴더에서 일한 단계(deepagents · cli-agent, `agent_config.folder`)는 work.js 가 자기 결과를 라인에 남기므로 건너뛴다.
- **라인 쓰기는 한 번에 하나**(`line.js`, 폴더별 잠금). 분리된 임시 체크아웃(`--detach`)에서 커밋하고 `update-ref`로 옮긴다 — 사람이 라인 변형을 작업실에 열어 두어도 된다. 다른 엔진 단계의 결과(work.js)는 이제 라인을 앞으로 감기(fast-forward)만 하고, 그사이 라인이 움직였으면(메일 · 다른 단계) 합친다. 예전처럼 `branch -f`로 되돌리지 않는다.
- 라인은 폴더의 변형(kind `instance`, 「<인스턴스> — 인스턴스 라인」, 반영 대기)으로 보인다. 사람이 「이 변형 반영」을 누르면 산출물이 main 에 들어간다.
- 기록하는 때: 지도 단계 일꾼이 단계를 시작할 때(앞 단계가 끝나자마자 다음 단계가 와도 그 앞 단계가 먼저 기록된다), 그리고 폴더 틱(`work.js stepTick` → `mailWork.tick`, 20초마다 `rules.mailWork.sweepSeconds`).

### 3.4 단계가 읽는 것

- **지도 단계 일꾼**(`ontology/run.js runStep`)이 단계마다 `mailWork.stepContext(instId)`를 읽는다: 메일(먼저 온 순서, 날짜 · 보낸 사람 · 제목 · 첨부 이름 · 본문 — 한 통 1500자, 모두 5000자)과 라인의 산출물(경로, `결과.md` 앞 800자, 모두 2500자). 숫자는 스킬 `rules.json`의 `mailWork`.
  - 글로 만드는 단계(doc-draft): 입력 JSON 에 `work: {folder, mails, outputs}`. 스킬 프롬프트 `draft-step.md`가 `work`를 설명한다(나중 메일이 바꾼 것을 따른다).
  - 양식 채우기 · 마이닝 스킬 · deepagents 위임: `extra`(일 정의 뒤)와 위임 글에 「작업 폴더」 메모를 붙인다. 메모의 글은 스킬 프롬프트 `prompts/work-folder.md`에 있다(코드에 지시문을 넣지 않는다).
  - 이 메모에 메일 본문이 들어가므로, 다른 파드에서 도는 deepagents 위임도 디스크 없이 메일과 결과를 읽는다.
- **마이닝 등록 흐름**(`mining/worker.js`)도 같은 메모를 `extra`로 받는다.
- **다른 엔진의 단계**(deepagents · cli-agent 등 `pgpt-pro-*`가 아닌 orch)는 `agent_config.folder` + `base_ref: '@previous'`를 받아(`mailWork.stepFolders`, 프로젝트 폴더의 `projectStepFolders`와 같은 때) work.js 가 라인에서 체크아웃을 준다.
- `caseIntake`는 바꾸지 않았다: 그 값(요청 접수의 제목 · 본문 · 보낸 사람)은 건을 옮길 때 새 인스턴스의 요청으로 다시 쓰이므로, 메일 목록을 섞지 않고 작업 폴더를 따로 준다.

### 3.5 들어올 때 — 지도와 견주고 단계대로

`lib/mail.js pollUser`: 트리아지가 카드를 만든 메일은 **모두** 그 자리에서 `mailFlow.routeMailCards`로 지도와 견준다(예전에는 문서를 요청하는 메일만). 카드가 없는 메일, 데모 메일함의 견본 메일, 같은 Gmail 스레드로 이미 이어진 메일은 견주지 않는다.

| 프로세스 단계 | 들어올 때 | 카드 · 시트 |
|---|---|---|
| 자동(adopted), 시작 일이 확실 | 저절로 시작 → 작업 폴더(메일 01) → 첫 단계는 엔진이 바로 집는다(사람 단계는 초안 모드). 인스턴스 대화와 Home 알림으로만 알린다 | 카드 · 칩이 「루틴 · …」 |
| 자동인데 진행 중인 같은 일로 읽힘 | **시작하지 않는다**(아래) | 시트가 「잇기」를 권한다(판정 결과가 카드에 있음) |
| 제안(suggested) | 시작하지 않는다 | 카드 한 줄 · 시트가 묻는다. 시트는 지도를 다시 읽지 않는다(카드에 12시간) |
| 관찰(paused) | 읽지 않는다 — 시작도 묻기도 없다 | 진행 중인 같은 일이면 시트가 「잇기」만 권한다 |

- **스레드로 이어진 다음 메일은 언제나 잇는다**: 같은 Gmail 스레드의 앞 메일이 진행 중인 인스턴스에 이어져 있으면 모델 없이 그 인스턴스로(그리고 작업 폴더의 다음 번호로) 가고, 지도를 다시 읽지 않는다 — 새 건을 시작하지 않는다.
- **스레드가 없는 다음 메일**(데모 · IMAP, 답장하지 않고 새로 쓴 메일): 자동으로 시작하기 전에 진행 중인 후보를 판정 모델(`prompts/same-work.md`, 시트와 같은 문턱 `mailFlow.joinMin`)로 읽고, 같은 일이면 시작하지 않고 카드가 묻는다. 그렇지 않으면 같은 고객이 「Re:」 없이 다시 쓴 메일마다 새 건이 생긴다. 판정 비용은 자동 시작이 있을 때만, 후보 4개까지다.
- 안전은 그대로다: 사람 단계는 초안 모드, 회사 밖으로 나가는 단계는 초안을 만들고 사람을 기다림(runmode.js), 메일은 「보내기」를 눌러야 나간다.
- 문서를 요청하는 메일의 기존 길(지도 → 마이닝 등록 흐름 → 즉석 초안)은 그대로이고, 지도가 먼저 읽은 결과를 이어 쓴다.

## 4. deepagents 엔진 단계의 공백 (운영)

운영의 deepagents 는 다른 파드에서 돈다. work.js 는 엔진 단계(deepagents)의 체크아웃을 Lite 디스크의 `runCheckoutDir`에만 만들었다. 채팅 길처럼 고쳤다.

- `work.js seedStep`: 체크아웃을 그 방(`/workspace/.bpmn/<인스턴스>/folders/<slug>`)의 Storage 자리에 올리고(`pushRoomDir`), 올린 것(해시 · 시각)을 변형의 `source.room_store`에 둔다(서버가 다시 떠도 남는다).
- `work.js pullStep`: 단계가 끝나면 커밋 전에 Storage 에서 고친 것 · 새 파일 · 지운 것을 체크아웃으로 받아 온다(`pullRoomChanges`, 기다리지 않음 — 넘긴 작업 항목의 방은 deepagents 가 항목을 닫기 전에 올린다).
- `handover.js runReceiver`(에이전트에게 변형 인계)와 `merge.js resolveWithAgent`(충돌 해결 에이전트)도 같은 왕복을 한다. 둘은 `runAgent`(채팅 길, `/chat/stream`)를 쓰므로 운영에서도 바로 효과가 있다.

**남은 한 가지(이 저장소 밖)**: 지금 deepagents(`process-gpt-deepagents` master)는 방을 Storage 에서 받는 일을 **채팅 턴**과 **대화창 인계로 받은 할 일**(`adhoc` + `[ChatRoom] <방>`)에만 한다. 엔진이 만든 보통 작업 항목은 받지도 올리지도 않는다. 그래서 위 Lite 쪽 왕복은 그 부분이 고쳐져야 운영의 deepagents 엔진 단계에서 효과가 난다. 필요한 변경: 폴러로 받은 할 일의 `agent_config.room_store.container`(또는 `query`의 `[Folder] … 작업 폴더: /workspace/.bpmn/<방>/…`)가 있으면 그 방을 인계 방처럼 내려받고, 항목을 닫기 전에 올린다(`_sync_room_workspace`). 로컬 개발(디스크 하나)은 지금도 된다. 지도 프로세스의 단계(이번 일의 주된 길)는 Lite 안에서 돌고 메일 · 결과를 글로 받으므로 이 공백과 상관없다.

## 5. 화면

- **인스턴스 화면**(`InstanceHeader`): 제목 아래 「작업 폴더 · <폴더>」 단추와 「메일 N통 · 단계 결과 N개 · 단계 결과 보기 →」. 단추는 폴더, 「단계 결과 보기」는 인스턴스 라인 변형. 폴더를 볼 수 있는 사람에게만 보인다(`GET /api/instances/:id`의 `workFolder`).
- **인스턴스 대화**: 폴더 칩(누르면 폴더).
- **폴더 화면**: 이름 옆 「작업 폴더」, 설명 아래 「↻ 루틴 · <인스턴스>」(누르면 인스턴스). 폴더 목록에도 「작업 폴더」.
- **메일 시트**: 인스턴스에 이어진 메일이면 「작업 폴더 · <폴더>」.
- 휴대폰(390×844)에서 옆으로 넘치지 않는다. 영어 화면은 `src/i18n/ko-en.json`.

## 7. 하지 않은 것 · 정할 것

- **라인을 main 에 저절로 반영할지**: 지금은 산출물이 인스턴스 라인(반영 대기)에 쌓이고 main 에는 메일만 있다. 폴더 목록 · 기본 화면에서 산출물을 바로 보려면 사람이 「이 변형 반영」을 누른다. 「작업 폴더는 그 일 전용이니 단계 결과를 main 에 바로 넣는다」로 바꿀지는 사용자가 정할 일이다.
- **역할을 맡은 동료의 권한**: 보기로 넣었다. 편집으로 줄지, 아예 넣지 않을지(메일 원문 공개 범위)는 사용자 결정.
- **진행 중인 같은 일이면 자동 시작을 멈추는 것**: 사용자 결정 2 에 없는 안전장치다. 대신 저절로 「잇기」까지 할지(지금은 시트가 묻는다)도 정할 수 있다.
- **사람 단계에서 낸 결과**는 그 항목이 끝나면 기록되지만, 사람이 단계 화면에서 올린 파일이 출력에 없으면 들어오지 않는다.
- **deepagents 쪽 변경**(§4) — 이 저장소 밖.
- **실제 지도 엔진으로 자동 시작 → 첫 단계**: 로컬 Ontological 엔진이 꺼져 있어 지도의 읽기 · 시작 · 판정은 시험 대역으로만 보았다.
- **카드가 없는 메일**(simulate-mail)은 예전처럼 `events.onMail`이 메인 채팅에 카드를 붙이고, 작업 폴더를 만들지 않는다.
- **IMAP 메일함의 스레드**: 스레드 id 가 없어 판정 모델로만 잇는다.
