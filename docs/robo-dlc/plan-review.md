## 2. 앱 규약 v1 (결정)

앱 하나 = `server/apps/<id>/` 폴더 하나. 폴더를 빼면 그 앱의 경로·화면·카드가 모두 사라지고, 나머지는 그대로 돈다.

```
server/apps/<id>/
  manifest.json   { id, version, contract: 1, name{ko,en}, icon, requires:['aidlc'], mounts:['folder','sheet'],
                    capabilities:['api','navigate','openApp','me'], events:['changed','presence'], handles:['aidlc.questions'] }
  server.js       export default (ctx) => ({ routes(router), waits?: { url(slug, wait), notify(folder, wait) } })
  ui/index.html   화면(정적 파일, 외부 빌드 없음). /api/apps/_runtime/lite.js 를 읽어 window.lite 를 쓴다
  sql/*.sql       앱 자기 표(app_<id>_*), 서버가 처음 뜰 때 한 번씩(lite_migrations 에 'app:<id>/<file>')
```

- **서버 쪽 경계:** 앱은 호스트 모듈을 import 하지 않는다. 호스트가 넘겨 주는 `ctx`(버전 1)만 쓴다.
  - `ctx.db.q`
  - `ctx.folders.access`
  - `ctx.aidlc.{current, questions, reviews, units, bolts, events, readDoc, docs, roles, deciders, screen, decide, answers, mob}`
  - `ctx.events.toFolder`
  - `ctx.notify`
  - `ctx.L`

  시험이 앱 폴더의 import 를 검사한다(같은 폴더 안 상대 경로와 node 내장만 허용). 그래서 앱 서버는 나중에 `ctx` 를 HTTP 로 바꿔 별도 프로세스로 옮길 수 있다.
- **화면 쪽 경계:** 앱 화면은 출처 없는 격리 iframe 이다. 호스트와는 `lite.call(type, payload)` 로만 이야기하고, 호스트는 매니페스트의 `capabilities` 에 없는 호출을 거절한다.
  - `api`: 자기 앱 경로만, 사람의 토큰은 호스트가 붙인다.
  - `navigate`: 정해진 호스트 경로만.
  - `openApp`: 다른 앱을 옆 시트로 연다. 앱끼리는 서로의 내부를 모르고, id 와 인자만 안다.
  - `me`
  - 이벤트는 호스트가 SSE 의 `app` 이벤트 중 그 앱 것만 넘긴다(`lite.on`).
- **붙는 자리:**
  - `folder`: 폴더 화면의 AI-DLC 띠에 단추로 붙는다. `/apps/<id>/<folder>` 전체 화면.
  - `sheet`: 다른 화면 위에 옆 시트로 붙는다.
  - `handles`: 감시기의 기다림 카드를 그 앱으로 보낸다.
- **패널도 같은 통로:** `PanelFrame` 의 if/else 를 기능 표(`src/apps/bridge.js`)로 바꾼다. 패널은 기존 기능 집합을 그대로 쓰고, 앱은 매니페스트의 집합을 쓴다.

## 3. 앱 세 개

### 3.1 검토 보드 (`review`)

- **카드:** 지금 단계의 검토 거리를 카드로 펼친다.
  - **질문 카드:** 질문 파일의 `## Qn. [역할] …`, 질문 아래 이유 문장, 선택지, 「(권장: 이유)」가 붙은 AI-DLC 추천.
  - **지적 카드:** 승인 대기 중이면 `reviews/review-NN.md` 의 R-xx(심각도·위치·지적·고칠 일).
- **역할 나누기:** 질문 태그가 역할 이름이다(실측 태그 분포: 제품·제품 관리자·제품 책임자 → PO, 아키텍트·아키텍처 → 아키텍트, 개발·개발자·개발 리드 → 개발자, 디자이너·디자인 → 디자이너, 품질·품질 엔지니어 → QA, 딜리버리 리드, 운영, 릴리스 엔지니어 → 배포). 태그가 없거나 그 역할에 사람이 없으면 단계 역할로 간다.
- **병렬 검토:** 각자 자기 열(역할)의 카드만 빠르게 본다.
  - 질문: 「추천대로」 한 번, 또는 다른 선택지·글.
  - 지적: 「위험 감수(승인)」 「고쳐 주세요」 「해당 없음」 + 이유.
  - 누구나 의견과 근거를 단다. 근거는 산출물 절 링크, URL, 그리고 「근거 찾기」(기록의 산출물에서 그 질문의 낱말이 나오는 절을 모델 없이 찾아 줌)에서 고른 것이다.
- **실시간:** 누가 어느 카드를 보는지(아바타), 의견, 상태가 SSE 로 바로 보인다.
  - 보는 중은 5초마다 알리고 15초 뒤 사라진다.
- **상태:**
  - 열림: 아무도 안 봄
  - 정함: 담당이 고름, 이의 없음
  - 논의 필요: 누군가 이의·질문
  - 보냄: 파일·세션에 들어감
- **함께 보는 모드:** 「논의 필요 N개로 몹 회의」는 기존 몹 회의를 그 질문만으로 연다. 회의의 합의 답이 보드에 채워진다.
- **보내기(단계 결정권자):**
  - 질문은 파일에 적고 세션에 알린다(기존 `answers`).
  - 지적은 결정 하나로 묶어 선택 창에 넣는다(기존 `decide`). 모두 위험 감수면 Approve, 고칠 것이 있으면 Request Changes 글에 R-xx 와 이유, 해당 없음만 있으면 승인 글에 그 이유를 적는다.
  - 논의 필요가 남아 있으면 확인을 한 번 더 받는다.
- **카드:** 질문·승인 대기 카드는 결정 화면 대신 보드로 연다(`handles`). 단계 결정권자가 아닌 검토자에게도 「검토할 질문 N개」 카드가 따로 간다.

### 3.2 볼트·유닛 보드 (`bolts`)

- **계층:** 의도 → 볼트(`delivery-planning/bolt-plan.md` 의 `## Bolt N — 이름 (\`id\`)` 와 「포함 단위」) → 유닛(`unit-of-work-dependency.md`) → 유닛의 구축 단계(감사 기록 UNIT_STARTED/COMPLETED·체크포인트·유닛 승인).
- **지금 도는 유닛:** 끝나지 않은 마지막 UNIT_STARTED 의 유닛과 단계다.
- **유닛 누르기:**
  - **진척 요약:** 단계 칸, AI 작업·사람 대기, 체크포인트 통과·실패, 최근 사건, 그 유닛의 산출물 목록과 원본 보기.
  - **세션 화면:** 그 유닛을 지금 만드는 세션이면 화면 글자를 3초마다 보여 준다.
  - **「작업실에서 열기」:** 같이 쓰는 쉘로 바로 간다.
- **알려진 한계 고침:** 같은 판별(끝나지 않은 유닛 단계)을 감시기·결정 화면의 역할 판별에도 쓴다. 코드 계획 승인이 개발자에게 간다.

### 3.3 산출물 보기 (`artifact`)

- `?path=<기록 안 경로>&focus=<절 이름>&quote=<글>`
  - 문서 전체를 마크다운으로 그린다. 원문 html 은 글자로 둔다.
  - 왼쪽에 목차와 같은 단계의 다른 산출물이 있다.
  - `focus` 절로 스크롤하고 그 절을 띠로 강조한다(예: `decisions.md` 의 ADR-004).
- **원본 보기 링크가 붙는 곳:**
  - 검토 보드의 지적 위치(`…/decisions.md > ADR-004, against requirements.md FR7.2` → 두 링크)
  - 질문 근거
  - 볼트 보드의 유닛 산출물
  - 결정 화면의 승인 창(그 단계 산출물 목록)
- 기록(`aidlc/`) 안의 `.md` 만 연다(경로 검사).

## 6. 11-12 고침: 함께 고르기와 의도 → 유닛 → 볼트 (결정 D-1112-21 · D-1112-22)

첫 실제 실행의 영상을 본 뒤의 지적 두 가지를 AI-DLC 원문(Raja SP, AWS 2025 「AI-DLC Method Definition」, prod.d13rzhkk8cj2z0.amplifyapp.com/aidlc.pdf)과 대조해 고쳤다.

- **볼트 계층.** 원문은 "A Unit may be executed through one or more Bolts"라고 정의한다. 2.11.2 의 `bolt-plan.md` 는 유닛을 전달 순서로 묶은 계획일 뿐이고 실행은 유닛 의존 그래프를 따르므로, 볼트 보드를 의도 → 유닛 → 볼트로 바꿨다. 볼트 하나 = 유닛의 코드 생성 한 번(`aidlc engine bolt checkpoint --kind unit` 검증으로 닫힘), 빌드·테스트의 `GATE_REJECTED` 가 그 볼트를 「되돌아옴」으로 닫고 다음 코드 생성이 새 볼트다. 계획의 묶음은 유닛의 「묶음 B<n>」 이름표(`server/apps/bolts/tree.js` `unitBolts`·`buildUnitTree`). 회의실 예약 실행: 계획 6, 실제 11(되돌아옴 5, u3 셋).
- **함께 고르기.** 원문의 몹 정교화는 팀이 답하고 팀이 검증하는 의식이며 역할 분담이나 투표 절차가 없다. 역할별 나눔(§3)을 「역할별로」 모드로 남기고, 기본을 플래닝 포커식 「함께 고르기」로 했다: 모두가 모든 카드에서 고르고, 남의 선택은 내가 고른 뒤에 보이며, 같은 답 두 사람 = 합의, 다르거나 마지막 선택 뒤 이의 = 의견 갈림, 결정권자가 정하거나(`review_settle`) 몹 회의로(`server/apps/review/board.js` `voteState`, 표 `app_review_modes`·`app_review_settled`).
- 시험: `apps.test.js` 25(voteState·unitBolts), `apps.e2e` 10(「함께 고르기」 한 바퀴), F-RD-06(두 브라우저: 가림 → 의견 갈림)·F-RD-08(유닛 → 볼트). 실제 classic 한 판(비품 대여, `pgpt-pro/demo/product/robo-dlc-review2-ko`)으로 영상을 다시 찍는다.
