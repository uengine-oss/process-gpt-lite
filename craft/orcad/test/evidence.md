# OrCAD 읽기 대조 기록

코드가 낸 값끼리 맞춘 것이 아니라, 공개 자료와 Capture 가 직접 만든 넷리스트에 대 본 기록이다.
실제 파일은 저장소에 넣지 않았다. 시험은 `ORCAD_TEST_DIR` 에서 찾는다 (`test/fetch-evidence.sh` 참고).

```
ORCAD_TEST_DIR=<폴더>[:<폴더>...] node --test craft/orcad/test/dsn.test.mjs
```

마지막 실행: 시험 51개 모두 통과. `ORCAD_TEST_DIR` 없이 돌리면 27개 통과, 24개는 이유를 적고 건너뛴다.

## 2. Capture 가 만든 넷리스트와 대조 (가장 강한 근거)

`.dsn` 과 Capture 의 `.net` 이 함께 있는 설계 전부를 `dsnToNetlist` 결과와 낱말 단위로 맞췄다.
도구는 `test/capture-net.mjs`, 시험은 `dsn.test.mjs` 의 `Capture 넷리스트 대조`.

**141개 설계 중 139개 통과 (98.6%).** 아래 셋을 모두 만족해야 통과다. 처음 돌렸을 때는 116개였고, 템플릿 언어와 조각 처리, 계층 이름을 고쳐 올렸다.

- 부품 이름: `.net` 의 소자 이름이 모두 있고, 더 있는 것이 없다.
- 연결: 넷을 핀의 묶음으로 비교한다. 넷 이름은 보지 않는다.
- 값: 노드 뒤의 글자가 같다 (값, 모델 이름, `DC`, `+PULSE`, `PARAMS:` 등). 템플릿이 만든 `.subckt` 본문과 `.model`, `.param` 줄도 같아야 한다.

| 항목 | 수 |
|---|---|
| 설계 | 141 (계층 설계 27, 그려진 블록 1) |
| Capture 소자 / 대조한 소자 | 1651 / 1640 |
| 대조한 값과 `.subckt` | 1768 |
| 부품 이름 일치 | 139 / 141 |
| 연결 일치 | 140 / 141 |
| 값 일치 | 141 / 141 |
| 파일의 선 id 로 구한 연결 = 좌표만으로 구한 연결 | 141 / 141 |
| `pspice.mjs` 의 `read()` 로 읽은 소자 수 = Capture `.net` 쪽 소자 수 | 140 / 141 |

값 일치가 141/141 이다. 다만 이름이 맞는 소자끼리만 값을 비교하므로, 이름이 달라 짝이 없는 소자의 값은 이 수에 들어가지 않는다 (아래 실패 2건의 11개).

### 실패 2건: 둘 다 넷리스트가 파일보다 옛것이다

| 설계 | 내용 | 근거 |
|---|---|---|
| `AMPLIFICATOR AUDIO DE PUTERE.DSN` | 넷리스트는 `R_R28-1`, `R_R28-2`, `R_R29-1`, `R_R29-2`, `R_R30-1`, `R_R30-2`, `R_R30-3`. 파일은 `R28A`, `R28B`, `R29A`, `R29B`, `R30A`, `R30B`, `R30C`. 나머지 소자의 값과 연결은 일치 | 파일 원본 바이트에 `R28-1` 이 없고 `R28A`, `R28B` 가 있다 |
| `UA741.DSN` (Library 2.0) | 넷리스트에 `V_V3`, `V_V6`, `V_VIN`, `R_R15` 가 더 있다. 파일에서는 `VI1`, `VI2`, `0` 이 같은 넷이다. 값은 모두 일치, 연결 3곳 다름 | 파일 원본 바이트에 `R15`, `VIN`, `V3` 글자가 없다. `V6` 글자는 있으나 부품으로 읽히지 않는다. 페이지 넷 표에서 `0`, `VI1`, `VI2` 의 id 가 모두 55394 이다 |

`read()` 소자 수가 다른 1건도 `UA741` 이다 (내 쪽 39, `.net` 43).
옛것이라는 판단은 파일 바이트에서 나온 추정이고, Capture 로 넷리스트를 다시 뽑아 확인한 것은 아니다.

### 비교에서 일부러 눈감는 것

넷리스트 글자가 달라도 같다고 치는 경우다. 합격률을 볼 때 함께 봐야 한다.

- 넷 이름. 요청대로 비교하지 않는다.
- 줄 나눔 위치, 빈칸, 대소문자.
- `TC=0,0`. 효과가 없는 값이고, 표본의 Capture 판에 따라 있기도 없기도 하다.
- 미연결 핀. Capture 는 노드를 쓰지 않거나 혼자인 이름을 주고, 나는 `NC_...` 로 쓴다. 다만 Capture 에서 다른 핀과 묶인 넷을 내가 미연결로 읽었으면 실패로 친다.
- `PSpiceTemplate` 이 없는 부품(커넥터 등)은 Capture 가 시뮬레이션 넷리스트에 쓰지 않고, 나는 `X_` 줄로 남긴다. 그래서 내 쪽 부품이 더 있어도 템플릿 없는 부품이면 허용한다.
- 한 설계에 `.net` 이 여럿이면 파일 안 회로도 이름과 맞는 것을 고른다. 밀려난 옛 넷리스트 37개는 합격률에서 뺐다. 그중 24개는 지금 파일과도 같았다.

`dsn.test.mjs` 의 `KNOWN_FAILURES` 에는 이 절의 실패 4개 설계만 있다. 다른 설계가 실패하면 시험이 깨진다.

### 같은 방법의 추가 대조

추가 프로젝트 6개도 같은 시험에 넣었다. 4개 통과. 합치면 **147개 중 143개**다.
나머지 2개(`LED5`, `MULTIVIBRATOR`)는 지금 파일에 없는 회로도 `SCHEMATIC1` 의 넷리스트다.
`SPICE_DIFFCIRCUIT` 는 그려지지 않는 전원 핀이 14개 있고, `PSpiceDefaultNet`(`$G_DPWR`, `$G_DGND`) 규칙의 정답 사례는 이 설계 하나뿐이다. 소자 줄은 Capture 와 글자까지 같다 (`X_U1A N00440 N00433 $G_DPWR $G_DGND 7405 PARAMS:`).

### 시뮬레이션으로 확인

같은 분석을 Capture 의 `.net` 과 내 넷리스트로 같은 엔진(`craft/circuitcraft-cli/sim.mjs` 의 ngspice)에 돌렸다. 앞쪽 25개 설계, 한 건에 15초 제한.

|---|---|
| 이름 있는 벡터가 모두 같음 (상대 오차 1e-6 미만) | 12 |

| 내 쪽만 실패 | 0 |

PSpice 로 돌려 본 것은 아니다.

## 8. 파서 결함과 처리 (소스는 고치지 않았다)

패치 파일은 없다. 전부 `orcad2json.cpp` 안에서 돌아갔다.

- `StreamLibrary::read()` 는 버전을 추측하며 같은 객체에 반복해 읽어 `strLst` 번호가 밀린다(로그의 `strLst Item @ 40 = DISCRETE`). 표를 직접 읽는다.
- Library 4.x 는 버전 뒤 2바이트 때문에, 2.x 는 레코드 형식이 달라 읽지 못한다. 둘 다 직접 읽는다.
- 인스턴스의 값·회전·구현 정보, 접두의 속성 쌍, 페이지 넷 표는 건너뛰거나(`printUnknownData`) 읽고 버린다. 직접 읽는다.
- `StructPortSymbol` 은 내용을 읽고 버리고, `DrawnInstance`(계층 블록)는 구현이 없다. 직접 읽는다.
- `StructDevice` 는 번호 없는 핀을 건너뛰어 뒤 핀 번호가 밀린다. 자리를 지킨다.
- 파서는 현재 폴더에 `logs/` 를 만들고, spdlog 기본 로거로 stdout 에 쓰며, 파일 쓰기 실패에 `std::exit(1)` 한다. 임시 폴더, 자체 sink, 자식 프로세스로 막았다.
- 파서는 스트림을 `replace_extension(".bin")` 으로 풀어, 마지막 점 뒤만 다른 이름이 한 파일에 겹친다. 넓은 묶음의 `lib1.OLB` 두 개에서 `AMS1117-3.3` 과 `AMS1117-3.3V` 중 하나가 실제로 사라졌다. 겹친 스트림만 온전한 이름으로 다시 풀어 둘 다 읽는다.

`craft/pspice/pspice.mjs` 에서 동작 버그는 찾지 못했다. 사소한 것 둘: 뜻 없는 삼항식 `lines.slice(lines[0]?.comment ? 1 : 1)`, `write()` 가 언제나 `.PROBE` 를 덧붙인다.

## 9. `.DSN`, `.OLB` 쓰기 가능성 (쓰지 않았다, 조사만)

이 파서의 지식으로는 안전하게 쓸 수 없다. 쓰는 CFBF 라이브러리가 없고(`compoundfilereader` 는 읽기 전용), 파서는 뜻을 모르는 바이트를 건너뛰기만 해서 되쓰면 잃으며, 레코드 길이 접두, 공유 문자열 표, 디렉터리와 `Hierarchy` 표를 모두 다시 만들어야 한다. 무엇보다 Capture 없이는 받아 주는지 확인할 방법이 없다. 현실적인 길은 원본 바이트를 그대로 두고 값만 바꾸는 좁은 수정 정도이고, 이것도 Capture 로 검증해 봐야 한다.

## 10. 확인하지 못한 것과 한계

- PSpice 로 돌려 본 적이 없다. Capture 도 PSpice 도 없다. 시뮬레이션 비교는 ngspice 뿐이다.
- 같은 회로도를 여러 번 쓰고 인스턴스마다 참조 이름을 다르게 주는 보드(`claudiolorini__TB9.DSN`, 쪽 18, 조각 3243)는 인스턴스별 참조를 찾지 못한다. 연결은 펼쳐지지만 참조 이름은 `PC9_C9` 처럼 경로로 붙고, 값이 다른 것이 섞였다고 경고한다. 이런 설계의 정답 넷리스트로는 확인하지 못했다.
- 계층 설계 일부의 `Hierarchy` 표를 읽지 못한다(넓은 묶음에서 `TB9` 포함 설계 4개). 교차 확인 없이 진행하고 경고한다.
- 그려지지 않는 전원 핀의 규칙은 정답 설계 하나로만 확인했다.
- 버스: 이름 펼치기는 넷 수가 맞는 것으로만 확인했다. 버스에 직접 닿은 핀은 다루지 않는다.
- 옛 형식(Library 2.x)은 길이 정보가 없어 읽기 실수를 바로 알아채기 어렵다. 그림 요소 일부와 ERC 표시는 읽지 않으며, 포트 끝부분과 `SymbolVector` 는 옛 형식 표본으로 확인하지 못했다. 정답 비교는 소수뿐이고 그중 `UA741` 은 옛 넷리스트다.
- BeagleBone AI 의 `02 Block Diagram` 쪽에서 레코드 하나를 읽지 못해 건너뛰고 경고한다. 이 쪽에 부품은 없고 3절 대조에 영향이 없다.
- 넷리스트에 `.lib` 는 넣지 않는다. Capture 의 `.net` 도 넣지 않는다. 모델 파일은 따로 줘야 돈다.
- 템플릿의 값은 글자 그대로 옮긴다. `1M` 은 Capture 처럼 밀리다.
- 심볼 라이브러리의 핀은 공개 핀 배치로 몇 개(AD817, AD8072, LM6182, TPS72301)만 맞춰 봤다.
- macOS arm64 에서만 빌드하고 돌렸다.
