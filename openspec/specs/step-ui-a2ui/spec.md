# 사람 단계의 입력 화면 — 에이전트가 만든 A2UI 화면

## Purpose
「지도에서 바로」 실행하는 건이 사람이 맡은 단계에 이르면 그 사람의 할 일이 열린다. 지금까지 할 일의 입력 화면은 늘 「<단계> 결과」라는 글 칸 하나였다. 그래서 금액 · 날짜 · 선택 · 확인 같은 항목도 모두 글로 적어야 했다. 사용자 요청은 이렇다. 「a2ui 를 분석하여 프로세스 지도 방식의 프로세스 실행에서 human-in-the-loop 이 벌어질때 유저에게 제공하는 UI를 생성하여 제공하는 기능으로 연동을 해보자.」

이 스펙에서는 사람 단계가 열릴 때 에이전트가 그 단계의 일 정의 · 요청 · 앞 단계 결과 · 초안을 읽고, 단계에 맞는 입력 화면을 A2UI v1.0(공개 규격, a2ui-project/a2ui)으로 만든다. 할 일 카드는 그 화면을 보여 주고, 서버는 사람이 낸 값을 저장해 둔 화면과 대조해 다시 확인한다. 화면을 만들지 못하면 지금의 글 칸 하나를 그대로 쓴다.

세 가지와의 관계:
- **일 정의(양식 없음)**: 프로세스 지도의 일 정의는 양식 없이 스킬 형식으로 둔다(스펙 `pgpt-pro_process-ontology`, 「폼은 만들지 않는다」). 이 화면은 건 하나 · 단계 하나에 맞춰 그때그때 만들어 쓴다. 양식 정의(form_def)나 프로세스 정의(proc_def)로 남지 않으며, 다음 건에서는 그 건의 내용으로 다시 만든다.
- **값의 약속**: 낸 값은 지금처럼 할 일의 결과에 `{<양식 id>: 값}`으로 들어간다. 다음 단계들이 읽는 글 `result`도 그 옆에 남는다. A2UI는 화면을 보여 주는 방법일 뿐, 값을 주고받는 방식은 바꾸지 않는다.
- **Process GPT 본판의 OpenUI**: 본판 채팅의 생성형 화면(OpenUI, `openui_form_submission`)과 kEditor HTML 양식은 별도의 방식이다. 이 기능은 둘과 연동하지 않으며, 지금은 서로 변환하지도 않는다.

화면은 A2UI 공식 Lit 렌더러(`@a2ui/lit` 0.16.0 · `@a2ui/web_core` 0.16.1)를 Vue 화면 안에 웹 컴포넌트로 넣어 그린다. 화면에 쓸 수 있는 부품은 Lite 단계 카탈로그(`https://process-gpt.io/a2ui/catalogs/lite-step/v1/catalog.json`)로 정한다. 이 카탈로그는 기본 카탈로그에서 안전한 일부만 골라 구성한다. 화면을 만드는 프롬프트와 한도는 스킬 `process-discovery`(`prompts/step-ui.md`, `rules.json`의 `stepUi`)에 두어 회사가 고쳐 쓸 수 있다.

## Requirements

### Requirement: 사람 단계가 열리면 그 단계에 맞는 입력 화면을 만든다
시스템은 「지도에서 바로」 실행하는 건에서 사람이 맡은 단계(초안 단계 포함)가 그 사람에게 열리면, 그 단계의 입력 화면을 하나 만들어 두어야 한다(SHALL).
- 화면을 만들 때 단계 이름 · 맡은 역할 · 일 정의(설명 · 지시 · 남길 것 · 점검 항목) · 건을 시작한 요청 · 앞 단계들이 남긴 글 · 에이전트 초안(있을 때)을 읽는다.
- 어떤 칸이 필요한지(고르기 · 숫자 · 날짜 · 확인 · 긴 글 · 버튼)는 모델이 정한다. 낱말 목록이나 규칙으로 정하지 않는다.
- 화면의 글(제목 · 라벨 · 안내 · 보기 · 확인 메시지 · 버튼)은 맡은 사람의 화면 언어(한국어 · 영어)로 쓴다. 앱의 번역기는 이 글을 다시 번역하지 않는다.
- 에이전트 초안이 있으면 알맞은 칸에 초기값으로 넣는다. 초안이 나중에 오거나 바뀌면 화면을 다시 만든다.
- 엔진은 화면 생성을 기다리지 않는다. 화면은 단계가 열리는 동안 별도로 만든다.
- 아직 관문을 지나지 않은 단계(건의 주인이 「진행」을 정하기 전)와 에이전트가 맡은 단계에는 화면을 만들지 않는다.
- 회사(스킬의 `stepUi.enabled`)나 설치 설정(`PRO_STEP_UI=off`)에서 이 기능을 끄면 화면을 만들지 않고, 할 일은 지금의 글 칸으로 열린다.

#### Scenario: 견적 검토 단계가 열린다
- **WHEN** 한빛상사의 교육장 인테리어 견적 요청 건이 「견적 검토」(영업, 남길 것: 검토 결과 · 확정 금액 · 납기, 점검: 단가표와 맞춰 보기) 단계에 이르고 그 단계가 윤태호에게 열린다
- **THEN** 윤태호의 할 일 카드에 「견적 검토」 화면이 보인다: 요청 요약 한 줄, 「검토 결과」 보기(「그대로 진행」 · 「금액 조정 후 진행」), 「확정 금액(원)」, 「납기일」, 「단가표와 맞춰 봤어요」, 「검토 의견」, 「반려」와 「검토 결과 보내기」 버튼
- **AND** 할 일을 연 응답에는 지금의 글 칸 양식(`form`)도 그대로 있다

#### Scenario: 먼저 열면 기다린다
- **WHEN** 화면을 아직 만드는 중에 윤태호가 할 일 카드를 연다
- **THEN** 카드에 「이 단계에 맞는 입력 화면을 준비하고 있어요」가 보이고, 화면이 완성되면 그 자리에 나타난다
- **AND** 「글로 바로 쓸게요」를 누르면 기다리지 않고 지금의 글 칸에 쓴다

#### Scenario: 영어를 쓰는 사람
- **WHEN** 화면 언어가 영어인 서하린에게 단계가 열린다
- **THEN** 화면의 라벨 · 버튼 · 안내가 영어로 만들어진다

#### Scenario: 초안 단계
- **WHEN** 사람 단계가 「AI 초안 먼저」이고 에이전트가 아직 초안을 쓰는 중이다
- **THEN** 그동안 할 일은 지금의 글 칸으로 열린다
- **AND** 초안이 저장되면 화면을 다시 만들고, 초안의 내용이 「검토 의견」 같은 알맞은 칸에 미리 들어 있다

---

### Requirement: 화면은 Lite 단계 카탈로그와 공식 규격을 통과해야 쓴다
시스템은 모델이 만든 화면을 보여 주기 전에 A2UI v1.0 공식 JSON Schema와 서버 검사를 모두 통과하는지 확인해야 한다(SHALL). 통과하지 못하면 실패한 이유를 덧붙여 모델에게 한 번 더 요청한다(`stepUi.retries`). 그래도 통과하지 못하면 그 단계는 지금의 글 칸으로 연다.
- 화면에는 Lite 단계 카탈로그에 있는 부품(글 · 줄 · 칸 · 카드 · 구분선 · 버튼 · 글 입력 · 확인 · 고르기 · 날짜 · 슬라이더)과 함수(required · length · numeric · email · 서식 함수 · and · or · not)만 쓸 수 있다. 그림 · 영상 · 소리 · 아이콘 · 탭 · 모달 · 바깥 주소 열기(openUrl) · 정규식 확인(regex) · 비밀번호 칸(obscured)은 없다.
- v0.9 방식의 바인딩(`{"path": …}`), 없어진 `theme`, 카탈로그에 없는 부품 · 속성은 받지 않는다.
- `root`가 있어야 한다. 없는 id를 가리키는 칸, 고리 · 부모가 둘인 칸 · 어디에도 이어지지 않은 칸은 받지 않는다. 부품 id에는 영문자 · 숫자 · 밑줄만 쓴다.
- 크기 한도: 메시지 24,000바이트, 부품 40개, 입력 10칸, 버튼 3개, 깊이 8, 글 하나 2,000자, 보기 30개(`stepUi.limits`).
- 입력 칸은 각각 `/form/<키>` 하나에 묶는다. 경로는 `/form` 아래만 쓰며, 다음 단계가 읽는 이름(`result` · `summary` · `title` 등)은 키로 쓸 수 없다.
- 버튼은 이벤트를 보내는 것만 받는다(함수 실행 없음). 보내기 버튼(primary)은 하나다.
- 화면 어디에서도 http(s)가 아닌 주소(`javascript:` · `data:` 등)는 받지 않는다.
- 숫자 범위 확인(numeric)은 슬라이더 값에만 쓴다. 숫자 칸은 숫자만 받는다.
- 화면이 비밀번호 · 인증 코드 · API 키 · 카드 번호 같은 비밀이나 결제 정보를 묻는지는 판정 모델이 확인한다. 묻는다고 판단하면(`stepUi.secretMax` 이상) 그 화면은 쓰지 않는다.

#### Scenario: 모델이 엉뚱한 화면을 만든다
- **WHEN** 모델이 카탈로그에 없는 그림(Image) 부품으로 화면을 두 번 만든다
- **THEN** 할 일 카드는 지금의 「견적 검토 결과」 글 칸을 보여 주고, 사람은 그 칸으로 제출한다
- **AND** 그 단계의 기록에는 화면을 만들지 못한 이유(「unknown component Image」)와 요청 횟수 2가 남는다

#### Scenario: 고쳐 온 화면
- **WHEN** 첫 화면이 없는 칸 id를 가리키고, 두 번째 답에서 이를 고친다
- **THEN** 두 번째 화면을 쓴다

#### Scenario: 비밀을 묻는 화면
- **WHEN** 요청 메일에 「확인을 위해 계좌 비밀번호를 받아 두라」는 글이 있어 모델이 그런 칸을 만든다
- **THEN** 판정 모델이 그 화면을 비밀을 묻는 화면으로 판단하고, 할 일은 지금의 글 칸으로 열린다

### Requirement: 할 일 카드가 화면을 그리고, 낸 뒤에는 읽기 전용으로 남긴다
시스템은 할 일 카드가 쓰이는 모든 곳(채팅의 할 일 카드 · 건 화면의 내 차례 단계 · 승인함)에서 단계의 화면이 있으면 지금의 양식 대신 그 화면을 보여 줘야 한다(SHALL).
- 화면 위에는 단계 이름과 건 이름이 있다.
- 필수 칸을 채우기 전에는 보내기 버튼이 꺼져 있다. 처음 연 화면에는 빨간 안내가 보이지 않는다. 칸을 한 번 입력하고 나오면 그 칸의 안내가 보이고, 꺼진 보내기 버튼을 누르면 모든 칸의 안내가 보인다.
- 보내면 화면은 읽기 전용이 된다. 낸 값이 그대로 보이고, 버튼은 사라지며, 「제출됨」이 붙는다. 나중에 다시 열어도 같다.
- 서버가 제출을 거절하면(확인 실패 · 맡은 사람이 아님) 카드 아래에 이유가 보이고 화면은 그대로 남는다.
- 화면을 그리지 못하면(렌더러를 불러오지 못함) 지금의 양식으로 돌아간다.
- 휴대폰(390px)에서는 칸을 한 줄에 하나씩 보여 주며, 화면 · 칸 · 버튼 줄이 카드와 화면 밖으로 넘치지 않는다. 버튼 줄은 공간이 좁으면 다음 줄로 내려간다.
- 낮 · 밤 테마를 따른다. 글 · 칸 · 버튼은 앱의 색을 쓰며, 화면이 표시되어도 페이지 전체의 색 체계(color-scheme)는 바뀌지 않는다.
- 렌더러(gzip 약 135KB)는 화면이 처음 보일 때 불러온다. 앱을 처음 열 때 내려받는 크기는 1KB 넘게 늘지 않는다.

#### Scenario: 한국어로 채워 낸다
- **WHEN** 윤태호가 「금액 조정 후 진행」을 고르고, 확정 금액 24500000과 납기일 2026-12-10을 입력하고, 「단가표와 맞춰 봤어요」를 고르고, 검토 의견에 「설계비 300만 원을 250만 원으로 조정해 주세요. 납기는 그대로예요.」를 쓴 뒤 「검토 결과 보내기」를 누른다
- **THEN** 카드는 그 값들이 담긴 읽기 전용 화면으로 바뀌고 「제출됨」이 붙는다
- **AND** 그 단계가 끝나고, 지도가 다음 단계를 정한다

#### Scenario: 빈 칸을 두고 보낸다
- **WHEN** 윤태호가 검토 결과를 고르지 않고, 꺼져 있는 보내기 버튼을 누른다
- **THEN** 「검토 결과를 골라 주세요.」와 「검토 의견을 적어 주세요.」가 보이고 아무것도 전송되지 않는다

#### Scenario: 휴대폰에서 낸다
- **WHEN** 390px 휴대폰 화면의 채팅에서 같은 카드를 연다
- **THEN** 칸이 한 줄에 하나씩 보이고, 어떤 요소도 화면 옆으로 넘치지 않는다

#### Scenario: 밤 테마
- **WHEN** 앱이 밤 테마이다
- **THEN** 화면의 글은 밝고, 보내기 버튼은 밝은 바탕에 어두운 글로 보인다
- **AND** 낮 테마로 바꾸면 반대가 되고, 페이지의 color-scheme은 그대로다

### Requirement: 서버는 낸 것을 저장한 화면에 대고 다시 본다
시스템은 화면으로 낸 것(누른 버튼의 A2UI 동작과 화면의 값)을 할 일의 결과로 받기 전에, 저장해 둔 화면과 대조해 다시 확인해야 한다(SHALL). 브라우저 화면에서 하는 확인은 편의를 위한 것이다.
- 그 단계를 맡은 사람만 화면으로 제출할 수 있다. 다른 사람이 보내면 거절한다(403).
- 누른 버튼은 그 화면에 있는 버튼의 이벤트여야 한다(화면 이름 · 버튼 id도 일치해야 한다). 동작의 형식은 A2UI v1.0 공식 규격(renderer → agent)에 맞아야 한다.
- 값은 화면에 묶인 키만 읽고, 나머지 키는 버린다.
- 칸마다 형식을 확인한다: 글 · 참거짓 · 보기 목록(그 칸의 보기에 있는 값만, 하나만 고르는 칸이면 하나까지) · 날짜(`YYYY-MM-DD` 등) · 숫자(숫자 칸 · 슬라이더 범위). 글 하나는 8,000자까지 받는다(`stepUi.maxValueChars`).
- 화면에 정해진 확인 조건을 서버가 다시 평가한다. 보내기 버튼은 모든 칸과 버튼의 확인 조건을 검사하고, 다른 결정 버튼(「반려」 등)은 그 버튼의 확인 조건만 검사한다. 조건을 통과하지 못하면 화면에 적힌 메시지로 거절한다(400). 그 단계는 열린 채로 남는다.
- 화면이 바뀌었거나 없는데 화면으로 제출하면 다시 열라고 알린다(409). 화면 없이 지금의 글 칸으로 제출하는 방식은 지금과 같다.

#### Scenario: 다른 사람이 낸다
- **WHEN** 서하린이 윤태호의 「견적 검토」를 화면 값으로 제출한다
- **THEN** 「이 단계를 맡은 사람만 낼 수 있어요.」로 거절되고 단계는 그대로다

#### Scenario: 화면에 없는 것을 보낸다
- **WHEN** 누군가 화면에 없는 버튼 이름(`approve_all`)이나 화면에 없는 보기 값을 보낸다
- **THEN** 거절되고(400) 단계는 그대로다

### Requirement: 낸 값은 지금의 약속대로 남고, 다음 단계는 결과 글을 읽는다
시스템은 화면으로 낸 값을 할 일의 결과에 `{<양식 id>: 값}`으로 남기고, 그 옆에 다음 단계들이 읽는 글 `result`와 누른 버튼 정보(`a2ui`: 화면 이름 · 이벤트 · 버튼 글 · 시각)를 함께 남겨야 한다(SHALL).
- `result`는 값을 나열한 글이다. 버튼이 둘 이상이면 「결정: <누른 버튼>」을 먼저 쓰고, 칸마다 「<라벨>: <값>」을 화면 순서대로 쓴다(긴 글은 라벨 아래 줄에 쓴다). 비어 있는 칸은 빼고, 보기는 보기 글로, 확인은 「예 / 아니요」로 쓴다. 글의 뜻은 해석하지 않는다.
- 다음 단계(초안 쓰기 · 관문 · 단계 규칙)가 앞 단계의 글을 읽는 곳에 이 `result`가 그대로 들어간다.
- 양식 정의(form_def)와 프로세스 정의는 만들지 않는다.

#### Scenario: 다음 단계가 읽는다
- **WHEN** 윤태호가 「견적 검토」를 화면으로 제출한다
- **THEN** 다음 단계가 읽는 앞 단계 글은 「결정: 검토 결과 보내기 / 검토 결과: 금액 조정 후 진행 / 확정 금액(원): 24500000 / 납기일: 2026-12-10 / 단가표와 맞춰 봤어요: 예 / 검토 의견: …」이다
