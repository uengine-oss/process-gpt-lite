## 결과
- 단위 BT-U-01~07 7/7: 이름에 따라 값만 가리는지 확인했다. 쿼리 · fragment · 해시 경로 · `;` 구분 · 대소문자 · %-인코딩과 키 · 서명 이름들을 확인했다. `code`는 `state`와 함께 있거나 이 앱 · 로그인 서버 주소일 때만 가리는지 확인했다. 값 안의 주소 한 단계, 주소 안의 사용자 이름 · 비밀번호, 세션 JSON fragment, 주소가 제목인 페이지의 제목, 가린 값을 뺀 주소를 확인했다. 데스크톱 사본(`maskUrl` · `maskTitle`)이 서버 함수와 같은지 확인했다. 로그인으로 들어가는 길의 판정을 확인했다. 로그인 서버의 단계는 로그인 서버와 이 앱의 주소에서 판정한다. Lite 로그인 API와 로그인 화면은 이 앱의 페이지에서만 판정한다. 같은 기계의 다른 사이트 `/login`은 해당하지 않는다. Fetch 패턴은 해당 호스트의 페이지 로드와 `/auth/v1/` · `/api/auth/` 아래 요청에만 적용한다.
- 단위 BT-C-01: 이 앱의 로그인 단계로 가는 링크가 든 메일의 코드를 넣지 않는지 확인했다.
- 실제 Chromium BT-E-01~11 11/11: 직접 이동 · 다른 사이트의 302 · callback · verify · `/lite/auth/v1/…` · 대소문자 · %-인코딩, 링크 · 프레임 · 새 창(window.open) · 새 탭 링크(noopener)가 첫 요청부터 차단되어 로그인 서버에 닿지 않는지 확인했다. Lite의 로그인 화면 · 완료 화면 · 「Google로 계속하기」 시작 주소와 ProcessGPT의 로그인 · 가입 · 비밀번호 찾기 화면이 열리지 않는지 확인했다. Lite 화면의 코드 받기 · 코드 확인 요청과 이 앱 화면 및 다른 사이트에서 보낸 비밀번호 로그인 요청이 서버에 닿지 않는지 확인했다. 이 앱의 Google 연결(콜백 → 끝 화면)과 보통 페이지가 열리는지 확인했다. 보통 사이트와 이 앱 호스트 페이지의 스크립트 · 그림을 한 번만 받는지 확인했다(캐시 유지). Playwright route가 함께 있어도 차단되는지 확인했다. 이때 Playwright가 캐시를 끄고 스크립트를 다시 받은 사실을 기록했다. Google 단계를 20 ms로 두고 새 탭 링크와 새 창을 각각 20번 열었을 때 로그인에 닿은 횟수가 0임을 확인했다. `--site-per-process`로 띄운 브라우저에서 다른 사이트의 프레임이 로그인으로 이동해도(3번) 로그인에 닿은 횟수가 0임을 확인했다. 차단을 켜지 못하면 브라우저 실행이 실패하고 해당 Chromium이 닫히는지 확인했다.
- 실제 Chromium · Electron BT-M-01~05 5/5: `?code=…&state=…#access_token=…&refresh_token=…` 주소에 닿은 작업에서 모델 · 판정 모델 · 실시간 화면 · 카드 · 결과 · lastFrame · 로그에 값이 가려진 주소만 전달되는지 확인했다. 내 PC의 브라우저는 보여 줄 주소(답의 url · 실시간 화면 · 보기)부터 가리고, 원래 주소는 돌아가기용으로만 보내는지 확인했다. 서명된 주소에서 끝난 카드에서 이어서 실행하면 원래 서명 값이 든 주소가 열리는지 확인했다. 에이전트가 본 가려진 주소로 다시 이동하면 원래 주소가 열리는지 확인했다. 이 서버가 모델에 전한 내용에 해당 값이 없는지 확인했다. PC 답의 원래 주소가 실시간 화면의 가려진 주소에 덮이지 않는지 확인했다.
- 단위 BT-U-08 · 09: 설치형(공개 주소 `http://localhost:18080`)에서 이 앱의 다른 루프백 이름(`127.0.0.1` · `app.localhost` · `[::1]`, 같은 포트)은 열리고 해당 주소의 로그인 화면 · 코드 확인 · verify는 차단되는지 확인했다. `web` · `kong` · 다른 포트 · 클러스터 이름과 주소 · 링크 로컬은 차단되고, 메일함은 허용 목록에 있어도 차단되며, 내부 주소로 해석되는 이름은 페이지 로드에서 차단되는지 확인했다. 공개 사이트와 허용 목록(출처 · 호스트 · `*.접미사`)의 주소는 열리는지 확인했다. ProcessGPT의 SSO 교환은 요청 종류와 관계없이 모두 차단되고, `/auth`는 페이지로 여는 요청이 차단되는지 확인했다.
- 실제 Chromium BT-E-12~14: 공개 주소가 `http://localhost:<포트>`인 설치 환경처럼 실행한 브라우저에서 이 앱의 다른 루프백 이름으로 화면은 열리고 로그인은 차단되는지 확인했다. 다른 포트 · `web` · `kong` · `mailpit` · 클러스터 이름 · 링크 로컬은 열리지 않고 요청이 해당 서버에 도달하지 않으며, 이 앱의 페이지가 다른 포트와 `web`으로 보내는 요청도 전송되지 않는지 확인했다. 허용 목록의 출처는 열리고 다른 출처는 열리지 않으며, 메일함은 허용 목록에 있어도 열리지 않는지 확인했다. 다른 사이트가 경로를 %-인코딩하거나 `/`를 겹쳐 써서 보내는 로그인 요청과 SSO 교환 요청이 서버에 도달하지 않고, `/auth` 페이지가 열리지 않는지 확인했다.
- 보통 사이트에서 일시 중지한 요청(측정): example.com 2개 중 1개, wikipedia.org 7개 중 1개, naver.com 218개 중 8개 — 모두 페이지와 프레임의 로드이며, 해당 페이지가 불러오는 다른 요청은 일시 중지되지 않았음을 확인했다.
