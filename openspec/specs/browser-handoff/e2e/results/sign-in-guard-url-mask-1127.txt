## 결과
- 단위 BT-U-01~06 6/6: 쿼리 · fragment · 해시 경로 · 대소문자 · %-인코딩에서 이름을 기준으로 값만 가리는지 확인했다. 세션 JSON fragment와 주소 안 비밀번호를 가리는지 확인했다. 데스크톱 사본이 서버 함수와 같은지 확인했다. 게이트웨이 회사 주소 · /lite 아래 · 설치형 주소에서 로그인 단계를 판정하는지 확인했다. Fetch 패턴이 해당 호스트의 문서에만 적용되는지 확인했다.
- 실제 Chromium BT-E-01~07 7/7(세 번 연속 통과): 직접 이동 · 다른 사이트의 302 · callback · verify · `/lite/auth/v1/…` · 대소문자 · %-인코딩을 모두 막아 로그인 서버에 요청이 가지 않는지 확인했다. 링크와 프레임도 막히는지 확인했다. 새 창(window.open)과 새 탭 링크(noopener)는 해당 탭이 닫히고 callback과 토큰 페이지에 닿지 않는지 확인했다. 새 탭 링크는 탭의 첫 요청이 나간 뒤에 닫힌다(시험의 가짜 Google 단계는 300ms). 보통 사이트와 이 앱 호스트 페이지의 스크립트 · 그림은 캐시를 유지해 한 번만 받는지 확인했다. 이 앱의 Google 연결 주소(`/lite/api/auth/google/callback`)와 로그인 서버의 다른 주소는 열리는지 확인했다. Playwright route가 함께 있어도 동일하게 막히는지 확인했다(그때는 Playwright가 캐시를 끄고 스크립트를 다시 받았다 — 기록용).
- 실제 Chromium · Electron BT-M-01~02 2/2: `?code=…#access_token=…&refresh_token=…` 주소에 닿은 작업에서 모델 · 판정 모델 · 실시간 화면 · 카드 · 결과 · lastFrame · 로그에 값이 가려진 주소만 전달되는지 확인했다. 내 PC의 브라우저는 주소를 보내는 단계(답마다의 페이지 · 실시간 화면 · 보기)부터 값을 가리는지 확인했다.
