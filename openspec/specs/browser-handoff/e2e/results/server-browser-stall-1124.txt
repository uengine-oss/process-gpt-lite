# 서버 브라우저가 멈춘 것처럼 보이던 것 — 다시 돌려 잰 전후 (2026-11-24)

사용자 보고: 「이 작업을 시켰는데, 멈췄음... 브라우저가 먹통이 된」(계룡대 인근 12월 18~20일 숙소 검색 → 네이버 여행 화면 ·
단계 「계룡대 인근 숙소 검색 비교」에서 멈춘 뒤 「작업을 취소했어요.」), 「순수 모바일에서는 이 작업이 가능해야하니 서버사이드에서의 문제도 테스트해봐」.

## 어떻게 쟀나
- 맥 한 대, 서버 모듈을 그대로(lib/browser.js runBrowserTask), Playwright 1.64.1 headless shell(운영 이미지와 같은 `--only-shell`),
  사내 모델 게이트웨이의 frentis-ai-model(운영과 같은 모델), 운영처럼 PRO_BROWSER_GATES=off · 판정 서버 없음(판정은 모델), 실제 DB.
- 작업마다 5분(처음 한 번은 6분)에서 끊고 cancel() — 끊은 뒤 실제로 멈추기까지 걸린 시간도 잼.
- 이벤트 버스를 구독해 5초마다 실시간 화면 장수 · 바이트, 알약(status) 줄, 카드 변화, 동작마다 걸린 시간(읽기 · 판정 · 사진 · 모델 · 동작)을 남김.
- 「전」은 origin/main 7248b8f 의 server 사본, 「후」는 이 브랜치. 같은 기계에서 하나씩(겹치지 않게).
- 검색어는 공개 지명(계룡대 · 강릉 · 대전역)뿐, 로그인한 계정 없음.

## 운영 파드 (process-gpt-k8s deployments/process-gpt-lite.yaml, 읽기만)
- process-gpt-lite-server: requests cpu 200m · memory 512Mi, limits cpu 2 · memory 4Gi, replicas 1, Recreate, /data PVC 10Gi
- PRO_BROWSER_GATES=off, PRO_LLM_BASE_URL=litellm-proxy, 모델 frentis-ai-model, PRO_JUDGE_URL 없음(판정은 모델)
- 메모리: 잰 동안 Chromium 브라우저 프로세스 100~250MB, 서버 프로세스 180~290MB — 한도와 거리가 멀어 까닭이 아님

까닭(멈춘 것처럼 보인 순서대로)
1. 모델이 30~50초 걸리는 턴(이미지 포함 요청의 게이트웨이 지연 — 같은 요청을 글만으로 다시 보내면 2~8s, 이미지를 붙이면 4.8~9.9s, 그때그때 크게 흔들림)에 화면이 아무 말도 하지 않았다.
2. 할 일이 없는 페이지에서 wait_for_page 가 분 단위로 돌았다(잘못 고른 글자 · 칸 안의 글자 · 사라지지 않는 오류 문구).
3. 취소가 그 걸음이 끝나야 들었다.
4. 그 밖: 사라진 요소 11초, 지도 결과(iframe)를 못 읽음 → 같은 단추 되풀이, 초당 10장 가까운 실시간 화면.
까닭이 아니었던 것: 큰 DOM 읽기(노드 24만 개에 옛 읽기 0.1s), networkidle(옛 코드도 domcontentloaded 만 기다림), 프로필 잠금(잰 동안 띄우기 실패 없음), 메모리.
모델이 숙소 사이트에서 결과까지 가지 못하는 것(네이버 여행 리다이렉트, booking.com 날짜 고르개)은 남은 일이다 — 이제는 그 사실을 말하고 끝내거나, 기다리는 중이라고 보이거나, 사람에게 넘긴다.

## 페이지 읽기 벤치(시험 사이트, 옛 읽기 → 새 읽기)
- 숙소(노드 4,517): 5ms → 8ms · 노드 6만: 30ms → 50ms · 노드 24만: 107ms → 203ms(한도 1.5s 안). 옛 읽기는 내려도 글이 문서 맨 앞 2500자 그대로, 새 읽기는 화면의 글.
