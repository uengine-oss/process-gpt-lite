# 서버 브라우저 작업의 진행 표시와 사람에게 넘기기

## Purpose
서버 브라우저 작업은 사람이 볼 수 없는 곳에서 돈다. 이 스펙은 작업이 어디를 누르는지 보여 주는 방식, 막힌 화면(로그인·거절·사람 확인)을 알아보고 사람에게 넘기는 방식, 멈추거나 실패했을 때 무엇이 필요하고 무엇을 하면 되는지 말하는 방식, 사이트 로그인을 배포 뒤에도 남기는 방식을 정한다. 근거는 2026-11-21 휴대폰 녹화의 「확인 필요」와 사용자 지시 「사용자에게 조치가능하게 올바른 오류 메시지」(결정 D-1121-10)다.

## Requirements

### Requirement: 멈추면 무엇이 필요한지와 할 일을 말한다
시스템은 서버 브라우저 작업이 사람을 기다리거나 실패하거나 확인이 필요한 채 끝나면, 작업 카드 내용에 `need`와 `reason`을 넣어야 한다(SHALL). 사이트 이름을 알면 `siteName`도 넣는다. `need`는 `login`·`blocked`·`captcha`·`choice`·`approve`·`stuck`·`other` 중 하나다. `reason`에는 사람이 이해할 수 있는 말로 두 가지를 쓴다. 무엇 때문에 멈췄는지, 그리고 무엇을 하면 이어지는지다. 작업이 다시 진행되거나 끝나면 둘을 비운다.

화면은 「확인 필요 · <제목>」 대신 `need`별 짧은 말을 알약에 보여 주어야 한다(SHALL). 예: 「로그인 필요 · NotebookLM」, 「구글이 로그인을 막음」, 「같은 화면에서 멈춤」. 카드에는 `reason` 전체를 잘리지 않게 보여 주고, 그 일에 맞는 첫 번째 단추를 크게 둔다. 단추는 로그인 → 「직접 로그인」, 헛돎·기타 → 「직접 확인」, 막힘·실패 → 「멈추기」 또는 「다시 시도」, 선택·승인 → 응답할 카드로 가기다. 카드가 기다림·실패·완료로 바뀌면, 대화 맨 아래를 보던 화면은 그 이유와 단추가 입력창에 가리지 않게 따라 내려간다.

#### Scenario: 녹화의 순서 — NotebookLM 로그인
- **GIVEN** NotebookLM 규칙이 있는 방이고, 서버 브라우저가 구글에 로그인되어 있지 않다
- **WHEN** 유튜브 링크를 올린다
- **THEN** 몇 초 안에 작업 카드가 `needs_input`·`need: login`이 되고 `siteName`은 페이지에서 읽은 이름이다. 알약은 「로그인 필요 · <사이트 이름>」이다
- **AND** 카드에 「이 브라우저에서 <사이트>에 한 번 로그인해야 이어서 할 수 있어요. 카드의 「직접 로그인」을 눌러 로그인하면 이어서 진행해요. 로그인은 다음에도 남아요.」와 「직접 로그인」 단추가 입력창 위로 보인다(390×844)

#### Scenario: 실패한 작업
- **WHEN** 작업이 실패로 끝난다
- **THEN** 알약에 완료 표시가 아니라 경고 표시가 뜨고, 왜 실패했는지와 다시 시도할 수 있는지가 보인다

### Requirement: 막힌 화면은 모델이 알아보고 바로 사람에게 넘긴다
시스템은 서버 브라우저가 새 페이지에 닿을 때마다(주소가 바뀔 때) 그 페이지가 막힌 화면인지 모델에 한 번 판정을 요청해야 한다(SHALL). 판정에 넘기는 것은 할 일 한 줄, 페이지 제목, 호스트, 보이는 글 앞부분, 비밀번호·로그인 칸이 있는지, 단추 이름 목록이다(칸에 입력한 값은 넘기지 않는다). 보기는 로그인 필요 · 거절(사이트가 이 브라우저의 로그인·이용을 허용하지 않음) · 사람 확인 · 사이트 오류(사이트가 페이지 대신 자체 오류 화면을 표시함) · 문제없음이다. 확률이 기준(0.7) 이상일 때만 따른다.

- 로그인 필요: 모델에게 다음 동작을 묻지 않고 바로 사람을 기다린다(`need: login`). 사람이 로그인을 마치면 자동으로 이어서 진행해야 한다(SHALL). 막힌 상태가 풀렸는지는 주기적으로 묻지 않고, 화면이 바뀌었을 때나 직접 제어를 돌려줄 때 한 번 다시 판정한다. 같은 화면에 막혀 세 번 넘게 기다리게 되면 실패로 끝내고 그 이유를 말한다.
- 거절: `need: blocked`로 실패 처리하고, 이유와 다른 방법(그 사이트에서 직접 만든 결과 파일을 방에 올리기)을 알린다.
- 사람 확인: `need: captcha`로 사람을 기다린다.
- 사이트 오류: 일반 작업에서는 막힌 화면으로 보지 않고 에이전트가 평소처럼 진행한다(뒤로 가거나 다른 방법을 찾는다). Google 연결처럼 다른 방법이 없으면 거절과 같은 방식으로 끝낸다.
- 판정을 받지 못하거나 기준보다 낮으면 평소처럼 에이전트가 진행한다.

막힌 화면을 사이트 주소나 문구 패턴으로 가리지 않는다(MUST NOT). 카드의 사이트 이름은 페이지 자체에서 가져온다(사이트 이름 메타 → 문서 제목 → 호스트). 시스템은 자동화 탐지를 피하는 설정을 쓰지 않는다(MUST NOT).

#### Scenario: NotebookLM 첫 화면
- **WHEN** 작업이 로그인되지 않은 NotebookLM 주소에서 시작한다
- **THEN** 판정이 로그인 필요(실제 모델 0.95, 약 2초)로 나와, 모델 턴 없이 `need: login`이 된다. 카드 이름은 페이지 제목에서 온 것이다
- **AND** 사람이 직접 제어로 로그인하면 저절로 이어진다

#### Scenario: 평범한 페이지
- **WHEN** 작업이 로그인 없이 읽을 수 있는 페이지(예: example.com)를 연다
- **THEN** 판정이 문제없음(실제 모델 0.98)으로 나와 평소처럼 진행한다

#### Scenario: 사이트가 거절한다
- **WHEN** 로그인 도중 사이트가 이 브라우저의 로그인을 받아 주지 않는 화면이 나온다
- **THEN** 작업은 `failed`·`need: blocked`가 된다. 이유와 다른 방법이 카드에 보인다

#### Scenario: 판정을 받지 못한다
- **WHEN** 판정이 실패하거나 0.7보다 낮다
- **THEN** 에이전트가 평소처럼 진행한다

### Requirement: 보관함의 로그인으로 로그인 벽을 넘는다
로그인이 필요한 화면에서 보관함에 해당 사이트의 로그인이 있으면 시스템은 사람을 기다리지 않고 에이전트가 `fill_secret`으로 로그인하게 해야 한다(SHALL). 사이트가 다른 곳에서 로그인을 받으면(NotebookLM은 Google 계정) 해당 사이트의 브라우저 스킬이 `metadata.sign_in`에 로그인하는 곳을 적는다. 보관함에 그곳의 로그인이 있으면 사이트의 첫 화면에서도 에이전트가 로그인 단추를 눌러 그곳에서 로그인한다. 사이트가 지난번에 거부한 비밀번호는 그대로 다시 넣지 않는다(MUST NOT). 먼저 카드에서 비밀번호를 고치게 한 뒤 고친 비밀번호를 넣는다. 같은 비밀번호를 거듭 넣으면 계정이 잠길 수 있기 때문이다. Google 2단계 인증의 「이 기기에서 다시 묻지 않음」은 켠다(스킬 `google-sign-in`). 그러면 다음부터는 저장된 비밀번호만으로 로그인한다.

#### Scenario: 로그인을 다른 곳에서 받는 사이트
- **WHEN** 스킬의 `sign_in` 호스트 로그인이 보관함에 있고, 사이트 첫 화면이 로그인 벽이다
- **THEN** 사람을 기다리지 않고 에이전트가 로그인 단추를 누른 뒤 보관함의 로그인으로 들어가 일을 마친다

#### Scenario: 지난번에 거부된 비밀번호
- **WHEN** 보관함의 로그인이 지난번에 거부됐다
- **THEN** 카드에서 먼저 비밀번호를 고치도록 안내하고, 고치기 전에는 넣지 않으며, 고친 뒤 그 비밀번호로 로그인한다

### Requirement: 같은 화면에서 헛돌지 않는다
시스템은 같은 화면(주소와 화면 내용이 같음)에서 효과 없는 동작이 다섯 번 반복되면, 더 시도하지 않고 `need: stuck`으로 사람에게 넘겨야 한다(SHALL).

#### Scenario: 아무것도 바뀌지 않는다
- **WHEN** 에이전트가 같은 단추를 눌러도 화면이 바뀌지 않는다
- **THEN** 다섯 번째 턴에서 「같은 화면에서 멈춤」으로 사람을 기다린다

### Requirement: 누르는 자리와 하는 일이 보인다
시스템은 서버 브라우저 에이전트가 누르거나 입력하기 직전에, 대상 요소의 가운데 좌표를 실시간 이벤트 `browser.click` `{ taskId, x, y, w, h, kind }`로 보내야 한다(SHALL). 화면은 실시간 화면(작업 카드, 입력창 옆 작업 원, 확장 화면) 위 해당 자리에 잠깐 커졌다 사라지는 원을 그린다. 상태 알약은 요소 이름으로 하는 일을 말한다. 예: 「「새 노트북」 누르는 중」, 「「검색」 칸에 입력 중」, 「notebooklm.google.com 여는 중」. 입력한 값은 이벤트·알약·요약 어디에도 넣지 않는다(MUST NOT). 비밀 칸은 「비밀번호 칸」처럼 종류만 말한다.

#### Scenario: 누르는 자리
- **WHEN** 에이전트가 단추를 누른다
- **THEN** 실시간 화면의 그 단추 자리(±3px)에 원이 뜬다

#### Scenario: 새 탭
- **WHEN** 누른 단추가 새 탭이나 팝업을 연다
- **THEN** 에이전트는 그 탭에서 일하고 실시간 화면도 그 탭을 보여 준다. 탭이 닫히면 원래 페이지로 돌아온다

### Requirement: 걸음마다 한도가 있고, 멈춘 것처럼 보이지 않는다
서버 브라우저 작업의 걸음(페이지 열기 · 페이지 읽기 · 화면 사진 · 모델의 답 · 동작 하나)에는 각각 시간 한도가 있어야 한다(SHALL). 한도를 넘긴 걸음은 멈추고, 그 결과를 모델이나 사람에게 알린다. 근거는 2026-11-24 사용자 보고 「이 작업을 시켰는데, 멈췄음... 브라우저가 먹통이 된」(계룡대 인근 숙소 검색)과 같은 작업을 실제 사이트에서 다시 돌려 잰 결과다(`e2e/results/server-browser-stall-1124.txt`). 그 결과 멈춘 것처럼 보인 까닭은 세 가지였다. 모델의 답이 30~50초 걸리는 동안 알약이 「페이지 읽는 중」에 머물렀다. 일이 없는 페이지에서 기다리기(`wait_for_page`)가 1~3분씩 돌았다. 작업을 취소해도 그 걸음이 끝날 때까지(최대 33초) 멈추지 않았다.

- 한도: 페이지 열기 20초(응답 시작 → 문서까지, 그 뒤 `load`는 최대 1.5초), 읽기 6초, 사진 6초, 동작 하나 15초(그 동작이 사람의 승인을 기다리는 동안은 세지 않음), 모델 한 번 90초(넘기면 한 번 더 묻고, 또 넘기면 「AI 모델이 제때 답하지 않아 …」로 멈춤), 계획 30초(넘기면 계획 없이 시작), 브라우저 띄우기 30초.
- 끝나지 않는 페이지: `networkidle`이나 `load`를 기다리지 않는다(MUST NOT). 문서가 오면 진행하고, 한도 안에 문서가 다 오지 않으면 불러오기를 멈추고 온 만큼 읽는다. 응답이 오지 않아 실패한 이동은 멈춰 두어, 다음 이동이 바로 거부되지 않게 한다.
- 알약: 모델이 생각하는 동안에는 「다음 할 일 고르는 중」, 기다리는 동안에는 「「…」 나오기를 기다리는 중 · 0:45」처럼 무엇을 얼마나 기다리는지 말한다.
- 감시: 20초 동안 다음 걸음으로 넘어가지 않으면 작업 카드 내용에 `stall { what, since, after }`를 넣는다. 화면은 카드 아래에 「기다리는 중 · <무엇>」, 몇 초째인지, 한 줄 설명, 「다시 시도」 · 「그만두기」를 보여 준다. 입력창 옆 독은 호박색 테두리가 된다. 다음 걸음이 시작되거나 작업이 끝나면 `stall`을 비운다. 사람의 답을 기다리는 동안(`needs_input`)은 멈춤이 아니다.
- 「다시 시도」(`POST /api/browser/retry {taskId}`): 하던 걸음(모델 호출, 이동, 기다리기)을 버리고 그 턴을 새로 본 페이지에서 다시 한다. 에이전트의 턴 수에는 세지 않는다.
- 「그만두기」 · 「작업 취소」(`POST /api/browser/cancel`): 하던 걸음이 무엇이든 그 자리에서 끝내고, 페이지가 불러오던 것을 멈추고, 브라우저를 줄 서 있는 다음 작업에 넘긴다.
- 기다리기(`wait_for_page`): 찾는 글자는 페이지 글자와 입력 칸의 값 · 자리 표시 글자까지 본다. 바로 없으면 판정(벽 판정과 같은 판정, 0.7)으로 페이지가 스스로 하는 일이 있는지 한 번 묻고, 확실히 없으면 기다리지 않고 「직접 하라」고 모델에게 돌려준다. 문구 패턴으로 가리지 않는다(MUST NOT). 처음 30초는 2초마다, 그 뒤에는 15초마다 본다.
- 읽기: 번호는 화면에 있는 요소에만, 120개까지(넘으면 입력 칸 · 단추를 링크보다 먼저), 글은 화면과 그 아래 한 화면에서 3000자까지, 페이지 안에서 1.5초 넘게 훑지 않는다. 지난번에 붙인 번호는 지운다. 화면 안의 iframe(다른 출처 포함, 120×60 이상)도 읽고, 번호는 이어서 붙이며, 그 번호의 동작은 그 프레임에서 한다.
- 실시간 화면: 1초에 3장까지(`PRO_BROWSER_LIVE_FPS`), 1024×640 · JPEG 품질 50. 보내지 못한 데이터가 256KB 넘게 쌓인 연결에는 새 프레임을 보내지 않는다(메시지와 카드 변화는 보낸다). 긴 폴링 버퍼에는 작업마다 마지막 프레임만 남긴다.
- 되풀이: 같은 화면으로 돌아와 같은 동작을 최근 12번 안에 세 번 하면(그 사이 화면은 바뀜) `need: stuck`으로 사람에게 넘긴다. 바뀌지 않는 화면에서의 시도는 위 「같은 화면에서 헛돌지 않는다」가 센다.
- 휠: `scroll`에 요소(`i`)를 주면 그 요소 위에서(그 목록 · 프레임), 없으면 화면 가운데에서 휠을 돌리고 0.3초 뒤에 본다.
- 취소된 작업의 카드 알약은 「취소함 · <제목>」이다(완료 표시가 아니다).
- 다음 작업의 시작: 페이지가 3초 안에 답하지 않으면(스크립트가 끝나지 않는 페이지) 그 렌더러를 끝내고 새 탭에서, 그래도 안 되면 같은 프로필로 브라우저를 새로 띄워 시작한다. 작업이 끝나면 그 작업이 연 다른 탭은 닫는다.
- 프로필 잠금: 프로필을 쥔 Chromium(잠금 링크가 가리키는 것, 링크가 없으면 세션이 띄운 그 프로필의 브라우저 프로세스)이 이 서버가 띄운 것(자식 프로세스이거나 세션이 띄운 것)이면 그 Chromium 을 멈추고 잠금을 지운다. 다른 프로그램의 것과 이 서버 프로세스 자신은 건드리지 않는다(MUST NOT).

이 한도 · 감시 · 읽기 · 실시간 화면 · 프로필 잠금은 `server/lib/browserSteps.js`에 있고 작업 · 카드 · DB를 모른다. 사람의 PC 에서 도는 브라우저도 같은 모듈을 쓸 수 있다.

#### Scenario: 모델이 답하지 않는다
- **GIVEN** 휴대폰(390×844)에서 서버 브라우저 작업이 돌고 있다
- **WHEN** 모델이 20초 넘게 답하지 않는다
- **THEN** 카드 아래에 「기다리는 중 · AI 모델의 답」, 몇 초째인지, 「다시 시도」 · 「그만두기」가 화면 안에 보인다
- **AND** 「다시 시도」를 누르면 답하지 않던 요청은 끊기고 그 턴을 다시 물어 작업이 이어진다. 줄은 사라진다

#### Scenario: 멈춘 채 그만두기
- **WHEN** 멈춘 카드에서 「그만두기」를 누른다
- **THEN** 2초 안에 카드가 `cancelled`가 되고, 브라우저가 비어 다음 작업이 바로 그 브라우저에서 돈다

#### Scenario: 계속 불러오는 무거운 페이지
- **GIVEN** 끝나지 않는 그림과 0.1초마다 새 요청이 있고 카드가 1500장인 숙소 페이지(시험 사이트)
- **WHEN** 에이전트가 검색하고 결과를 정리한다
- **THEN** 25초 안에 끝나고, 이동은 1.5초 정리 뒤 진행하며, 한도를 넘긴 걸음이 없다

#### Scenario: 일이 없는 페이지에서 기다리기
- **WHEN** 에이전트가 스스로 하는 일이 없는 페이지에서 3분 기다리기를 고른다
- **THEN** 판정이 「하는 일 없음」(0.7 이상)이면 기다리지 않고 「직접 하라」고 돌려준다. 판정을 받지 못하면 평소처럼 기다린다

#### Scenario: 칸에 쓴 값을 기다린다
- **WHEN** 에이전트가 칸에 쓴 값이나 칸의 자리 표시 글자를 기다린다
- **THEN** 바로 끝난다(전에는 1분을 다 채웠다)

#### Scenario: 결과가 iframe 안에 있는 지도
- **WHEN** 검색 결과가 다른 출처의 iframe 안에 있다
- **THEN** 에이전트는 그 결과를 읽고, 그 안의 단추를 누른다

#### Scenario: 렌더러가 답하지 않는 페이지 뒤의 작업
- **GIVEN** 앞 작업의 페이지가 끝나지 않는 스크립트로 답하지 않는 채 취소됐다
- **WHEN** 다음 작업을 시킨다
- **THEN** 그 작업은 새 탭(또는 새 브라우저)에서 시작해 끝난다

### Requirement: 끝난 작업 카드는 끝난 것으로 보인다
시스템은 작업이 끝나면 해당 시점의 화면을 작업 카드(`shot`)에 남겨야 한다(SHALL). 현재 화면을 찍지 못하면 실시간 화면이 마지막으로 보여 준 장면을 남긴다. 끝난 카드에 화면이 없으면(이 규칙이 적용되기 전에 끝난 카드 등) 빈 화면에 제목을 띄우지 않고, 완료 표시가 있는 알약만 담은 짧은 줄로 보여 준다. 알약을 누르면 카드가 펼쳐져 계획을 보여 준다. 반짝이는 제목(불러오는 중 효과)은 작업 중이거나 앞선 작업을 기다리는 카드에만 쓴다(그 밖의 카드에는 사용하지 않는다: MUST NOT).

#### Scenario: 화면 없이 끝난 카드
- **GIVEN** 끝난(`done`) 작업 카드에 `shot`이 없다
- **WHEN** 휴대폰(390 폭)에서 채팅을 연다
- **THEN** 카드는 높이 80px 이내의 줄로 보이고, 반짝이는 제목이 없다. 알약을 누르면 계획 두 줄이 보인다

### Requirement: 사이트 로그인은 배포 뒤에도 남는다
시스템은 서버 브라우저 프로필을 영속 볼륨에 두어야 한다(SHALL). 위치는 `PRO_BROWSER_PROFILES`이고, 없으면 쓸 수 있는 `/data` 아래 `browser-profiles`, 그것도 없으면 서버 폴더를 쓴다. 띄우기 전에 다른 호스트나 끝난 프로세스가 남긴 브라우저 잠금 파일을 지운다. 이 기계에서 실행 중인 브라우저의 잠금 파일은 그대로 둔다. 다만 그 브라우저가 이 서버가 띄웠다가 답하지 않게 된 것이면 멈추고 지운다(위 「걸음마다 한도」). 디스크 캐시는 50MB로 제한한다.

#### Scenario: 파드가 바뀐다
- **GIVEN** 이전 파드가 프로필에 잠금 파일을 남겼다
- **WHEN** 새 파드에서 브라우저 작업을 시작한다
- **THEN** 브라우저가 뜨고, 앞서 한 사이트 로그인이 남아 있다

### Requirement: 받은 파일과 넣을 파일은 운영에서도 오간다
시스템은 작업 중 사이트가 내려 준 파일을 파일 카드로 올려야 한다(SHALL). 소리·영상 파일은 그 형식(`audio/mpeg` 등)을 붙여 저장해 바로 재생되게 한다. 사이트가 파일 이름을 주지 않거나(「download」) 이 앱이 모르는 확장자를 주면, 파일 앞부분의 형식 표시(파일 시그니처)로 형식을 알아내 파일 이름에 확장자를 붙인다. 이 앱이 아는 확장자는 사이트가 준 그대로 둔다. 사이트가 새 탭을 열어 파일을 내려 주면, 파일만 받고 자체 페이지가 없는 탭은 파일을 받은 뒤 닫고 원래 페이지에서 작업을 이어서 한다(Chrome과 같다). 받지 못한 파일(크기 상한 초과 등)이 있으면 대화에 알린다. 사람이 그 작업에 첨부한 파일은, 에이전트 서비스와 작업 폴더를 공유하지 않는 운영에서도 저장소 사본을 받아 사이트의 파일 칸에 넣을 수 있어야 한다(SHALL).

#### Scenario: 오디오를 받는다
- **WHEN** 사이트가 mp3를 내려 준다
- **THEN** 대화에 `audio/mpeg` 형식의 파일 카드가 올라오고, 그 주소의 파일이 재생된다

#### Scenario: 이름 없이 받는다
- **WHEN** 사이트가 이름 없이(「download」, 형식 `application/octet-stream`) M4A 파일을 제공한다
- **THEN** 파일 카드는 `download.m4a` · `audio/mp4`로 올라오고, 그 주소의 파일이 재생된다

#### Scenario: 새 탭에서 받는다
- **WHEN** 누른 링크가 새 탭을 열고, 그 탭에서 파일 받기가 시작된다
- **THEN** 파일 카드가 표시되고, 빈 탭은 닫히며, 에이전트와 실시간 화면은 원래 페이지로 돌아온다. 끝난 작업 카드에는 원래 페이지의 마지막 화면과 주소가 남는다
