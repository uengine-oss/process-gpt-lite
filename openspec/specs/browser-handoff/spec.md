# 서버 브라우저 작업의 진행 표시와 사람에게 넘기기

## Purpose
서버 브라우저 작업은 사람이 볼 수 없는 곳에서 돈다. 이 스펙은 작업이 어디를 누르는지 보여 주는 방식, 막힌 화면(로그인·거절·사람 확인)을 알아보고 사람에게 넘기는 방식, 멈추거나 실패했을 때 무엇이 필요하고 무엇을 하면 되는지 말하는 방식, 사이트 로그인을 배포 뒤에도 남기는 방식을 정한다. 근거는 2026-11-21 휴대폰 녹화의 「확인 필요」와 사용자 지시 「사용자에게 조치가능하게 올바른 오류 메시지」(결정 D-1121-10)다. 사람의 데스크톱 앱이 켜져 있으면 같은 작업이 그 PC 의 브라우저에서 돈다(「브라우저 작업은 내 PC에서」 — 아래 세 요구사항). 에이전트 루프 · 카드 · 이 스펙의 규칙은 어디서 돌든 같다. 설계는 `docs/local-agents/browser.md` 에 있다.

## Requirements

### Requirement: 멈추면 무엇이 필요한지와 할 일을 말한다
시스템은 서버 브라우저 작업이 사람을 기다리거나 실패하거나 확인이 필요한 채 끝나면, 작업 카드 내용에 `need`와 `reason`을 넣어야 한다(SHALL). 사이트 이름을 알면 `siteName`도 넣는다. `need`는 `login`·`blocked`·`captcha`·`choice`·`approve`·`stuck`·`limit`·`other` 중 하나다(`limit`: 동작 한도에서 멈춤 — 「되풀이하며 나아가는 일은 멈춤이 아니다」). `reason`에는 사람이 이해할 수 있는 말로 두 가지를 쓴다. 무엇 때문에 멈췄는지, 그리고 무엇을 하면 이어지는지다. 작업이 다시 진행되거나 끝나면 둘을 비운다.

화면은 「확인 필요 · <제목>」 대신 `need`별 짧은 말을 알약에 보여 주어야 한다(SHALL). 예: 「로그인 필요 · NotebookLM」, 「구글이 로그인을 막음」, 「같은 화면에서 멈춤」. 카드에는 `reason` 전체를 잘리지 않게 보여 주고, 그 일에 맞는 첫 번째 단추를 크게 둔다. 단추는 로그인 → 「직접 로그인」, 헛돎·기타 → 「직접 확인」, 막힘·실패 → 「멈추기」 또는 「다시 시도」, 선택·승인 → 응답할 카드로 가기다. 카드가 기다림·실패·완료로 바뀌면, 대화 맨 아래를 보던 화면은 그 이유와 단추가 입력창에 가리지 않게 따라 내려간다.

#### Scenario: 녹화의 순서 — NotebookLM 로그인
- **GIVEN** NotebookLM 규칙이 있는 방이고, 서버 브라우저가 구글에 로그인되어 있지 않다
- **WHEN** 유튜브 링크를 올린다
- **THEN** 몇 초 안에 작업 카드가 `needs_input`·`need: login`이 되고 `siteName`은 페이지에서 읽은 이름이다. 알약은 「로그인 필요 · <사이트 이름>」이다
- **AND** 카드에 「이 브라우저에서 <사이트>에 한 번 로그인해야 이어서 할 수 있어요. 카드의 「직접 로그인」을 눌러 로그인하면 이어서 진행해요. 로그인은 다음에도 남아요.」와 「직접 로그인」 단추가 입력창 위로 보인다(390×844)

#### Scenario: 실패한 작업
- **WHEN** 작업이 실패로 끝난다
- **THEN** 알약에 완료 표시가 아니라 경고 표시가 뜨고, 왜 실패했는지와 다시 시도할 수 있는지가 보인다

### Requirement: 막힌 화면은 모델이 알아보고 바로 사람에게 넘긴다
시스템은 서버 브라우저가 새 페이지에 닿을 때마다(주소가 바뀔 때) 그 페이지가 막힌 화면인지 모델에 한 번 판정을 요청해야 한다(SHALL). 판정에 넘기는 것은 할 일 한 줄, 페이지 제목, 호스트, 보이는 글 앞부분, 비밀번호·로그인 칸이 있는지, 단추 이름 목록이다(칸에 입력한 값은 넘기지 않는다). 보기는 로그인 필요 · 거절(사이트가 이 브라우저의 로그인·이용을 허용하지 않음) · 사람 확인 · 사이트 오류(사이트가 페이지 대신 자체 오류 화면을 표시함) · 문제없음이다. 확률이 기준(0.7) 이상일 때만 따른다.

- 로그인 필요: 모델에게 다음 동작을 묻지 않고 바로 사람을 기다린다(`need: login`). 다만 그 페이지에 로그인 폼이 있고 보관함에 맞는 로그인이 있으면 먼저 그 로그인으로 들어간다(아래 「보관함의 로그인으로 로그인 벽을 넘는다」). 사람이 로그인을 마치면 자동으로 이어서 진행해야 한다(SHALL). 막힌 상태가 풀렸는지는 주기적으로 묻지 않고, 화면이 바뀌었을 때나 직접 제어를 돌려줄 때 한 번 다시 판정한다. 같은 화면에 막혀 세 번 넘게 기다리게 되면 실패로 끝내고 그 이유를 말한다.
- 거절: `need: blocked`로 실패 처리하고, 이유와 다른 방법(그 사이트에서 직접 만든 결과 파일을 방에 올리기)을 알린다.
- 사람 확인: `need: captcha`로 사람을 기다린다.
- 사이트 오류: 일반 작업에서는 막힌 화면으로 보지 않고 에이전트가 평소처럼 진행한다(뒤로 가거나 다른 방법을 찾는다). Google 연결처럼 다른 방법이 없으면 거절과 같은 방식으로 끝낸다.
- 판정을 받지 못하거나 기준보다 낮으면 평소처럼 에이전트가 진행한다.

막힌 화면을 사이트 주소나 문구 패턴으로 가리지 않는다(MUST NOT). 카드의 사이트 이름은 페이지 자체에서 가져온다(사이트 이름 메타 → 문서 제목 → 호스트). 시스템은 자동화 탐지를 피하는 설정을 쓰지 않는다(MUST NOT).

#### Scenario: NotebookLM 첫 화면
- **WHEN** 작업이 로그인되지 않은 NotebookLM 주소에서 시작한다
- **THEN** 판정이 로그인 필요(실제 모델 0.95, 약 2초)로 나와, 모델 턴 없이 `need: login`이 된다. 카드 이름은 페이지 제목에서 온 것이다
- **AND** 사람이 직접 제어로 로그인하면 저절로 이어진다

#### Scenario: 평범한 페이지
- **WHEN** 작업이 로그인 없이 읽을 수 있는 페이지(예: example.com)를 연다
- **THEN** 판정이 문제없음(실제 모델 0.98)으로 나와 평소처럼 진행한다

#### Scenario: 사이트가 거절한다
- **WHEN** 로그인 도중 사이트가 이 브라우저의 로그인을 받아 주지 않는 화면이 나온다
- **THEN** 작업은 `failed`·`need: blocked`가 된다. 이유와 다른 방법이 카드에 보인다

#### Scenario: 판정을 받지 못한다
- **WHEN** 판정이 실패하거나 0.7보다 낮다
- **THEN** 에이전트가 평소처럼 진행한다

### Requirement: 보관함의 로그인으로 로그인 벽을 넘는다
로그인 벽(판정 `login_needed` 0.7 이상)의 페이지에 로그인 폼이 있고 보관함에 맞는 로그인이 있으면, 시스템은 사람을 기다리기 전에 보관함의 로그인으로 먼저 들어가야 한다(SHALL). 근거는 2026-11-24 휴대폰 사진(네이버 예약 → nid.naver.com 로그인 화면에서 「직접 로그인」만)과 사용자 질문 「로그인이 왜 vault 를 이용하여 암호관리를 호출하지 않는것인가」다.

- 로그인 폼: 에이전트가 보는 화면(번호 붙은 요소)에서 비밀번호 칸과 그 앞의 아이디 칸, 또는 아이디만 묻는 첫 단계의 로그인 칸. 두 단계(아이디 → 다음 화면의 비밀번호)까지 넣는다. 같은 화면과 채우기 · 키 입력을 주는 페이지 드라이버면 어느 것이든 같은 방식으로 넣는다.
- 맞는 로그인: 그 사람의 항목 중 확인을 기다리는 capture 를 뺀 것, 정확한 호스트 → 상위 · 하위 도메인 → 같은 회사의 다른 하위 도메인(nid.naver.com 에 booking.naver.com 의 로그인, `co.kr` 같은 2단 국가 도메인 포함). 여럿이 쓰는 호스팅 주소(github.io · vercel.app 등)의 이웃 주소에는 주지 않는다(MUST NOT). 여럿이면 보관함의 고르기 카드로 묻는다.
- 넣기: 값은 서버가 넣고 모델에게 보이지 않는다. 키를 하나씩 짧은 간격으로 친다(칸이 키 입력을 읽는 사이트 — 네이버의 아이디 · 비밀번호 칸은 keydown/keyup 을 듣고, `fill()` 은 키를 보내지 않는다). 첫 키 전에 칸을 가려 실시간 화면 · 모델의 화면 사진에 보이지 않게 한다. 값은 이벤트 · 서버 로그 · 모델 · 판정 요청에 넣지 않는다(MUST NOT). 넣는 동안 작업 카드 내용에 `signingIn { via: 'vault', site }`를 두고, 카드와 확장 화면은 「보관함의 로그인으로 들어가는 중 · <회사 도메인>」을 보여 준다.
- 보낸 뒤: Enter 로 보내고 페이지를 판정한다(벽 판정과 같은 판정, 0.7). 로그인됨 → 사람을 부르지 않고 이어서 한다. 비밀번호가 틀림 → 그 항목을 거부됨으로 두고 보관함의 고침 카드로 묻고, 고치면 다시 넣어 이어서 한다. 인증 코드 → 에이전트의 코드 카드(`need_secret`, 메일이 연결돼 있으면 메일에서 먼저). 사람 확인 · 다른 기기 승인처럼 사람만 할 수 있는 단계 → 「보관함에 저장된 로그인 정보로 <사이트>에 로그인하려 했는데, <사이트>에서 <막는 것>」과 「직접 로그인」으로 사람을 기다린다. 그 화면이 비밀번호를 다시 물으면 보관함의 것을 다시 넣어 둔다. 거절 → `need: blocked`. Enter 로 보내지지 않는 폼 → 모델이 폼의 로그인 단추를 누른다(값은 이미 들어 있음).
- 저장된 로그인이 없으면: 로그인 폼이 있는 벽에서는 보관함 요청 카드를 함께 띄우고 「카드에 로그인 정보를 저장하면 제가 입력해 로그인해요. 「직접 로그인」을 눌러 직접 해도 돼요. 직접 입력한 로그인 정보도 보관함에 저장할 수 있어요. 다음부터는 제가 입력해요.」라고 말한다. 카드에 저장하면 바로 넣어 이어서 하고, 직접 로그인하면 저절로 이어지며 입력한 로그인은 보관함에 저장할지 묻는다. 카드를 닫으면 그 작업에서는 다시 묻지 않는다. 휴대폰 작업 카드의 단추는 「직접 로그인」 · 「로그인 정보 저장」(보관함 카드로) · 「멈추기」다.
- 폼이 없는 화면(로그인 단추만 있는 첫 화면): 보관함에 로그인이 있으면 모델이 폼으로 간다. 사이트가 다른 곳에서 로그인을 받으면(NotebookLM은 Google 계정) 해당 사이트의 브라우저 스킬이 `metadata.sign_in`에 로그인하는 곳을 적고, 보관함에 그곳의 로그인이 있으면 모델이 로그인 단추를 누른 뒤 그곳의 폼에서 위와 같이 보관함이 넣는다.
- 한 작업에서 한 사이트에 두 번까지 넣는다. 사람에게 넘긴 뒤(틀린 비밀번호를 고치지 않음, 사람 확인)에는 그 작업에서 다시 넣지 않는다.

사이트가 지난번에 거부한 비밀번호는 그대로 다시 넣지 않는다(MUST NOT). 먼저 카드에서 비밀번호를 고치게 한 뒤 고친 비밀번호를 넣는다. 같은 비밀번호를 거듭 넣으면 계정이 잠길 수 있기 때문이다. Google 2단계 인증의 「이 기기에서 다시 묻지 않음」은 켠다(스킬 `google-sign-in`). 그러면 다음부터는 저장된 비밀번호만으로 로그인한다. Google 연결(`connectGoogle`)은 지금처럼 모델이 스킬을 따라 넣는다.

#### Scenario: 로그인 벽은 보관함부터
- **GIVEN** 보관함에 그 사이트(또는 상위 도메인 · 같은 회사의 다른 하위 도메인)의 로그인이 있다
- **WHEN** 작업이 그 사이트의 로그인 폼 화면(로그인 벽)에 닿는다
- **THEN** 카드가 「보관함의 로그인으로 들어가는 중 · <회사 도메인>」을 보여 주는 동안 서버가 아이디 · 비밀번호를 키로 쳐 넣고 보낸다
- **AND** 로그인되면 카드가 사람을 기다리지 않고(`needs_input` 없음) 모델이 로그인한 화면에서 이어서 한다. 값은 이벤트 · 로그 · 모델 · 판정 요청 · 실시간 화면에 없다

#### Scenario: 저장된 로그인이 없다
- **WHEN** 로그인 폼이 있는 로그인 벽인데 보관함에 맞는 로그인이 없다
- **THEN** 카드는 `need: login`, 저장하거나 직접 로그인하라는 이유와 보관함 요청 카드를 띄운다(휴대폰 390에서 「직접 로그인」 · 「로그인 정보 저장」 · 「멈추기」가 화면 안)
- **AND** 카드에 저장하면 그 로그인을 넣어 이어서 한다

#### Scenario: 넣은 뒤 추가 확인
- **WHEN** 보관함의 로그인을 보낸 뒤 사이트가 사람 확인을 요구한다
- **THEN** 카드는 「보관함에 저장된 로그인 정보로 <사이트>에 로그인하려 했는데, <사이트>에서 사람인지 확인하는 절차를 추가로 요구해요. 「직접 로그인」을 눌러 로그인을 마치면 이어서 진행해요.」로 기다리고, 확인 화면의 비밀번호 칸에는 보관함의 것을 다시 넣어 둔다
- **AND** 사람이 확인을 마치면 저절로 이어진다

#### Scenario: 저장된 비밀번호가 틀렸다
- **WHEN** 사이트가 보관함의 비밀번호를 받아들이지 않는다
- **THEN** 그 항목이 거부됨이 되고 보관함의 고침 카드와 그 이유가 뜬다
- **AND** 카드에서 고치면 고친 비밀번호를 넣어 이어서 한다

#### Scenario: 인증 코드를 묻는다
- **WHEN** 보관함의 로그인을 보낸 뒤 사이트가 일회용 코드를 묻는다
- **THEN** 에이전트가 그 칸으로 코드 카드(`need_secret`)를 띄우고, 메일이 연결돼 있으면 메일에서 먼저 찾는다

#### Scenario: 로그인을 다른 곳에서 받는 사이트
- **WHEN** 스킬의 `sign_in` 호스트 로그인이 보관함에 있고, 사이트 첫 화면이 로그인 벽이다
- **THEN** 사람을 기다리지 않고 에이전트가 로그인 단추를 누르고, 그곳의 폼에서는 보관함이 로그인을 넣어 일을 마친다

#### Scenario: 지난번에 거부된 비밀번호
- **WHEN** 보관함의 로그인이 지난번에 거부됐다
- **THEN** 카드에서 먼저 비밀번호를 고치도록 안내하고, 고치기 전에는 넣지 않으며, 고친 뒤 그 비밀번호로 로그인한다

### Requirement: 같은 화면에서 헛돌지 않는다
시스템은 같은 화면(주소와 화면 내용이 같음)에서 효과 없는 동작이 다섯 번 반복되면, 더 시도하지 않고 `need: stuck`으로 사람에게 넘겨야 한다(SHALL).

#### Scenario: 아무것도 바뀌지 않는다
- **WHEN** 에이전트가 같은 단추를 눌러도 화면이 바뀌지 않는다
- **THEN** 다섯 번째 턴에서 「같은 화면에서 멈춤」으로 사람을 기다린다

### Requirement: 누르는 자리와 하는 일이 보인다
시스템은 서버 브라우저 에이전트가 누르거나 입력하기 직전에, 대상 요소의 가운데 좌표를 실시간 이벤트 `browser.click` `{ taskId, x, y, w, h, kind }`로 보내야 한다(SHALL). 화면은 실시간 화면(작업 카드, 입력창 옆 작업 원, 확장 화면) 위 해당 자리에 잠깐 커졌다 사라지는 원을 그린다. 상태 알약은 요소 이름으로 하는 일을 말한다. 예: 「「새 노트북」 누르는 중」, 「「검색」 칸에 입력 중」, 「notebooklm.google.com 여는 중」. 입력한 값은 이벤트·알약·요약 어디에도 넣지 않는다(MUST NOT). 비밀 칸은 「비밀번호 칸」처럼 종류만 말한다.

#### Scenario: 누르는 자리
- **WHEN** 에이전트가 단추를 누른다
- **THEN** 실시간 화면의 그 단추 자리(±3px)에 원이 뜬다

#### Scenario: 새 탭
- **WHEN** 누른 단추가 새 탭이나 팝업을 연다
- **THEN** 에이전트는 그 탭에서 일하고 실시간 화면도 그 탭을 보여 준다. 탭이 닫히면 원래 페이지로 돌아온다

### Requirement: 걸음마다 한도가 있고, 멈춘 것처럼 보이지 않는다
서버 브라우저 작업의 걸음(페이지 열기 · 페이지 읽기 · 화면 사진 · 모델의 답 · 동작 하나)에는 각각 시간 한도가 있어야 한다(SHALL). 한도를 넘긴 걸음은 멈추고, 그 결과를 모델이나 사람에게 알린다. 근거는 2026-11-24 사용자 보고 「이 작업을 시켰는데, 멈췄음... 브라우저가 먹통이 된」(계룡대 인근 숙소 검색)과 같은 작업을 실제 사이트에서 다시 돌려 잰 결과다(`e2e/results/server-browser-stall-1124.txt`). 그 결과 멈춘 것처럼 보인 까닭은 세 가지였다. 모델의 답이 30~50초 걸리는 동안 알약이 「페이지 읽는 중」에 머물렀다. 일이 없는 페이지에서 기다리기(`wait_for_page`)가 1~3분씩 돌았다. 작업을 취소해도 그 걸음이 끝날 때까지(최대 33초) 멈추지 않았다.

- 한도: 페이지 열기 20초(응답 시작 → 문서까지, 그 뒤 `load`는 최대 1.5초), 읽기 6초, 사진 6초, 동작 하나 15초(그 동작이 사람의 승인을 기다리는 동안은 세지 않음), 모델 한 번 90초(넘기면 한 번 더 묻고, 또 넘기면 「AI 모델이 제때 답하지 않아 …」로 멈춤), 계획 30초(넘기면 계획 없이 시작), 브라우저 띄우기 30초.
- 끝나지 않는 페이지: `networkidle`이나 `load`를 기다리지 않는다(MUST NOT). 문서가 오면 진행하고, 한도 안에 문서가 다 오지 않으면 불러오기를 멈추고 온 만큼 읽는다. 응답이 오지 않아 실패한 이동은 멈춰 두어, 다음 이동이 바로 거부되지 않게 한다.
- 알약: 모델이 생각하는 동안에는 「다음 할 일 고르는 중」, 기다리는 동안에는 「「…」 나오기를 기다리는 중 · 0:45」처럼 무엇을 얼마나 기다리는지 말한다.
- 감시: 20초 동안 다음 걸음으로 넘어가지 않으면 작업 카드 내용에 `stall { what, since, after }`를 넣는다. 화면은 카드 아래에 「기다리는 중 · <무엇>」, 몇 초째인지, 한 줄 설명, 「다시 시도」 · 「그만두기」를 보여 준다. 입력창 옆 독은 호박색 테두리가 된다. 다음 걸음이 시작되거나 작업이 끝나면 `stall`을 비운다. 사람의 답을 기다리는 동안(`needs_input`)은 멈춤이 아니다.
- 「다시 시도」(`POST /api/browser/retry {taskId}`): 하던 걸음(모델 호출, 이동, 기다리기)을 버리고 그 턴을 새로 본 페이지에서 다시 한다. 에이전트의 턴 수에는 세지 않는다.
- 「그만두기」 · 「작업 취소」(`POST /api/browser/cancel`): 하던 걸음이 무엇이든 그 자리에서 끝내고, 페이지가 불러오던 것을 멈추고, 브라우저를 줄 서 있는 다음 작업에 넘긴다.
- 기다리기(`wait_for_page`): 찾는 글자는 페이지 글자와 입력 칸의 값 · 자리 표시 글자까지 본다. 바로 없으면 판정(벽 판정과 같은 판정, 0.7)으로 페이지가 스스로 하는 일이 있는지 한 번 묻고, 확실히 없으면 기다리지 않고 「직접 하라」고 모델에게 돌려준다. 문구 패턴으로 가리지 않는다(MUST NOT). 처음 30초는 2초마다, 그 뒤에는 15초마다 본다.
- 읽기: 번호는 화면에 있는 요소에만, 120개까지(넘으면 입력 칸 · 단추를 링크보다 먼저), 글은 화면과 그 아래 한 화면에서 3000자까지, 페이지 안에서 1.5초 넘게 훑지 않는다. 지난번에 붙인 번호는 지운다. 화면 안의 iframe(다른 출처 포함, 120×60 이상)도 읽고, 번호는 이어서 붙이며, 그 번호의 동작은 그 프레임에서 한다.
- 실시간 화면: 1초에 3장까지(`PRO_BROWSER_LIVE_FPS`), 1024×640 · JPEG 품질 50. 보내지 못한 데이터가 256KB 넘게 쌓인 연결에는 새 프레임을 보내지 않는다(메시지와 카드 변화는 보낸다). 긴 폴링 버퍼에는 작업마다 마지막 프레임만 남긴다.
- 되풀이: 같은 화면으로 돌아와 같은 동작을 최근 12번 안에 세 번 하면(그 사이 화면은 바뀜) `need: stuck`으로 사람에게 넘긴다. 바뀌지 않는 화면에서의 시도는 위 「같은 화면에서 헛돌지 않는다」가 센다.
- 휠: `scroll`에 요소(`i`)를 주면 그 요소 위에서(그 목록 · 프레임), 없으면 화면 가운데에서 휠을 돌리고 0.3초 뒤에 본다.
- 취소된 작업의 카드 알약은 「취소함 · <제목>」이다(완료 표시가 아니다).
- 다음 작업의 시작: 페이지가 3초 안에 답하지 않으면(스크립트가 끝나지 않는 페이지) 그 렌더러를 끝내고 새 탭에서, 그래도 안 되면 같은 프로필로 브라우저를 새로 띄워 시작한다. 작업이 끝나면 그 작업이 연 다른 탭은 닫는다.
- 프로필 잠금: 프로필을 쥔 Chromium(잠금 링크가 가리키는 것, 링크가 없으면 세션이 띄운 그 프로필의 브라우저 프로세스)이 이 서버가 띄운 것(자식 프로세스이거나 세션이 띄운 것)이면 그 Chromium 을 멈추고 잠금을 지운다. 다른 프로그램의 것과 이 서버 프로세스 자신은 건드리지 않는다(MUST NOT).

이 한도 · 감시 · 읽기 · 실시간 화면 · 프로필 잠금은 `server/lib/browserSteps.js`에 있고 작업 · 카드 · DB를 모른다. 사람의 PC 에서 도는 브라우저(아래 「브라우저 작업은 내 PC 의 브라우저에서도 돈다」)도 같은 한도 · 감시 · 취소 · 다시 시도를 쓰고, 페이지를 읽는 스크립트는 같은 것의 사본을 데스크톱이 갖는다.

#### Scenario: 모델이 답하지 않는다
- **GIVEN** 휴대폰(390×844)에서 서버 브라우저 작업이 돌고 있다
- **WHEN** 모델이 20초 넘게 답하지 않는다
- **THEN** 카드 아래에 「기다리는 중 · AI 모델의 답」, 몇 초째인지, 「다시 시도」 · 「그만두기」가 화면 안에 보인다
- **AND** 「다시 시도」를 누르면 답하지 않던 요청은 끊기고 그 턴을 다시 물어 작업이 이어진다. 줄은 사라진다

#### Scenario: 멈춘 채 그만두기
- **WHEN** 멈춘 카드에서 「그만두기」를 누른다
- **THEN** 2초 안에 카드가 `cancelled`가 되고, 브라우저가 비어 다음 작업이 바로 그 브라우저에서 돈다

#### Scenario: 계속 불러오는 무거운 페이지
- **GIVEN** 끝나지 않는 그림과 0.1초마다 새 요청이 있고 카드가 1500장인 숙소 페이지(시험 사이트)
- **WHEN** 에이전트가 검색하고 결과를 정리한다
- **THEN** 25초 안에 끝나고, 이동은 1.5초 정리 뒤 진행하며, 한도를 넘긴 걸음이 없다

#### Scenario: 일이 없는 페이지에서 기다리기
- **WHEN** 에이전트가 스스로 하는 일이 없는 페이지에서 3분 기다리기를 고른다
- **THEN** 판정이 「하는 일 없음」(0.7 이상)이면 기다리지 않고 「직접 하라」고 돌려준다. 판정을 받지 못하면 평소처럼 기다린다

#### Scenario: 칸에 쓴 값을 기다린다
- **WHEN** 에이전트가 칸에 쓴 값이나 칸의 자리 표시 글자를 기다린다
- **THEN** 바로 끝난다(전에는 1분을 다 채웠다)

#### Scenario: 결과가 iframe 안에 있는 지도
- **WHEN** 검색 결과가 다른 출처의 iframe 안에 있다
- **THEN** 에이전트는 그 결과를 읽고, 그 안의 단추를 누른다

#### Scenario: 렌더러가 답하지 않는 페이지 뒤의 작업
- **GIVEN** 앞 작업의 페이지가 끝나지 않는 스크립트로 답하지 않는 채 취소됐다
- **WHEN** 다음 작업을 시킨다
- **THEN** 그 작업은 새 탭(또는 새 브라우저)에서 시작해 끝난다

### Requirement: 끝난 작업 카드는 끝난 것으로 보인다
시스템은 작업이 끝나면 해당 시점의 화면을 작업 카드(`shot`)에 남겨야 한다(SHALL). 현재 화면을 찍지 못하면 실시간 화면이 마지막으로 보여 준 장면을 남긴다. 끝난 카드에 화면이 없으면(이 규칙이 적용되기 전에 끝난 카드 등) 빈 화면에 제목을 띄우지 않고, 완료 표시가 있는 알약만 담은 짧은 줄로 보여 준다. 알약을 누르면 카드가 펼쳐져 계획을 보여 준다. 반짝이는 제목(불러오는 중 효과)은 작업 중이거나 앞선 작업을 기다리는 카드에만 쓴다(그 밖의 카드에는 사용하지 않는다: MUST NOT).

#### Scenario: 화면 없이 끝난 카드
- **GIVEN** 끝난(`done`) 작업 카드에 `shot`이 없다
- **WHEN** 휴대폰(390 폭)에서 채팅을 연다
- **THEN** 카드는 높이 80px 이내의 줄로 보이고, 반짝이는 제목이 없다. 알약을 누르면 계획 두 줄이 보인다

### Requirement: 사이트 로그인은 배포 뒤에도 남는다
시스템은 서버 브라우저 프로필을 영속 볼륨에 두어야 한다(SHALL). 위치는 `PRO_BROWSER_PROFILES`이고, 없으면 쓸 수 있는 `/data` 아래 `browser-profiles`, 그것도 없으면 서버 폴더를 쓴다. 띄우기 전에 다른 호스트나 끝난 프로세스가 남긴 브라우저 잠금 파일을 지운다. 이 기계에서 실행 중인 브라우저의 잠금 파일은 그대로 둔다. 다만 그 브라우저가 이 서버가 띄웠다가 답하지 않게 된 것이면 멈추고 지운다(위 「걸음마다 한도」). 디스크 캐시는 50MB로 제한한다.

#### Scenario: 파드가 바뀐다
- **GIVEN** 이전 파드가 프로필에 잠금 파일을 남겼다
- **WHEN** 새 파드에서 브라우저 작업을 시작한다
- **THEN** 브라우저가 뜨고, 앞서 한 사이트 로그인이 남아 있다

### Requirement: 받은 파일과 넣을 파일은 운영에서도 오간다
시스템은 작업 중 사이트가 내려 준 파일을 파일 카드로 올려야 한다(SHALL). 소리·영상 파일은 그 형식(`audio/mpeg` 등)을 붙여 저장해 바로 재생되게 한다. 사이트가 파일 이름을 주지 않거나(「download」) 이 앱이 모르는 확장자를 주면, 파일 앞부분의 형식 표시(파일 시그니처)로 형식을 알아내 파일 이름에 확장자를 붙인다. 이 앱이 아는 확장자는 사이트가 준 그대로 둔다. 사이트가 새 탭을 열어 파일을 내려 주면, 파일만 받고 자체 페이지가 없는 탭은 파일을 받은 뒤 닫고 원래 페이지에서 작업을 이어서 한다(Chrome과 같다). 받지 못한 파일(크기 상한 초과 등)이 있으면 대화에 알린다. 사람이 그 작업에 첨부한 파일은, 에이전트 서비스와 작업 폴더를 공유하지 않는 운영에서도 저장소 사본을 받아 사이트의 파일 칸에 넣을 수 있어야 한다(SHALL).

#### Scenario: 오디오를 받는다
- **WHEN** 사이트가 mp3를 내려 준다
- **THEN** 대화에 `audio/mpeg` 형식의 파일 카드가 올라오고, 그 주소의 파일이 재생된다

#### Scenario: 이름 없이 받는다
- **WHEN** 사이트가 이름 없이(「download」, 형식 `application/octet-stream`) M4A 파일을 제공한다
- **THEN** 파일 카드는 `download.m4a` · `audio/mp4`로 올라오고, 그 주소의 파일이 재생된다

#### Scenario: 새 탭에서 받는다
- **WHEN** 누른 링크가 새 탭을 열고, 그 탭에서 파일 받기가 시작된다
- **THEN** 파일 카드가 표시되고, 빈 탭은 닫히며, 에이전트와 실시간 화면은 원래 페이지로 돌아온다. 끝난 작업 카드에는 원래 페이지의 마지막 화면과 주소가 남는다

### Requirement: 브라우저 작업은 내 PC 의 브라우저에서도 돈다
시스템은 브라우저 작업이 브라우저를 받을 때, 그 작업의 사람이 이어 둔 데스크톱 앱(0.2.3 이상, `caps.browser`) 중 켜져 있고 그 PC 의 설정이 이 작업을 받는 것이 있으면 그 PC 의 브라우저에서 돌려야 한다(SHALL — 받는 PC 는 아래 「PC 마다 동의한 작업만 그 PC 로 간다」). 아니면 지금처럼 서버 브라우저에서 돈다(휴대폰만 쓸 때, 0.2.2 이하의 데스크톱, 그 PC 가 받지 않음). 근거는 사용자 질문 「이 부분도 일렉트론 버전에서는 로컬 브라우저를 이용하는게 더 효율적이지 않을까?」와 「그래도 순수 모바일에서는 이 작업이 가능해야하니」(2026-11-24)다.

- 에이전트 루프(계획 · 모델 · 판정 · 보관함 · 스킬 · 카드 · 감시 · 걸음마다 한도 · 「다시 시도」 · 「그만두기」)는 서버에 하나다. 바뀌는 것은 페이지를 움직이는 드라이버뿐이다 — 서버의 Chromium, 또는 그 사람 데스크톱의 링크 너머 브라우저. 두 드라이버는 같은 동작(열기 · 읽기 · 요소 이름 · 누르기 · 입력 · 키 · 스크롤 · 보관함 값 · 그림 · 낱말 · 멈추기 · 파일 넣기 · 직접 제어 · 페이지의 대화 상자)을 같게 해야 한다(SHALL).
- 어디서 돌지는 작업이 브라우저를 받을 때 한 번 정한다. PC 의 브라우저가 30초 안에 열리지 않으면 그 작업은 서버 브라우저가 맡고 카드에 그렇게 남긴다. 서버 브라우저도 열리지 않으면 카드는 「브라우저를 열지 못해 작업을 시작하지 못했어요 …」로 실패로 끝나고 줄 선 다음 작업이 시작해야 한다(SHALL) — 「진행 중」으로 남거나 줄이 멈추지 않는다. 시작한 작업은 저절로 다른 곳으로 옮기지 않는다(MUST NOT — 아래 「PC 가 꺼지면 …」).
- PC 의 브라우저는 데스크톱 앱 안의 숨은 창이고, 사람마다의 세션에 로그인이 남는다(그 PC 를 떠나지 않는다). 「이 PC에서 보기」를 누르면 그 창이 PC 에 보이고, 사람은 그 창에서 직접 할 수 있다(그 PC 에서의 직접 제어). 닫으면 다시 숨는다. 웹 · 휴대폰의 카드에는 지금처럼 실시간 화면(1초에 3장까지, 1024×640)이 온다.
- 데스크톱은 서버가 보낸 코드를 돌리지 않는다(MUST NOT). 이름 붙은 동작만 자기 코드로 하고, 그 데스크톱에 로그인한 사람의 작업만 받는다. 페이지는 웹 주소(http · https)로만 가고 그 PC 의 파일은 열지 않는다. 사이트는 카메라 · 마이크 · 화면 · 위치 · 알림 · 클립보드 읽기를 받지 못한다.
- PC 에서 받은 파일은 서버 브라우저에서 받은 것과 같은 파일 카드로 올라온다.
- 카드: PC 에서 도는 작업은 화면 왼쪽 위에 「내 PC · <기기 이름>」, 확장 화면과 사람을 기다릴 때의 단추에 「이 PC에서 보기」가 있다. 서버에서만 도는 작업에는 표시가 없다. 확장 화면의 단추줄에는 「서버에서 이어서」(PC 가 꺼졌을 때) · 「직접 제어」 · 「제어 돌려주기」(직접 제어 중) 가운데 하나만 있다(MUST — 2026-11-25 검토: 「직접 제어」와 「제어 돌려주기」가 함께 보였다).

#### Scenario: 데스크톱이 켜져 있다
- **GIVEN** 윤태호의 맥에서 데스크톱 앱 0.2.3 이 켜져 있다(「테스트 맥」)
- **WHEN** 윤태호가 휴대폰(390)에서 「가상 상점(<주소>)에 로그인해서 가상 사과를 찾아 줘」를 보낸다
- **THEN** 작업이 그 맥의 브라우저에서 돌고, 휴대폰과 앱의 카드에 「내 PC · 테스트 맥」과 실시간 화면이 보인다
- **AND** 서버는 그 사람의 Chromium 을 띄우지 않는다

#### Scenario: 휴대폰만
- **WHEN** 데스크톱이 꺼져 있거나 그 PC 의 설정이 「쓰지 않음」이다
- **THEN** 작업은 서버 브라우저에서 지금처럼 돌고 카드에 위치 표시가 없다

#### Scenario: 사람이 필요한 순간
- **WHEN** PC 에서 도는 작업이 사람을 기다린다(직접 확인)
- **THEN** 휴대폰의 카드에 「직접 확인」 · 「이 PC에서 보기」 · 「멈추기」가 있고, 「이 PC에서 보기」를 누르면 PC 에 그 브라우저 창이 보인다(창 제목은 그 페이지의 출처부터, 전체 화면은 되지 않는다)
- **AND** 그 창에서 한 일 뒤 「제어 돌려주기」로 작업이 이어서 끝난다

#### Scenario: 확장 화면의 단추줄
- **GIVEN** PC 에서 도는 작업의 카드를 휴대폰에서 확장했다
- **THEN** 단추줄에 「직접 제어」만 있고 「제어 돌려주기」 · 「서버에서 이어서」는 없다
- **WHEN** 「직접 제어」를 누른다
- **THEN** 「제어 돌려주기」만 있고, 누르면 다시 「직접 제어」만 있다(`e2e/tests/feature/local-browser-card.spec.js` F-LB-01)

#### Scenario: 브라우저가 열리지 않는다
- **GIVEN** 앞 작업이 도는 동안 두 작업이 줄을 섰다
- **WHEN** 앞 작업이 끝난 뒤 서버 브라우저가 열리지 않는다
- **THEN** 줄 선 두 작업의 카드가 차례로 「브라우저를 열지 못해 …」 실패로 끝난다(10초 안에, 「진행 중」으로 남지 않는다)

#### Scenario: 같은 동작, 같은 결과
- **WHEN** 같은 시험(열기 · 다른 출처 iframe 안 누르기 · 입력 + Enter · 날짜 칸 · 보관함 값 · 키 하나씩 · 스크롤 · 파일 칸 · 파일 고르개 · 받은 파일 · 새 탭으로 받는 파일 · 끝나지 않는 페이지 · 직접 제어 · confirm · alert · 한글 40만 자 페이지 · 스스로 닫는 창)을 서버 드라이버와 PC 드라이버에 돌린다
- **THEN** 둘 다 같은 결과다(`server/test/browserDriver.test.js`)

### Requirement: PC 마다 동의한 작업만 그 PC 로 간다
시스템은 PC 마다 그 PC 의 데스크톱 앱에서 정한 「브라우저 작업은 이 PC에서」 — 「내가 시킨 작업만」(`own`, 기본) · 「단계 · 예약 작업까지 모두」(`all`) · 「쓰지 않음」(`off`) — 를 따라야 한다(SHALL). 이 설정은 그 PC 의 앱이 실행 설정과 함께 저장하고 링크로 알린다(서버에는 저장하지 않는다 — 운영 SQL 없음). 웹 · 휴대폰의 설정은 PC 마다 무엇으로 정했는지와 지금 어디서 도는지를 읽기만 하고, 바꾸는 칸을 두지 않는다(MUST NOT — 바꾸기는 그 PC 의 앱에서).

- 그 PC 에서 「이 컴퓨터에서 단계 실행」을 껐으면(`enabled: false`) 브라우저 설정이 무엇이든 그 PC 로 브라우저 작업을 보내지 않는다(MUST NOT).
- 그 사람이 자기 채팅에서 시킨 작업만 기본으로 PC 로 간다. 사람이 없는 작업(프로세스 단계 · 예약 · MCP · 다른 사람이 시킨 것 · 회사가 정한 루틴을 묻지 않고 하는 자동 실행)은 그 PC 가 명시적으로 「단계 · 예약 작업까지 모두」일 때만 간다(정하지 않았거나 모르는 값이면 서버).
- 사람이 없는 작업은 그 PC 의 내부망을 열지 않는다(MUST NOT). 내부망은 이름 · 번호로 `localhost`(·`*.localhost`), 한 단어 이름(`intranet`), `*.local` · `*.lan` · `*.internal` · `*.intranet` · `*.localdomain` · `*.home.arpa`, 끝에 점이 붙은 이름(`localhost.`), 127/8, 10/8, 172.16/12, 192.168/16, 링크 로컬 169.254/16 · fe80::/10, 100.64/10, 0/8, ::, ::1, fc00::/7, IPv6 안의 IPv4(`[::ffff:127.0.0.1]`)이고, PC 에서는 이름이 그 PC 에서 이런 주소로 풀리는 것(`localtest.me` · `127.0.0.1.nip.io`)도 내부망이다. 서버는 시작 페이지를 열지 않고 「사람이 없는 작업이라 PC 의 내부망 주소는 열지 않음」이라 남기며, 모델의 `goto` 는 까닭과 함께 거절된다. PC 는 그 작업이 쥔 동안 그 사람의 브라우저 세션의 모든 요청(페이지 · 그림 · 스크립트 · fetch · 폼 · 새 창의 첫 요청)을 먼저 보고 막는다.
- 이름이 지금은 공개 주소로, 연결할 때는 내부 주소로 풀리는 경우(DNS rebinding)는 막지 못한다(남은 위험 — 설계 9장).

#### Scenario: 쓰지 않음
- **GIVEN** 「테스트 맥」의 앱에서 「쓰지 않음」을 골랐다
- **WHEN** 윤태호가 브라우저 작업을 시킨다
- **THEN** 앱이 켜져 있어도 서버 브라우저에서 돌고(`where.why: 'off'`), 설정 화면에 「서버 브라우저에서 해요 — PC 앱에서 「브라우저 작업은 이 PC에서」를 껐어요」

#### Scenario: 단계 실행을 끈 PC
- **GIVEN** 「테스트 맥」에서 「이 컴퓨터에서 단계 실행」을 껐고 브라우저 설정은 「모두」다
- **WHEN** 윤태호가 브라우저 작업을 시킨다
- **THEN** 서버 브라우저에서 돈다

#### Scenario: 사람이 없는 작업
- **GIVEN** 「테스트 맥」이 켜져 있고 설정은 기본(「내가 시킨 작업만」)이다
- **WHEN** 프로세스 단계 · 예약 · 다른 사람이 시킨 브라우저 작업이 온다
- **THEN** 서버 브라우저에서 돈다(`where.why: 'not-own'`)
- **WHEN** 그 PC 에서 「단계 · 예약 작업까지 모두」로 바꾸고, 같은 작업의 시작 주소와 모델이 가려는 주소가 내부망(127.0.0.1 · 192.168.0.1)이다
- **THEN** 그 PC 에서 돌되 두 주소 모두 열지 않고, PC 에는 그런 주소로 가라는 말이 가지 않는다

#### Scenario: 회사 루틴의 자동 실행
- **WHEN** 회사가 「자동」으로 정한 루틴이 묻지 않고 브라우저 작업을 시작한다
- **THEN** 그 작업은 그 사람이 시킨 것이 아니다(`own: false`): 기본 설정의 PC 로는 가지 않고, 「모두」인 PC 에서도 그 PC 의 내부망은 열지 않는다

#### Scenario: 들어온 페이지의 요청
- **GIVEN** 사람이 시킨 작업으로 이 PC 의 내부망 페이지가 열려 있다
- **WHEN** 사람이 없는 작업이 그 브라우저를 쥐고, 그 페이지에서 fetch · 그림 · 새 창 · 폼 · `localtest.me` 로의 fetch 를 한다
- **THEN** 그 사이트에 닿은 요청이 하나도 없고, `localtest.me` · `127.0.0.1.nip.io` · `[::ffff:127.0.0.1]` · `localhost.` 는 열리지 않는다. 작업이 놓으면 같은 요청이 다시 간다

#### Scenario: 웹은 읽기만
- **WHEN** 휴대폰에서 설정 › 계정 › 내 컴퓨터의 에이전트를 연다
- **THEN** 「내가 시킨 브라우저 작업」 · 「단계 · 예약 브라우저 작업」이 지금 어디서 도는지와 PC 마다의 설정(「… — 바꾸기는 그 PC 의 앱에서」)이 보이고, 바꾸는 칸은 없다
- **AND** 앱에서 바꾸면 서버가 곧바로 그대로 따르고, 앱의 다른 칸(실행 전에 묻기)을 바꿔도 그 설정은 남는다

### Requirement: PC 의 브라우저는 작업이 쥔 동안만 일하고, 끝이 있다
시스템은 PC 의 브라우저가 작업이 쥔 동안(`begin` 부터 `idle` 까지)만 실시간 화면과 받은 파일을 서버로 보내야 한다(SHALL). 작업이 끝나면 실시간 화면을 멈추고 페이지를 비운다(그 창을 사람이 보고 있으면 그대로). 숨은 창은 소리를 내지 않고, 사람 동작 없이 소리 · 영상을 재생하지 않는다.

- 계획하는 동안 취소한 작업도 그동안 쥔 브라우저를 놓는다(`idle`). 링크가 끊기면 PC 는 스스로 놓는다(보내지도 막지도 않고, 페이지는 같은 작업이 돌아올 때를 위해 남긴다).
- 작업이 사람이 필요한 채로 끝나면(로그인 · 사람 확인 · 같은 화면 · 아무것도 못 함 — PC 가 꺼진 것은 아님) 그 페이지는 그 PC 에 남고(`idle keep`), 카드에 「다시 시도」 · 「이 PC에서 보기」가 있으며, 이유도 「직접 제어」 · 「직접 로그인」이 아니라 「이 PC에서 보기」로 그 PC 에 열어 둔 페이지에서 하라고 말한다. 다른 작업이 그 브라우저를 쥐면 그 카드의 「이 PC에서 보기」는 없어진다.
- 작업 사이에 「이 PC에서 보기」 창에서 사람이 받는 파일은 그 PC 의 다운로드 폴더로 간다(같은 이름은 「(2)」) — 서버로는 가지 않는다. 보이지 않을 때 받는 파일은 지운다.
- 「이 PC에서 보기」 창을 닫으면 그 창은 닫히고 일은 같은 주소의 새 숨은 탭에서 잇는다(Electron 에서 보였다가 숨은 창은 새 페이지를 그리지 않았다 — 그 페이지에 치다 만 글은 옮겨지지 않는다). 페이지가 제 창을 닫으면(`window.close`) 앱이 그 탭을 닫고, 다음 동작은 새 탭에서.
- 「떠날까요?」(beforeunload)를 거는 페이지도 다음 주소 · 작업 뒤의 빈 페이지로 간다(아무도 답할 사람이 없다).
- 페이지의 대화 상자(`alert` · `confirm` · `prompt`)는 PC 에 상자를 띄우지 않고(MUST NOT) 넘어가거나 취소되며 — 페이지가 스크립트로 만든 빈 iframe · `frames[]` · 연 창의 것도 — 그 말은 다음 읽기의 글 끝에 `[dialog] <종류>: <말>` 로 한 번 온다(서버 브라우저도 같다).
- 받는 파일은 50MB 까지다: 크기를 말하지 않는 응답도 받는 동안 세어 넘으면 멈추고 「너무 큼」(413)으로 알린다. 새 탭으로 여는 다운로드 링크의 파일도 오고, 그 빈 탭은 닫히며 일은 원래 페이지에 남는다.
- 탭이 없을 때 곁에서 도는 동작(멈추기 · 직접 제어 · 실시간 한 장)이 한꺼번에 와도 새 탭은 하나이고, 새 탭을 만드는 것도 그 동작의 시간 끝 안에 든다.
- 한 작업에 새 창은 10개, 한 번에 탭은 8개까지다. 이 PC 의 클립보드는 붙여 넣지 않는다(⌘V · Ctrl+V 거절 — 보는 사람의 글은 글로 친다). 「이 PC에서 보기」 창의 제목은 페이지의 출처로 시작하고 전체 화면이 되지 않는다. 앱이 서버에 답하는 기본 인증은 이 브라우저의 세션에 답하지 않는다.
- 모델의 그림은 비밀 칸을 칠한 뒤 새로 그려진 화면만 쓴다. 페이지가 그리지 못하면 그림 없이 간다(가리기 전 화면으로 대신하지 않는다).
- PC 와 서버 사이의 긴 메시지는 바이트로 재어 1MB 아래 조각으로 간다(한국어 페이지도). 서버는 작업이 그 PC 의 브라우저를 쥔 동안(또는 그 링크에 답을 기다리는 호출이 있을 때)만 조각을 받는다 — 한 번 작업을 한 링크라고 받지 않는다. 한 링크에 메시지 둘 · 조각 수 · 72MB, 모든 링크를 합쳐 144MB 까지만 모으고, 끝을 넘어 버린 메시지의 나머지 조각은 다시 받지 않는다 — PC 들이 서버의 메모리를 채울 수 없다(MUST NOT). 버렸다는 로그는 링크마다 1분에 한 번. 같은 PC 의 새 링크가 생기면 옛 링크가 늦게 닫혀도 새 링크의 조각은 그대로다.

#### Scenario: 작업 사이
- **WHEN** 작업이 끝난 뒤 PC 의 브라우저에서 페이지가 파일을 받거나 화면이 바뀐다
- **THEN** 서버로는 아무것도 오지 않고 페이지는 `about:blank` 다. 다음 작업이 시작하면 다시 온다

#### Scenario: 대화 상자
- **WHEN** 작업이 「지우기」를 누르자 페이지가 「정말 지울까요?」를 묻고 「끝났어요」를 알린다
- **THEN** 페이지는 「안 지움」이 되고, 다음 읽기에 `[dialog] confirm: 정말 지울까요?` · `[dialog] alert: 끝났어요` 가 한 번 온다(두 드라이버 모두)

#### Scenario: 큰 파일
- **WHEN** 페이지가 크기를 말하지 않는 큰 파일을 내려준다
- **THEN** 끝을 넘는 순간 받기를 멈추고 서버에 「너무 큼」(413)이 온다

#### Scenario: 한국어 긴 페이지
- **WHEN** 한글 40만 자(1.2MB)의 페이지를 읽는다
- **THEN** 링크가 끊기지 않고 낱말 · 읽기가 온다(PC 의 낱말은 20만 자까지)

#### Scenario: 조각을 쏟아붓는 PC
- **WHEN** 작업이 쓰지 않는 링크에서 끝나지 않는 조각 400개가 온다
- **THEN** 서버는 하나도 모으지 않는다(RSS 가 늘지 않는다). 작업이 쓰는 링크에서도 셋째 메시지 · 조각 수 · 바이트가 끝을 넘으면 버린다
- **AND** 작업이 끝난(드라이버만 남은) 링크의 조각도 받지 않고, 두 PC 가 함께 보낸 것이 모든 링크의 끝을 넘으면 나중 것을 버리며, 로그는 그 PC 마다 한 번이다

#### Scenario: 사람이 필요한 채로 끝난 작업
- **WHEN** PC 에서 돈 작업이 아무 동작도 하지 못하고 끝난다
- **THEN** 카드의 이유는 「…카드의 「이 PC에서 보기」로 그 PC 에 열어 둔 페이지를 확인해 주세요」이고, 단추는 「다시 시도」 · 「이 PC에서 보기」 — 누르면 그 PC 에 그 페이지가 보인다
- **AND** 다음 작업이 그 브라우저를 쥐면 앞 카드의 「이 PC에서 보기」는 사라진다

#### Scenario: 보였다가 숨은 창
- **WHEN** 사람이 「이 PC에서 보기」로 본 창을 닫고, 작업이 다음 페이지로 가서 누른다
- **THEN** 그 동작들이 그대로 되고(새 숨은 탭) 실시간 화면도 다시 온다. 작업 사이에 그 창에서 사람이 받은 파일은 그 PC 의 다운로드 폴더에 있다

#### Scenario: 떠날까요 · iframe 의 알림
- **WHEN** 칸에 입력하면 「떠날까요?」를 거는 페이지에서 다른 주소로 가고, 스크립트가 만든 빈 iframe 이 alert · confirm 을 띄운다
- **THEN** 다음 주소가 열리고(작업 뒤의 빈 페이지도), 상자 없이 페이지가 이어서 움직이며 그 말은 다음 읽기에 온다

### Requirement: PC 의 브라우저는 Lite 앱과 그 로그인 주소를 열지 않는다
시스템은 서버의 에이전트가 모는 PC 의 브라우저가 그 데스크톱 앱이 연결한 Lite 서버의 주소(그 출처 — 이 PC 에 있는 서버면 같은 포트의 이 PC 의 다른 이름 · 주소도)와 그 서버의 로그인(Supabase) 주소를 열거나 그리로 요청을 보내지 않게 해야 한다(MUST NOT, 데스크톱 0.2.6). 에이전트의 열기, 그리로 보내는 사이트, 페이지의 링크 · 새 창 · 프레임, 페이지의 요청(fetch · 그림 · 소켓)이 모두 그렇고, 「이 PC에서 보기」로 사람이 넘겨받은 창에서도 같다. `about:blank` 와 다른 사이트(Google 계정 화면을 포함)는 그대로 연다.

- 막히면 에이전트는 까닭을 열기의 답으로 받고, 페이지가 그리로 가려 한 것은 다음 읽기의 글 끝에 `[not opened] <출처>: …` 로 온다. 페이지는 있던 자리에 남는다.
- 넘겨받아 보이는 창에서 막히면 그 창에 「이 주소는 에이전트 브라우저에서 열지 않아요」(그 출처와 함께)를 보인다. 같은 주소는 잠시 다시 띄우지 않는다.

#### Scenario: 에이전트가 Lite 를 열려 한다
- **WHEN** PC 에서 도는 작업의 에이전트가 앱이 연결한 Lite 의 로그인 화면을(이 PC 의 다른 이름으로) 열고, 그리로 보내는 사이트 주소를 열고, 페이지의 「Lite 로 가기」 링크를 누른다
- **THEN** 셋 다 열리지 않고, 앞의 둘은 열기의 답이 `error: could not open …` 이며, 링크 뒤의 읽기는 그 사이트 그대로에 `[not opened] <Lite 의 출처>: …` 가 붙는다(DH-02)
- **AND** PC 의 브라우저 탭은 한 번도 Lite 의 주소가 아니다

#### Scenario: 넘겨받은 창에서
- **WHEN** 사람이 「이 PC에서 보기」로 보인 창에서 Lite 로 가는 링크를 누르고, 페이지가 Lite 로 fetch · 그림 · 새 창을 시도한다
- **THEN** 페이지는 그대로이고 요청은 모두 닿지 않으며(새 창은 열리지 않음), 그 창에 「이 주소는 에이전트 브라우저에서 열지 않아요」가 뜬다(DH-02). 「제어 돌려주기」 뒤 작업은 이어서 끝난다

### Requirement: PC 가 꺼지면 작업은 멈추고, 어디서 이을지는 사람이 고른다
시스템은 PC 에서 돌던 작업의 데스크톱 링크가 끊기면, 하던 걸음을 바로 끝내고 작업을 멈춰 카드에 `need: 'offline'` 과 이유를 보여야 한다(SHALL). 알약은 「PC 연결 끊김 · <사이트>」, 이유는 「「<기기>」의 PC 앱 연결이 끊겨 브라우저 작업을 멈췄어요. 「서버에서 이어서」를 누르면 …」, 단추는 「서버에서 이어서」 · 「PC가 다시 켜지면」 · 「멈추기」다. 다른 곳으로 저절로 옮기지 않는다(MUST NOT).

- 「서버에서 이어서」: 서버 브라우저가 마지막 주소를 열어 같은 작업을 잇는다. 모델에게 「PC 의 로그인은 이 브라우저에 없다」고 알린다. 카드는 「서버 브라우저에서 이어서」.
- 「PC가 다시 켜지면」: 카드가 「「<기기>」의 PC 앱이 다시 연결되면 그 PC 에서 이어서 해요 …」가 되고, 같은 PC 가 다시 이어지면 그 PC 의 브라우저가 같은 페이지에서 잇는다. 링크가 곧바로 돌아오면(잠깐 끊김) 묻지 않고 그 PC 에서 잇는다.
- 사람이 PC 에서 하던 일(로그인 · 사람 확인 · 직접 제어 · 같은 화면)을 기다리던 중이면 그 기다림이 끝나고 이 카드가 된다.
- 30분 안에 아무 일도 없으면 그렇다고 말하고 멈춘다. 사람이 없는 작업(무인)은 기다리지 않고 그 까닭과 함께 바로 멈춘다.
- PC 는 이어져 있는데 그 브라우저가 거듭 열리지 않으면 3번까지만 다시 열고, 그다음은 「「<기기>」의 브라우저가 거듭 열리지 않아 작업을 멈췄어요 …」와 「서버에서 이어서」로 멈춘다(MUST — 끝없이 다시 열지 않는다). 페이지를 한 번 제대로 읽으면 셈은 다시 시작한다.
- 페이지가 하나뿐인 창을 스스로 닫는 것은 PC 가 꺼진 것이 아니다: 다음 동작이 새 탭에서 잇는다.

#### Scenario: PC 를 껐다가 다시 켠다
- **WHEN** PC 에서 돌던 작업 중에 데스크톱 앱이 꺼진다
- **THEN** 몇 초 안에 카드가 「PC 연결 끊김」이 되고, 2.5초가 지나도 그대로다(서버 브라우저는 뜨지 않는다)
- **AND** 「PC가 다시 켜지면」을 누르고 앱을 다시 켜면 그 PC 에서 같은 페이지로 이어서 끝난다

#### Scenario: 서버에서 이어서
- **WHEN** 앱이 꺼진 채 「서버에서 이어서」를 누른다
- **THEN** 서버 브라우저가 그 주소를 열고 작업이 끝까지 간다. 카드는 「서버 브라우저에서 이어서」
- **AND** 확장 화면의 단추줄에는 「서버에서 이어서」만 있다(「직접 제어」 · 「제어 돌려주기」 없음 — F-LB-02)

#### Scenario: 거듭 열리지 않는 브라우저
- **GIVEN** PC 의 앱은 이어져 있는데 그 브라우저가 읽을 때마다 「열려 있지 않음」이라 답한다
- **WHEN** 그 PC 에서 작업이 돈다
- **THEN** 브라우저를 처음 한 번과 다시 3번만 열고 카드가 「거듭 열리지 않아 …」로 멈추며, 그 뒤로는 다시 열지 않는다

### Requirement: 보관함 값은 그 사람의 PC 로, 한 번의 입력을 위해서만 간다
시스템은 PC 에서 도는 작업이 보관함의 로그인 · 카드를 넣을 때(에이전트의 `fill_secret`, 로그인 벽에서 보관함 먼저, 인증 코드), 그 값을 그 작업이 도는 링크 — 그 작업의 사람의 기기 — 로만, 그 한 번의 입력을 위해 보내야 한다(SHALL). 데스크톱은 그 칸을 먼저 가리고(`data-pro-secret`) 값을 넣으며(키를 읽는 로그인 페이지에는 사람처럼 키 하나씩), 저장하지도 로그에 적지도 않는다. 값은 서버 로그 · 이벤트 · 모델 요청 · 대화 어디에도 없다(MUST NOT). 다른 사람의 데스크톱으로는 가지 않는다(MUST NOT).

- 가리기는 PC 를 떠나기 전에 한다: 읽기에는 「채워짐」만, 기다리기의 낱말에서는 빠지고, 실시간 화면에서는 점, 모델의 그림에서는 칠해진다(서버 브라우저와 같다).
- PC 에서 사람이 직접 친 로그인은 보관함으로 가져오지 않는다. 그 로그인은 그 PC 의 브라우저에 남는다.
- 이 결정과 위험(훔친 기기 토큰 · 탈취된 서버)은 `docs/local-agents/browser.md` 6장에 있다. 받아들이지 않는 사람은 그 PC 의 앱에서 「브라우저 작업은 이 PC에서」를 「쓰지 않음」으로 한다.

#### Scenario: 보관함 로그인
- **GIVEN** 가상 상점의 로그인이 보관함에 있고, 다른 사람의 데스크톱도 켜져 있다
- **WHEN** PC 에서 도는 작업이 로그인 화면에서 아이디 · 비밀번호를 보관함에서 넣고 로그인한다
- **THEN** 비밀번호는 그 사람의 PC 링크로 한 번(`fillSecret`)만 가고, 다른 사람의 링크 · 서버 로그 · 이벤트 · 모델 요청 · 대화에는 없다
- **AND** 모델이 받은 그림에서 비밀번호 칸은 칠해져 있고, 읽기에는 `secret: true, filled: true` 만 있다

#### Scenario: 로그인 벽에서 보관함 먼저(PC)
- **WHEN** PC 에서 도는 작업이 보관함에 로그인이 있는 사이트의 로그인 벽에 닿는다
- **THEN** PC 의 브라우저가 아이디 · 비밀번호를 키 하나씩 쳐 넣고 Enter 로 보내 들어가며, 사람에게 묻지 않는다

### Requirement: 기다리는 작업에 입력창으로 답한다
시스템은 이 방에서 사람의 응답을 기다리는 브라우저 작업이 있을 때, 사람이 입력창에 쓴 말을 다른 경로로 보내기 전에 판정 모델에 먼저 판정을 요청해야 한다(SHALL). 판정 모델은 작업 제목, 진행 중인 단계, 작업의 질문과 카드의 보기, 사람이 쓴 말을 읽는다. 판정 보기는 「그 보기를 고른 답」(보기마다 하나), 「질문에 대한 자기 말의 답」, 「그 작업에게 어떻게 하라는 말」, 「그 작업을 그만두고 다른 일을 하라는 말」, 「그 밖의 말」이다. 답으로 판정될 확률(각 보기를 고른 답과 자기 말로 쓴 답의 확률을 합한 값)이 0.7 이상이면 그 말을 카드에 입력한 답처럼 작업에 전달한다. 카드의 보기와 일치하면 해당 보기로, 그렇지 않으면 쓴 말 그대로 전달한다. 이때 새 브라우저 작업을 만들거나 라우터로 보내서는 안 되며(MUST NOT), 「'<작업>' 작업의 답으로 전했어요.」라고 응답한다. 보기 카드에는 전달한 말과 「채팅으로 답함」을 표시한다. 낱말이나 정규식으로 의미를 판별해서는 안 된다(MUST NOT). 로그인 · 카드 · 일회용 코드를 묻는 카드에는 입력창의 말로 답하지 않는다(채팅에 남고 판정 모델이 읽게 되기 때문이다). 파일을 첨부한 말도 답으로 전달하지 않는다. 근거는 2026-11-25 녹화다. NotebookLM 작업이 「기존 노트북 중 어느 것에 만들까요?」 카드를 띄운 채 기다리는 동안 사람이 입력창에 「새로 만들어」라고 쓰자, 그 말이 새 작업으로 처리되어 기다리는 작업 뒤에 대기했다.

승인 · 로그인 · 카드 · 일회용 코드 · 사람 확인을 기다리는 작업에는 입력창의 말로 답하지 않는다(MUST NOT). 이런 대기 상태는 사람이 카드를 누르거나 화면에서 직접 완료해야 해소되며, 판정 보기에도 해당하는 답이 없다. 입력창의 말을 하나의 보기로 전달하는 것은 그 보기의 확률이 0.7 이상일 때뿐이다. 보기들의 확률 합이 0.7을 넘더라도 이 조건을 충족하지 않으면 입력한 말을 그대로 전달한다. 판정 모델이 답하지 못해 다른 모델이 대신 고르면, 선택한 보기에만 확신도를 부여하고 나머지 보기에는 확률을 배분하지 않는다. 알 수 없는 보기를 고르면 아무것도 고르지 않은 것으로 본다. 입력창의 말은 판정 시점에 작업이 묻고 있던 질문(질문 번호)에 대한 답으로만 처리하며, 그사이에 새로 나온 질문에는 전달하지 않는다. 턴이 끝나 마무리 중인 작업은 더 이상 진행 중이 아니므로, 그 뒤에 입력한 말은 끝난 작업에 대한 말로 처리한다.

#### Scenario: 「새로 만들어」
- **GIVEN** NotebookLM 작업이 노트북 목록 보기 카드를 띄운 채 기다린다
- **WHEN** 사람이 입력창에 「새로 만들어」라고 보낸다
- **THEN** 판정 모델이 이를 「자기 말의 답」으로 판정하고, 보기 카드에는 「새로 만들어 · 채팅으로 답함」이 표시되며, 작업은 그 답을 받아 계속 진행한다
- **AND** 새 작업 카드는 생성되지 않고, 라우터는 호출되지 않는다

#### Scenario: 보기와 같은 말
- **WHEN** 사람이 「액센츄어 걸로 해」처럼 보기 하나를 가리키는 말을 보낸다
- **THEN** 작업은 해당 보기를 선택했을 때와 동일하게 「The user chose: <보기>」를 받는다

#### Scenario: 입력창의 말은 결제를 승인하지 못한다
- **GIVEN** 작업이 「39,000원을 결제할까요?」 승인 카드를 띄우고 기다린다
- **WHEN** 사람이 입력창에 「응 결제해」라고 보내고, 판정 과정에서 혼동하여 「승인」에 높은 확률을 부여한다
- **THEN** 그 말은 작업에 전달되지 않고, 승인 카드는 대기 상태를 유지한다
- **AND** 카드의 「승인」을 눌러야 결제가 진행된다

#### Scenario: 기다리는 동안 취소
- **WHEN** 보기 카드를 기다리는 작업을 취소한다
- **THEN** 작업 카드는 「취소함」 상태를 유지하고 「진행 중」으로 돌아가지 않는다

### Requirement: 기다리는 작업 뒤에 말없이 줄 서지 않는다
시스템은 브라우저를 점유한 작업이 사람의 응답을 기다리는 동안 사람이 요청한 새 브라우저 작업이 대기열에 들어가면, 별도의 채팅 메시지를 남기지 않고 새 작업의 카드에 세 가지 선택지를 표시해야 한다(SHALL). 세 가지 선택지는 「이 말을 앞 작업의 답으로」, 「앞 작업 멈추고 이것부터」, 「앞 작업 뒤에 줄 세우기」다. 첫 번째 버튼(크게 표시되는 버튼)은 앞 요구사항의 판정에서 확률이 가장 높은 항목에 해당하는 선택지다. 답이나 해당 작업에 대한 지시이면 「답으로」, 그 작업을 그만두고 다른 일을 하라는 말이면 「이것부터」, 그 밖의 말이면 「뒤에 줄 세우기」가 첫 번째 버튼이 된다. 카드에는 앞 작업의 질문도 함께 표시한다. 판정 결과가 「그만두라는 말」이어도 앞 작업을 자동으로 중단해서는 안 된다(MUST NOT). 대기 중인 모든 카드는 무엇을 기다리는지(앞 작업의 제목과, 그 작업이 사람의 응답을 기다리는 경우 해당 질문)를 표시하며, 언제든 「앞 작업 멈추고 이것부터」로 순서를 바꾸거나 「취소」로 작업을 취소할 수 있다. 앞 작업이 응답을 기다리기 시작하거나 기다림을 마치면 대기 중인 카드의 설명도 갱신된다. 사람이 요청하지 않은 작업(예약 · 프로세스 단계)의 카드에는 「답으로」가 없다.

- 「이 말을 앞 작업의 답으로」(`POST /api/browser/queue {taskId, action: answer}`): 해당 작업을 시작하게 한 말을 앞 작업의 답으로 전달하고, 해당 작업은 시작하지 않는다. 카드에는 「이 말은 앞 작업 '<제목>'의 답으로 보냈어요.」가 남는다.
- 「앞 작업 멈추고 이것부터」(`action: first`): 해당 작업을 대기열 맨 앞으로 옮기고 앞 작업을 중단한다. 중단된 작업의 카드에는 「'<이 작업>'부터 하려고 멈췄어요. 「다시 시도」를 누르면 멈춘 자리부터 이어서 해요.」가 남는다.
- 「앞 작업 뒤에 줄 세우기」(`action: after`): 대기열을 그대로 유지하고, 카드에는 「앞 작업 멈추고 이것부터」 · 「취소」만 남긴다.

#### Scenario: 답이 아닌 말
- **GIVEN** 앞 작업이 보기 카드를 띄운 채 기다린다
- **WHEN** 사람이 「노트 사이트 제목도 적어 줘」를 보내고, 판정 모델이 이를 「그 밖의 말」로 판정하며, 라우터가 브라우저 작업을 시작한다
- **THEN** 새 작업의 카드에 「앞 작업 '<제목>'이(가) 입력을 기다리고 있어요.」와 앞 작업의 질문, 「앞 작업 뒤에 줄 세우기」(크게) · 「이 말을 앞 작업의 답으로」 · 「앞 작업 멈추고 이것부터」 · 「취소」가 표시된다(1280 · 390, 가로로 넘치지 않음)
- **AND** 「앞 작업 멈추고 이것부터」를 누르면 앞 작업이 이유와 함께 중단되고 새 작업이 즉시 실행된다

#### Scenario: 확실하지 않은 답
- **WHEN** 답일 가능성이 높은 것으로 판정되지만 그 확률이 0.7에 미치지 않는다(0.62)
- **THEN** 말을 자동으로 전달하지 않고, 새 작업 카드의 첫 번째 버튼을 「이 말을 앞 작업의 답으로」로 표시한다. 이 버튼을 누르면 그 말이 앞 작업의 보기 카드에 답으로 전달되고, 새 작업은 브라우저를 사용하지 않는다

### Requirement: 「마치고 해」는 그 순서대로 한다
시스템은 사람의 말이 이 방에서 중단된 브라우저 작업을 먼저 마저 끝내고 그다음에 다른 일을 하라는 뜻이면, 해당 작업을 먼저 재개하고 다른 일은 그 뒤에 수행해야 한다(SHALL). 의미는 판정 모델이 판별한다. 판정 모델은 이 방의 최근 브라우저 작업 중 완료하지 못하고 중단된 작업(사람이 중단 · 동작 한도에 도달하여 중단 · 실패 · 확인 필요)과 방금 완료된 작업, 그리고 각 작업의 제목 · 종료 상태 · 처리한 수 · 첫 결과와 마무리 메시지 · 마지막 동작 세 개를 읽는다. 판정 보기는 「먼저 마저 끝내고 다른 일」, 「그 작업만 멈춘 자리부터 이어서(다시)」, 「그 작업을 이렇게 이어서」(다음 요구사항), 「그 밖의 말」이다. 판정 확률이 0.7 이상일 때만 따른다. 아무 동작도 수행하지 않은 채 시작 전에 취소된 작업은 판정 대상에 포함하지 않는다.

- 재개: 같은 카드가 다시 「작업 중」 상태가 된다. 동작 한도는 처음부터 다시 계산하고, 계획 단계 · 기록한 사실 · 수행한 일 목록을 이어받는다. 에이전트에게는 「멈춘 자리부터 이어서 하고, 한 일은 다시 하지 말라」와 함께 수행한 일 목록, 기록한 사실, 마지막 페이지 주소를 제공한다. 브라우저가 아직 해당 페이지에 있으면 다시 열지 않는다.
- 순서: 다음 일이 브라우저 작업이면 해당 카드는 「① '<앞 작업>'을(를) 마저 끝내면 이어서 시작해요.」를 표시한 채 대기하고, 앞 작업이 완료되면 시작한다. 응답은 「① '<앞 작업>' 마저 끝내고 → ② '<다음 일>' 시작할게요.」다. 다음 일이 에이전트 작업이면 「① '<앞 작업>' 마저 끝내고 → ② 그다음에 이 요청을 할게요.」라고 응답하고, 앞 작업이 완료된 뒤 같은 말을 한 번 더 처리한다.
- 「다시 시도해 줘: <제목>」(종료된 카드의 「다시 시도」)처럼 해당 작업만 다시 하라는 말이면, 그 작업을 중단된 지점부터 이어서 수행한다.

판정 결과가 「먼저 마저 끝내고 다른 일」이면, 그 메시지는 방 판정에 다시 보내지 않는다. 그 뒤의 일은 ②이며, 방의 규칙이나 작업에 대한 말로 처리되지 않는다. 진행 중인 작업에 대한 판정과 끝난 작업에 대한 판정은 짧은 제한 시간 안에 함께 요청한다. 끝난 작업에 대한 판정은 이 방에서 수행한 일이 있는 멈춘 작업이나 방금 끝난 작업이 있을 때만 요청한다.

#### Scenario: 녹화의 순서
- **GIVEN** 「NotebookLM '제목없음' 노트북 모두 삭제」 작업이 몇 개를 삭제한 뒤 중단되었다
- **WHEN** 사람이 「작업을 마치고 아까 노트북 엘엠 만들던거 진행해.」라고 보낸다
- **THEN** 응답은 「① 'NotebookLM '제목없음' 노트북 모두 삭제' 마저 끝내고 → ② '<NotebookLM 작업>' 시작할게요.」이다
- **AND** 삭제 작업이 같은 카드에서 재개되어 남은 노트북을 삭제하고 완료되며, 그동안 NotebookLM 카드는 「② 대기 중」 상태로 기다리다가 삭제 작업이 완료된 뒤 실행된다

### Requirement: 되풀이하며 나아가는 일은 멈춤이 아니다
시스템은 브라우저 작업에 동작 한도를 40번씩 부여하고, 마지막 40번 동안 작업이 진전되었으면 40번을 추가로 부여해야 한다(SHALL). 한도는 160번을 넘지 않는다. 진전 여부는 구조만으로 판단해야 한다(MUST). 판단 근거는 에이전트의 클릭이나 입력 동작(동작 종류와 요소 이름)과 해당 동작 직전의 화면 내용(번호가 붙은 요소의 텍스트와 텍스트 줄, 개수)이다. 가장 자주 수행한 클릭 · 입력 동작을 한 라운드의 기준으로 삼아, 해당 동작 직전의 화면을 라운드 간에 비교한다. 앞선 라운드에서 본 적 없는 화면이고 요소 하나 또는 텍스트 두 줄 이상이 사라졌으면 진전된 라운드로 판단한다. 기준 라운드가 세 번 이상이고, 마지막 라운드가 진전되었으며, 진전되지 않은 라운드가 많아야 하나이고, 앞서 본 화면으로 돌아온 적이 없으면 작업이 진전된 것으로 판단한다. 스크롤(scroll)은 기준으로 삼지 않는다. 텍스트 한 줄만 바뀌는 화면(시계 · 숫자)도 진전된 것으로 보지 않는다.

- 작업이 진전되는 동안 카드 화면 오른쪽 위에 「진행 중 · N개 처리」를 표시한다(N은 진전된 라운드 수). 「같은 화면에서 멈춤」은 표시하지 않는다.
- 한도에 도달하면 `need: limit`으로 확인 필요 상태가 되고, 알약에는 「N개 처리 · 동작 한도」(진전된 라운드가 없으면 「동작 한도에서 멈춤」)를 표시한다. 이유는 「동작 <n>번 동안 N개를 처리했지만 다 끝내지 못해 멈췄어요. 「다시 시도」를 누르면 멈춘 자리부터 이어서 해요.」이다.
- 같은 화면에서의 헛돎(「같은 화면에서 헛돌지 않는다」)과 같은 화면으로 돌아오는 반복(`need: stuck`)은 기존과 동일하게 중단한다.

#### Scenario: 녹화의 삭제
- **GIVEN** 「제목 없는 노트북」 16개가 있는 목록이 있다(시험 사이트)
- **WHEN** 에이전트가 「more_vert」 → 「delete 삭제」 → 「삭제」를 반복해 한 번에 하나씩 삭제한다
- **THEN** 동작 40번에서 중단되지 않고 끝까지 삭제하며(49번), 카드에는 「진행 중 · 13개 처리」 이상이 표시되고, 「같은 화면에서 멈춤」 · 「동작 한도」는 표시되지 않는다(390)

#### Scenario: 지워지지 않는 목록
- **WHEN** 같은 반복 과정에서 「삭제」를 눌러도 목록이 그대로다
- **THEN** 기존과 동일하게 「같은 화면으로 돌아와 같은 동작을 세 번 되풀이해 멈췄어요」라고 알리고 사람에게 넘긴다(동작 12번 이내)

### Requirement: 결과는 한두 줄, 자세한 것은 접어 둔다
시스템은 브라우저 작업이 완료되거나 중단되면 채팅에 남기는 결과 메시지와 작업 카드의 결과를 한두 줄로 줄여야 한다(SHALL). 첫 줄은 결과의 첫 문장이고, 둘째 줄은 결과의 마지막 문장(어디까지 수행했고 다음에 무엇을 할지)이며, 두 문장을 합쳐 140자를 넘지 않을 때만 둘째 줄을 덧붙인다. 구분 기준은 문장부호와 줄뿐이다. 수행한 일 목록(「실제로 한 일」 — 동작 하나마다 한 줄)과 결과 전문은 메시지의 「자세히 · N단계」에 접어 두고, 누르면 펼친다. 메시지 본문에는 클릭 기록을 넣어서는 안 된다(MUST NOT). 이는 에이전트가 나중에 읽는 대화에 클릭 기록이 쌓이지 않도록 하기 위함이다. 수행한 일 목록과 전문은 메시지와 카드의 구조 필드(`did` · `detail`)에 160단계까지 남긴다. 받은 파일은 기존과 동일하게 파일 카드로 표시하고, 사람이 할 일이 남아 있으면 카드에 이유와 버튼을 표시한다. 프로세스 단계의 결과 값에는 기존과 동일하게 전체 내용을 남긴다.

메시지 본문은 짧게 남기지만, 이후 턴이 읽는 대화와 텔레그램으로 보내는 마지막 답에는 결과 전문(`detail`)을 쓴다. 수행한 일의 목록(`did`)은 넣지 않는다.

#### Scenario: Medium 글이 들어가지 않은 노트북
- **WHEN** 작업이 「새 노트북은 만들었지만, Medium 글은 소스로 들어가지 않았습니다. … 원하시면 그 방식으로 이어서 해 드릴게요.」로 종료된다
- **THEN** 채팅에는 「새 노트북은 만들었지만, Medium 글은 소스로 들어가지 않았습니다.」와 「원하시면 그 방식으로 이어서 해 드릴게요.」 두 줄만 표시되고, 「실제로 한 일」은 「자세히 · 2단계」 안에 있다

#### Scenario: 마흔여덟 단계의 삭제
- **WHEN** 삭제 작업이 완료된다(390)
- **THEN** 결과는 「제목 없는 노트북을 모두 삭제했어요.」 한 줄이며, 「자세히 · 48단계」를 누르면 「'more_vert' 누르기」부터 순서대로 표시된다

### Requirement: 작업에 주는 말은 그 작업으로 간다
시스템은 이 방에서 실행 중이거나 대기 중인 브라우저 작업에 대한 지시(방법을 바로잡는 말, 막힌 부분을 해결하는 방법, 추가할 일)를 해당 작업에 전달해야 한다(SHALL). 의미는 「기다리는 작업에 입력창으로 답한다」와 같은 판정 방식으로 판별하고, 판정 확률이 0.7 이상일 때 따른다. 작업은 그 말을 다음 턴에 읽는다(「사람이 채팅으로 한 말 — 계획과 다르면 이 말이 우선」). 페이지나 모델의 응답을 기다리던 단계는 즉시 중단하고, 페이지를 새로 확인한 뒤 다시 수행한다. 사람의 응답을 기다리던 작업이면 이 말로 기다림을 종료한다. 카드에는 「받은 지시 · <말>」을 표시하고, 응답은 「'<작업>' 작업에 그대로 전했어요. 그 말대로 이어서 해요.」이다.

방금 완료된 작업(이 방의 최근 메시지 여섯 개 안)이나 중단된 작업을 이렇게 이어서 수행하라는 말이면(「마치고 해」와 같은 판정의 「그 작업을 이렇게 이어서」), 중단된 작업은 그 말과 함께 같은 카드에서 재개한다. 완료된 작업이면 원래 목표 · 첨부 파일 · 마지막 페이지에 그 말을 더한 새 작업 하나를 시작한다(목표는 「<원래 목표>\n\n이어서 할 일: <말>」). 에이전트는 앞 작업이 수행한 일 · 기록한 사실 · 마지막 페이지를 전달받고, 앞 작업이 만든 것(노트북 · 문서)을 다시 만들지 않고 사용한다. 이런 말은 방 판정으로 전달하지 않는다.

#### Scenario: 2분 기다림 중의 지시
- **GIVEN** 작업이 「소스 0개」가 사라지기를 최대 2분 동안 기다린다
- **WHEN** 사람이 「미디엄은 접근 권한 문제가 있으니, 내 계정으로 접근해서 인쇄시킨 후, pdf 등으로 만든후에 노트북엘엠에 넣어야 해.」라고 보낸다
- **THEN** 카드 아래에 「받은 지시」와 그 말이 표시되고, 대기는 즉시 중단되며, 에이전트가 다음 턴에 그 말을 읽는다
- **AND** 작업은 글을 PDF로 저장해 「파일 업로드」로 넣는다(아래 「사이트에 PDF 로 넣는다」)

#### Scenario: 끝맺으며 제안한 다음 일
- **GIVEN** 작업이 「… 원하시면 PDF 로 저장해 올리는 방식으로 이어서 해 드릴게요.」로 막 종료되었다
- **WHEN** 사람이 그 방식대로 수행하라는 말을 보낸다
- **THEN** 해당 작업의 원래 목표 · 입력 · 마지막 페이지에 그 말을 더한 새 작업 하나가 실행되고, 방의 규칙은 생성되거나 변경되지 않는다

### Requirement: 사이트에 PDF 로 넣는다
서버 브라우저 에이전트는 현재 화면의 페이지를 PDF로 저장할 수 있어야 한다(SHALL, 도구 `save_pdf`). 사이트가 로그인을 요구하면 해당 사람의 로그인 정보(보관함)로 로그인한 이 브라우저에서 인쇄한다(A4, 배경 포함, 동작 하나의 한도 이내). 저장한 PDF는 파일 카드로 사람에게 전달되며, 해당 작업의 파일이 되어 `attach_file`로 다른 사이트의 파일 입력란이나 파일 선택 창에 넣을 수 있다. 사람의 PC 브라우저는 아직 인쇄를 지원하지 않으며, 이 경우 에이전트에게 해당 사실을 알린다. 사이트 지식은 브라우저 스킬에 둔다. NotebookLM 스킬은 웹사이트 소스가 1분 넘게 「소스 0개」에 머물거나 가져오기에 실패하면, 사람에게 묻지 않고 해당 주소 열기 → `save_pdf` → 「파일 업로드」에서 `attach_file` 순서로 넣도록 지시한다. Medium 글은 처음부터 이 경로로 넣도록 지시한다.

저장한 PDF는 비공개 저장소(`lite-private`)에만 둔다. 파일 카드에는 주소를 넣지 않고, 열 때마다 잠시 사용할 수 있는 서명 주소를 생성한다. 공개 버킷(`files`)에는 두지 않는다(MUST NOT). 이 PDF는 사람이 첨부한 파일이 아니므로, 다른 사이트에 올리기 전에 아래 「이 대화의 파일을 사이트에 올린다」의 확인 절차를 거친다.

#### Scenario: 가져오기를 막는 사이트
- **GIVEN** 웹사이트 소스가 계속 「소스 0개」에 머무는 시험용 NotebookLM 화면과 같은 호스트의 글이 있다
- **WHEN** 에이전트가 글을 열어 `save_pdf`를 실행하고 「파일 업로드」에서 `attach_file`을 실행한다
- **THEN** 실제 Chromium이 인쇄한 PDF(`%PDF-`)가 업로드되어 「소스 1개: Agentic AI in practice.pdf」가 되고, PDF 파일 카드가 채팅에 표시되며, 작업 카드의 파일 목록에 남는다

### Requirement: 이 대화의 파일을 사이트에 올린다
시스템은 브라우저 작업이 사이트에 업로드할 파일로 해당 작업을 시작한 요청에 첨부된 파일뿐 아니라 그 사람이 이 대화에서 볼 수 있는 파일도 사용할 수 있게 해야 한다(SHALL). 사용 가능한 파일은 이 방에서 AI가 만든 파일(산출물), 채팅에 업로드한 파일, 방에 연결된 폴더의 파일(그 폴더의 구성원일 때만), 동료가 그 사람에게 공유한 파일이다. 다른 사람의 방이나 구성원이 아닌 폴더의 파일은 후보에 포함해서는 안 된다(MUST NOT).

- 사용할 파일은 판정 모델이 수행할 일(및 찾는 파일)을 읽고, 후보의 이름 · 형식 · 크기 · 출처를 확인해 선택한다. 이름을 코드로 대조해서는 안 된다(MUST NOT). 작업을 시작할 때 판정 모델에 한 번 판정을 요청하고, 확실한 후보 하나(0.6 이상이고 다른 후보가 0.2 미만)가 있으면 사람에게 묻지 않고 작업의 파일로 지정한다.
- 작업 중에는 도구 `pick_file`로 다시 찾는다. 확실하지 않고 적합해 보이는 후보가 여럿이면 작업 안에 「파일 고르기」 카드(최대 여섯 개)를 표시한다. 맞는 파일이 없으면 검색한 위치를 에이전트에게 알려, 사람에게 무엇이 필요한지 설명하게 한다. 「이 작업에 첨부해 주세요」라고 말해서는 안 된다(MUST NOT).
- 업로드할 때는 파일을 작업의 비공개 임시 폴더에 복사한 뒤 파일 입력란이나 파일 선택 창에 넣는다. 복사 원본은 에이전트 작업 공간의 해당 파일, 비공개로 받은 저장소 사본, 폴더의 git, 공유 원본이다. 공개 주소(`/object/public/`)를 거쳐서는 안 된다(MUST NOT).

작업이 사이트에 올릴 수 있는 파일은 해당 작업의 파일뿐이다. 즉, 사람이 요청에 첨부한 파일이나 작업이 찾았거나 저장한 파일이다. 다른 파일을 이름만으로 가져와 올리지 않는다(MUST NOT). 사람이 첨부하지 않은 파일(찾은 파일, 작업이 저장한 PDF)을 어떤 사이트에 처음 올리기 전에는 확인이 필요하다. 그 사람이 직접 한 말(작업을 요청한 말과 이후 작업에 전달한 말)에 해당 파일과 사이트가 모두 언급되었다고 판정 모델이 0.7 이상의 확률로 판단했거나, 사람이 「「<파일>」을(를) <사이트>에 올릴까요?」 카드에서 「승인」을 눌렀을 때만 올린다(SHALL). 「파일 고르기」 카드는 올릴 사이트를 함께 보여 주며, 그 카드에서 파일을 고르면 해당 사이트에 올려도 된다는 뜻이다. 사람이 없는 작업은 이런 파일을 올리지 않는다. 다시 실행하는 작업도 폴더 · 공유 · 비공개 파일과 해당 파일을 얻은 방법을 그대로 이어받으며, 사용할 때 그 사람의 권한을 다시 확인한다. 작업 공간의 파일은 실제 경로가 작업 공간 안에 있는 일반 파일일 때만 올린다(링크를 따라 작업 공간 밖으로 나가지 않는다). 확실한 하나로 판단하는 조건은 해당 파일의 확률이 0.6 이상이고 다른 후보와 「맞는 것이 없다」의 확률이 모두 0.2 미만인 경우다.

#### Scenario: AI 가 만든 PDF 로 팟캐스트
- **GIVEN** 이 방에 AI가 만든 「통신망 장애 온톨로지·광선로 단선 진단 보고서.pdf」 카드가 있다
- **WHEN** 사람이 「이 PDF로 NotebookLM 팟캐스트 만들어 줘」라고 보낸다
- **THEN** 질문 카드 없이 해당 PDF가 작업의 파일로 지정되고, 시험용 NotebookLM의 「파일 업로드」에 업로드되어 「소스 1개: <이름>」이 된다(390)

#### Scenario: 그럴듯한 PDF 가 둘
- **WHEN** 이 방에 비슷한 보고서 PDF가 둘 있고, 에이전트가 `pick_file`을 호출한다
- **THEN** 작업 안의 「파일 고르기 · <찾는 파일>」 카드에 두 파일이 표시되고, 선택한 파일이 업로드된다

#### Scenario: 아무도 말하지 않은 곳으로는 올리지 않는다
- **GIVEN** 이 방에서 AI가 만든 「내부 보고서.pdf」가 작업의 파일이 되었지만, 사람의 말에는 올릴 곳이 언급되지 않았다
- **WHEN** 에이전트가 그 파일을 어떤 사이트의 파일 입력란에 넣으려 한다
- **THEN** 「「내부 보고서.pdf」을(를) <사이트>에 올릴까요?」 카드가 뜨고, 「취소」를 누르면 올리지 않는다
- **AND** 에이전트가 작업의 파일이 아닌 다른 파일의 이름을 지정하면 올리지 않고 pick_file 을 사용하라고 알려 준다
