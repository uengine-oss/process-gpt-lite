# 서버 브라우저 작업의 진행 표시와 사람에게 넘기기

## Purpose
서버 브라우저 작업은 사람이 볼 수 없는 곳에서 돈다. 이 스펙은 작업이 어디를 누르는지 보여 주는 방식, 막힌 화면(로그인·거절·사람 확인)을 알아보고 사람에게 넘기는 방식, 멈추거나 실패했을 때 무엇이 필요하고 무엇을 하면 되는지 말하는 방식, 사이트 로그인을 배포 뒤에도 남기는 방식을 정한다. 근거는 2026-11-21 휴대폰 녹화의 「확인 필요」와 사용자 지시 「사용자에게 조치가능하게 올바른 오류 메시지」(결정 D-1121-10)다.

## Requirements

### Requirement: 멈추면 무엇이 필요한지와 할 일을 말한다
시스템은 서버 브라우저 작업이 사람을 기다리거나 실패하거나 확인이 필요한 채 끝나면, 작업 카드 내용에 `need`와 `reason`을 넣어야 한다(SHALL). 사이트 이름을 알면 `siteName`도 넣는다. `need`는 `login`·`blocked`·`captcha`·`choice`·`approve`·`stuck`·`other` 중 하나다. `reason`에는 사람이 이해할 수 있는 말로 두 가지를 쓴다. 무엇 때문에 멈췄는지, 그리고 무엇을 하면 이어지는지다. 작업이 다시 진행되거나 끝나면 둘을 비운다.

화면은 「확인 필요 · <제목>」 대신 `need`별 짧은 말을 알약에 보여 주어야 한다(SHALL). 예: 「로그인 필요 · NotebookLM」, 「구글이 로그인을 막음」, 「같은 화면에서 멈춤」. 카드에는 `reason` 전체를 잘리지 않게 보여 주고, 그 일에 맞는 첫 번째 단추를 크게 둔다. 단추는 로그인 → 「직접 로그인」, 헛돎·기타 → 「직접 확인」, 막힘·실패 → 「멈추기」 또는 「다시 시도」, 선택·승인 → 응답할 카드로 가기다. 카드가 기다림·실패·완료로 바뀌면, 대화 맨 아래를 보던 화면은 그 이유와 단추가 입력창에 가리지 않게 따라 내려간다.

#### Scenario: 녹화의 순서 — NotebookLM 로그인
- **GIVEN** NotebookLM 규칙이 있는 방이고, 서버 브라우저가 구글에 로그인되어 있지 않다
- **WHEN** 유튜브 링크를 올린다
- **THEN** 몇 초 안에 작업 카드가 `needs_input`·`need: login`이 되고 `siteName`은 페이지에서 읽은 이름이다. 알약은 「로그인 필요 · <사이트 이름>」이다
- **AND** 카드에 「이 브라우저에서 <사이트>에 한 번 로그인해야 이어서 할 수 있어요. 카드의 「직접 로그인」을 눌러 로그인하면 이어서 진행해요. 로그인은 다음에도 남아요.」와 「직접 로그인」 단추가 입력창 위로 보인다(390×844)

#### Scenario: 실패한 작업
- **WHEN** 작업이 실패로 끝난다
- **THEN** 알약에 완료 표시가 아니라 경고 표시가 뜨고, 왜 실패했는지와 다시 시도할 수 있는지가 보인다

### Requirement: 막힌 화면은 모델이 알아보고 바로 사람에게 넘긴다
시스템은 서버 브라우저가 새 페이지에 닿을 때마다(주소가 바뀔 때) 그 페이지가 막힌 화면인지 모델에 한 번 판정을 요청해야 한다(SHALL). 판정에 넘기는 것은 할 일 한 줄, 페이지 제목, 호스트, 보이는 글 앞부분, 비밀번호·로그인 칸이 있는지, 단추 이름 목록이다(칸에 입력한 값은 넘기지 않는다). 보기는 로그인 필요 · 거절(사이트가 이 브라우저의 로그인·이용을 허용하지 않음) · 사람 확인 · 사이트 오류(사이트가 페이지 대신 자체 오류 화면을 표시함) · 문제없음이다. 확률이 기준(0.7) 이상일 때만 따른다.

- 로그인 필요: 모델에게 다음 동작을 묻지 않고 바로 사람을 기다린다(`need: login`). 사람이 로그인을 마치면 자동으로 이어서 진행해야 한다(SHALL). 막힌 상태가 풀렸는지는 주기적으로 묻지 않고, 화면이 바뀌었을 때나 직접 제어를 돌려줄 때 한 번 다시 판정한다. 같은 화면에 막혀 세 번 넘게 기다리게 되면 실패로 끝내고 그 이유를 말한다.
- 거절: `need: blocked`로 실패 처리하고, 이유와 다른 방법(그 사이트에서 직접 만든 결과 파일을 방에 올리기)을 알린다.
- 사람 확인: `need: captcha`로 사람을 기다린다.
- 사이트 오류: 일반 작업에서는 막힌 화면으로 보지 않고 에이전트가 평소처럼 진행한다(뒤로 가거나 다른 방법을 찾는다). Google 연결처럼 다른 방법이 없으면 거절과 같은 방식으로 끝낸다.
- 판정을 받지 못하거나 기준보다 낮으면 평소처럼 에이전트가 진행한다.

막힌 화면을 사이트 주소나 문구 패턴으로 가리지 않는다(MUST NOT). 카드의 사이트 이름은 페이지 자체에서 가져온다(사이트 이름 메타 → 문서 제목 → 호스트). 시스템은 자동화 탐지를 피하는 설정을 쓰지 않는다(MUST NOT).

#### Scenario: NotebookLM 첫 화면
- **WHEN** 작업이 로그인되지 않은 NotebookLM 주소에서 시작한다
- **THEN** 판정이 로그인 필요(실제 모델 0.95, 약 2초)로 나와, 모델 턴 없이 `need: login`이 된다. 카드 이름은 페이지 제목에서 온 것이다
- **AND** 사람이 직접 제어로 로그인하면 저절로 이어진다

#### Scenario: 평범한 페이지
- **WHEN** 작업이 로그인 없이 읽을 수 있는 페이지(예: example.com)를 연다
- **THEN** 판정이 문제없음(실제 모델 0.98)으로 나와 평소처럼 진행한다

#### Scenario: 사이트가 거절한다
- **WHEN** 로그인 도중 사이트가 이 브라우저의 로그인을 받아 주지 않는 화면이 나온다
- **THEN** 작업은 `failed`·`need: blocked`가 된다. 이유와 다른 방법이 카드에 보인다

#### Scenario: 판정을 받지 못한다
- **WHEN** 판정이 실패하거나 0.7보다 낮다
- **THEN** 에이전트가 평소처럼 진행한다

### Requirement: 보관함의 로그인으로 로그인 벽을 넘는다
로그인이 필요한 화면에서 보관함에 해당 사이트의 로그인이 있으면 시스템은 사람을 기다리지 않고 에이전트가 `fill_secret`으로 로그인하게 해야 한다(SHALL). 사이트가 다른 곳에서 로그인을 받으면(NotebookLM은 Google 계정) 해당 사이트의 브라우저 스킬이 `metadata.sign_in`에 로그인하는 곳을 적는다. 보관함에 그곳의 로그인이 있으면 사이트의 첫 화면에서도 에이전트가 로그인 단추를 눌러 그곳에서 로그인한다. 사이트가 지난번에 거부한 비밀번호는 그대로 다시 넣지 않는다(MUST NOT). 먼저 카드에서 비밀번호를 고치게 한 뒤 고친 비밀번호를 넣는다. 같은 비밀번호를 거듭 넣으면 계정이 잠길 수 있기 때문이다. Google 2단계 인증의 「이 기기에서 다시 묻지 않음」은 켠다(스킬 `google-sign-in`). 그러면 다음부터는 저장된 비밀번호만으로 로그인한다.

#### Scenario: 로그인을 다른 곳에서 받는 사이트
- **WHEN** 스킬의 `sign_in` 호스트 로그인이 보관함에 있고, 사이트 첫 화면이 로그인 벽이다
- **THEN** 사람을 기다리지 않고 에이전트가 로그인 단추를 누른 뒤 보관함의 로그인으로 들어가 일을 마친다

#### Scenario: 지난번에 거부된 비밀번호
- **WHEN** 보관함의 로그인이 지난번에 거부됐다
- **THEN** 카드에서 먼저 비밀번호를 고치도록 안내하고, 고치기 전에는 넣지 않으며, 고친 뒤 그 비밀번호로 로그인한다

### Requirement: 같은 화면에서 헛돌지 않는다
시스템은 같은 화면(주소와 화면 내용이 같음)에서 효과 없는 동작이 다섯 번 반복되면, 더 시도하지 않고 `need: stuck`으로 사람에게 넘겨야 한다(SHALL).

#### Scenario: 아무것도 바뀌지 않는다
- **WHEN** 에이전트가 같은 단추를 눌러도 화면이 바뀌지 않는다
- **THEN** 다섯 번째 턴에서 「같은 화면에서 멈춤」으로 사람을 기다린다

### Requirement: 누르는 자리와 하는 일이 보인다
시스템은 서버 브라우저 에이전트가 누르거나 입력하기 직전에, 대상 요소의 가운데 좌표를 실시간 이벤트 `browser.click` `{ taskId, x, y, w, h, kind }`로 보내야 한다(SHALL). 화면은 실시간 화면(작업 카드, 입력창 옆 작업 원, 확장 화면) 위 해당 자리에 잠깐 커졌다 사라지는 원을 그린다. 상태 알약은 요소 이름으로 하는 일을 말한다. 예: 「「새 노트북」 누르는 중」, 「「검색」 칸에 입력 중」, 「notebooklm.google.com 여는 중」. 입력한 값은 이벤트·알약·요약 어디에도 넣지 않는다(MUST NOT). 비밀 칸은 「비밀번호 칸」처럼 종류만 말한다.

#### Scenario: 누르는 자리
- **WHEN** 에이전트가 단추를 누른다
- **THEN** 실시간 화면의 그 단추 자리(±3px)에 원이 뜬다

#### Scenario: 새 탭
- **WHEN** 누른 단추가 새 탭이나 팝업을 연다
- **THEN** 에이전트는 그 탭에서 일하고 실시간 화면도 그 탭을 보여 준다. 탭이 닫히면 원래 페이지로 돌아온다

### Requirement: 사이트 로그인은 배포 뒤에도 남는다
시스템은 서버 브라우저 프로필을 영속 볼륨에 두어야 한다(SHALL). 위치는 `PRO_BROWSER_PROFILES`이고, 없으면 쓸 수 있는 `/data` 아래 `browser-profiles`, 그것도 없으면 서버 폴더를 쓴다. 띄우기 전에 다른 호스트나 끝난 프로세스가 남긴 브라우저 잠금 파일을 지운다. 이 기계에서 실행 중인 브라우저의 잠금 파일은 그대로 둔다. 디스크 캐시는 50MB로 제한한다.

#### Scenario: 파드가 바뀐다
- **GIVEN** 이전 파드가 프로필에 잠금 파일을 남겼다
- **WHEN** 새 파드에서 브라우저 작업을 시작한다
- **THEN** 브라우저가 뜨고, 앞서 한 사이트 로그인이 남아 있다

### Requirement: 받은 파일과 넣을 파일은 운영에서도 오간다
시스템은 작업 중 사이트가 내려 준 파일을 파일 카드로 올려야 한다(SHALL). 소리·영상 파일은 그 형식(`audio/mpeg` 등)을 붙여 저장해 바로 재생되게 한다. 사이트가 파일 이름을 주지 않거나(「download」) 이 앱이 모르는 확장자를 주면, 파일 앞부분의 형식 표시(파일 시그니처)로 형식을 알아내 파일 이름에 확장자를 붙인다. 이 앱이 아는 확장자는 사이트가 준 그대로 둔다. 받지 못한 파일(크기 상한 초과 등)이 있으면 대화에 알린다. 사람이 그 작업에 첨부한 파일은, 에이전트 서비스와 작업 폴더를 공유하지 않는 운영에서도 저장소 사본을 받아 사이트의 파일 칸에 넣을 수 있어야 한다(SHALL).

#### Scenario: 오디오를 받는다
- **WHEN** 사이트가 mp3를 내려 준다
- **THEN** 대화에 `audio/mpeg` 형식의 파일 카드가 올라오고, 그 주소의 파일이 재생된다

#### Scenario: 이름 없이 받는다
- **WHEN** 사이트가 이름 없이(「download」, 형식 `application/octet-stream`) M4A 파일을 제공한다
- **THEN** 파일 카드는 `download.m4a` · `audio/mp4`로 올라오고, 그 주소의 파일이 재생된다
