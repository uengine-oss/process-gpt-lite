# 템플릿 폴더 — 템플릿에서 프로젝트를 시작하고, 결과물은 그 프로젝트에만, 템플릿의 개선은 고른 파일만 반영 요청으로

## Purpose
2026-11-27 사용자 요청: 「일반 폴더와 템플릿 폴더 종류가 있을거 같은데… 템플릿 폴더는 어떤 프로젝트를 시작할때 참고하는 예를 들어 제안서 템플릿 폴더는 제안에 필요한 정보들이 참조폴더들로 묶여있고 제안관련 스킬들이 포함된 (.claude..) 구조를 갖고있을 수 있다. 이 템플릿 폴더가 선택되어 시작되면 해당 프로젝트에 템플릿 폴더가 참조로 연결된 이 프로젝트 전용 폴더가 생기고 결과물은 전용 폴더내에만 남게 될 것임. 작업 도중 원본 폴더 자체에 뭔가의 개선이필요한 내용은 PR 처럼 요청될 수 있겠지.」 이어서 「일단 variant-based 도 구현하고... 프로젝트 폴더는 별도로 관리될 수 있도록 "폴더" 목록에 나와서는 안되고 해당 프로젝트에서만 보이게하면 될듯.」

공유 폴더의 소유자는 폴더를 「템플릿」으로 지정할 수 있다. 템플릿에서 프로젝트를 시작하면 그 프로젝트만의 작업 공간이 생긴다. 작업 공간은 시작한 순간의 템플릿 main에서 갈라진 변형이고, 프로젝트를 시작한 사람만 볼 수 있다. 프로젝트의 에이전트는 작업 공간에서 일하고, 템플릿의 참조 자리(폴더 참조)는 템플릿을 통해 읽는다. 결과물은 작업 공간에만 남으며 템플릿에 통째로 반영되지 않는다. 템플릿 자체를 고칠 일이 생기면 작업 공간에서 고친 템플릿 파일만 골라 「원본에 반영 요청」으로 보낸다. 요청은 템플릿의 지금 main 위에 새 변형으로 올라가고, 템플릿 주인이 검토해 기존 변형 반영으로 넣는다. 다음 프로젝트는 고친 main에서 시작하며 앞 프로젝트의 작업 공간은 보이지 않는다.

이 스펙은 첫 판(v0, 서버 · 웹)을 다룬다. 새 데이터베이스 변경은 없다(폴더 설정과 변형 기록의 기존 JSON 칸을 쓴다). 작업 공간에 참조 자리의 읽기 전용 사본을 놓는 일, 템플릿의 새 파일(스킬 추가 등)을 요청으로 보내는 일, 요청에 대한 주인의 「수정 요청」 · 「닫기」, 템플릿 프로젝트 안에서 시작한 프로세스의 에이전트 단계가 작업 공간에서 일하는 일은 다음 단계에서 다룬다. 프로젝트 채팅에서 고른 「내 PC」 CLI(스펙 `local-agents`)는 이 판에서 작업 공간에서 일한다.

## Requirements

### Requirement: 소유자가 폴더를 템플릿으로 지정하고, 템플릿은 표시된다
관리형 공유 폴더의 소유자는 폴더 화면의 「템플릿으로 지정」으로 폴더를 템플릿으로 지정하고 「지정 풀기」로 되돌릴 수 있어야 한다(SHALL). 연결형 · 스킬 · 작업 폴더는 지정할 수 없다. 템플릿 폴더는 폴더 화면 제목 옆과 「폴더」 목록에 「템플릿」 표시가 붙고, 폴더 화면에 「템플릿」 띠를 보여 준다. 띠에는 폴더 맨 위의 `TEMPLATE.md` 머리말 `description`(없으면 본문 첫 줄, 그것도 없으면 「프로젝트를 시작할 때 쓰는 폴더예요」)과, 「프로젝트마다 전용 작업 공간이 생기고, 결과물은 그 프로젝트의 「<결과물 폴더>/」에만 남아요 · 이 폴더는 그대로예요」를 적는다. 결과물 폴더는 `TEMPLATE.md` 머리말 `outputs`이며 없으면 「산출물」이다. `..` · `.git`이 든 값은 무시한다. 지정을 풀어도 이미 시작한 프로젝트의 작업 공간은 그대로다.

#### Scenario: F-TF-01 템플릿으로 지정한다
- **WHEN** 정하윤이 자기 폴더 「제안서 템플릿」 화면에서 「템플릿으로 지정」을 누른다
- **THEN** 제목 옆에 「템플릿」 표시와 「템플릿 · 제안서를 쓸 때 시작하는 템플릿이에요」 띠, 「「산출물/」에만 남아요」 문구, 「템플릿으로 시작」 단추가 보인다
- **AND** 「폴더」 목록의 「제안서 템플릿」 줄에 「템플릿」 표시가 붙고, 다른 폴더에는 붙지 않는다

### Requirement: 템플릿으로 시작하면 그 프로젝트만의 작업 공간이 생긴다
템플릿의 실행 이상 구성원은 템플릿 화면의 「템플릿으로 시작」을 누르고 띠에 나온 칸에 프로젝트 이름을 적어 「시작」을 누르거나, 「새 프로젝트」 화면의 「폴더 고르기」에서 「템플릿」 표시가 붙은 폴더를 골라(칩 「· 템플릿으로 시작」) 프로젝트를 시작할 수 있어야 한다(SHALL). 프로젝트가 만들어지는 순간 템플릿 main의 지금 판에서 갈라진 작업 공간(변형, 가지 `var/t/…`)이 생기고, 작업 공간에는 어느 템플릿의 어느 판에서 시작했는지와 결과물 폴더가 기록된다. 작업 공간은 프로젝트를 시작한 사람의 것이며, 템플릿의 「변형」 목록, 폴더 카드의 변형 수 · 최근 활동, 회의 자료 후보, 「폴더」 목록 어디에도 나오지 않는다. 그 사람이 아닌 사람(템플릿 주인 포함)이 작업 공간의 화면 · 파일 · 차이 · 작업실을 열거나 일괄 반영에 넣으려 하면 없는 변형과 같이 404를 받는다. 프로젝트 화면 위에는 작업 공간 막대가 보인다: 「템플릿」 표시와 템플릿 이름, 「전용 작업 공간 · 바뀐 것 없음」(바뀌면 「전용 작업 공간 · 바뀐 것 N건」), 「원본에 반영 요청」 단추. 막대의 작업 공간을 누르면 작업 공간 화면이 열린다.

#### Scenario: F-TF-02 템플릿 화면에서 시작한다
- **WHEN** 김서연이 「제안서 템플릿」에서 「템플릿으로 시작」을 누르고 띠에 나온 칸에 「가나정밀 3분기 제안」을 적어 「시작」을 누른다
- **THEN** 그 프로젝트가 열리고 위에 「템플릿 · 제안서 템플릿 · 전용 작업 공간 · 바뀐 것 없음 · 원본에 반영 요청」 막대가 보인다
- **AND** 「제안서 템플릿」의 「변형」 목록에는 정하윤 · 김서연 · 박도윤 누구에게도 이 작업 공간이 없고, 「폴더」 목록에도 프로젝트 폴더가 없다
- **AND** 정하윤이 작업 공간을 주소로 열면 404다

#### Scenario: F-TF-05 「새 프로젝트」에서 템플릿을 고른다
- **WHEN** 박도윤이 「새 프로젝트」에서 「폴더 고르기」를 열어 「템플릿」 표시가 붙은 「제안서 템플릿」을 고르고 첫 말을 보낸다
- **THEN** 칩은 「제안서 템플릿 · 템플릿으로 시작」이고, 만들어진 프로젝트에는 작업 공간 막대가 보인다
- **AND** 작업 공간은 그 순간의 템플릿 main(앞 요청이 반영된 양식)에서 시작했고, 김서연의 결과물은 없으며, 김서연의 작업 공간은 404다

### Requirement: 프로젝트의 에이전트는 작업 공간에서 일하고 결과물은 거기에만 남는다
작업 공간이 있는 프로젝트에서 에이전트에게 일을 맡기면, 에이전트의 작업 폴더에 작업 공간이 꺼내지고 에이전트는 다음 안내를 받아야 한다(SHALL): 템플릿 이름과 작업 공간, 결과물은 결과물 폴더 아래 새 파일로 둘 것, 템플릿의 양식 · 스킬 · `TEMPLATE.md`를 따를 것, 여기서 바꾼 것은 이 프로젝트에만 남고 템플릿 원본은 바뀌지 않는다는 것, 템플릿 파일 자체를 고쳐야 하면 작업 공간의 그 파일을 고치고 사용자가 「원본에 반영 요청」으로 그 파일만 보낼 수 있다는 것, 그리고 템플릿의 참조 자리(자리 이름과 원본, 그 사람에게 잠긴 자리는 「볼 수 없는 참조」)와 그 자리를 폴더 도구(`folder_files` · `folder_read`, 템플릿 이름과 「자리/파일」 경로)로 읽는다는 것. 참조 자리는 그 사람의 원본 권한으로 읽힌다. 턴이 끝나면 바뀐 것은 작업 공간에 커밋되고, 대화에 「이 프로젝트 작업 공간에 담았어요 · <파일> · 템플릿 「<이름>」 원본은 그대로예요」가 남는다. 템플릿 main은 바뀌지 않는다. 작업 공간 화면은 바뀐 파일마다 「결과물」(결과물 폴더 아래이거나 새 파일) 또는 「템플릿 파일」을 표시하고, 「인계하기」 · 「이 변형 반영」 대신 「원본에 반영 요청」과 「이 프로젝트 전용 작업 공간 — 템플릿 「…」의 <판> 에서 시작했어요 …」 안내를 보여 주며, 뒤로 가기는 프로젝트로 간다. 작업 공간의 파일 목록(`tree?ref=<작업 공간>`)에는 템플릿의 참조 자리 파일도 그 사람의 권한대로 나온다.

#### Scenario: F-TF-03 참조 자리를 읽고 초안을 쓰고, 양식도 고친다
- **WHEN** 김서연이 프로젝트에서 「템플릿의 참조 자료를 읽고 가나정밀 3분기 제안서 초안을 써 줘」, 이어서 「양식의 회사 주소가 옛 주소예요. 새 주소로 고쳐 줘」라고 한다
- **THEN** 에이전트가 받은 안내에 「템플릿 '제안서 템플릿' 에서 시작했어요」, 「'산출물/' 아래에 새 파일로」, 「회사 소개 자료/ — 원본: 「회사 소개 자료」 폴더 전체」가 있고, 에이전트는 「회사 소개 자료」 · 「납품 실적」 자리를 김서연의 권한으로 읽는다
- **AND** 대화에 「이 프로젝트 작업 공간에 담았어요」가 남고 막대는 「전용 작업 공간 · 바뀐 것 N건」이 된다
- **AND** 초안(`산출물/가나정밀 3분기 제안서 초안.md`)과 고친 양식은 작업 공간에만 있고, 템플릿 main의 양식은 옛 주소 그대로이며 초안이 없다
- **AND** 박도윤이 작업 공간의 파일 목록이나 초안을 열면 404이고, 정하윤이 작업 공간을 일괄 반영하려 하면 404다

### Requirement: 프로젝트의 「내 PC」 CLI 도 작업 공간에서 일한다
템플릿에서 시작한 프로젝트의 사람이 채팅 입력창에서 「Claude Code · 내 PC」 · 「Codex · 내 PC」를 골라 보내면(스펙 `local-agents` 「채팅에서 고르는 에이전트」), 그 실행은 그 사람의 작업 공간에서 일해야 한다(SHALL). 그 템플릿의 실행 이상 구성원이면 보낼 수 있다(작업 공간은 그 사람만의 것이고 템플릿에 통째로 반영되지 않으므로 편집 권한은 필요 없다). 그 사람의 PC 로 내려가는 작업 폴더에는 작업 공간의 파일 — 템플릿의 스킬(`.claude/skills`) · `TEMPLATE.md` · `CLAUDE.md` · 양식 · 참고 자료 — 이 그대로 있고, CLI 는 서버 에이전트가 받는 것과 같은 뜻의 안내(템플릿 이름 · 결과물 폴더 · 템플릿의 안내 · 양식 · 스킬을 따를 것 · 템플릿 파일은 「원본에 반영 요청」으로)를 받는다. 턴마다 바뀐 것은 작업 공간의 가지에 들어가고(「반영하면 …」 변경 카드 없음), 만든 파일은 대화에 파일 카드로 오며, 템플릿 main 은 바뀌지 않는다. 템플릿을 고칠 수 없는 사람의 실행에서는 템플릿의 실행 설정 — 설정 파일, 그리고 스킬 · 명령 · 에이전트 머리말의 실행 키(훅 · 허용 도구 등, 스펙 `local-agents`) — 을 켜지 않고 스킬의 나머지와 CLAUDE.md 만 쓰며, 그 실행은 그 사람만 본다.

#### Scenario: F-TF-08 회사 제안서 스킬로 내 PC 의 Claude Code 가 Word · PPT 를 만든다
- **WHEN** 정하윤이 데스크톱 앱의 「내 PC 폴더 올리기」로 회사 제안서 스킬(`.claude/skills/artifact-template-msaschool-purple`)이 든 「MSA 교육 제안서 템플릿」을 올려 템플릿으로 지정하고 김서연을 「실행」으로 초대한 뒤, 김서연이 자기 데스크톱 앱에서 「템플릿으로 시작」한 프로젝트 「가나정밀 MSA 전환 교육 제안」에서 「Claude Code · 내 PC」로 Word · PPT 제안서를 부탁한다
- **THEN** 김서연의 PC 의 작업 폴더에 `.claude/skills/artifact-template-msaschool-purple/SKILL.md` 와 키트(`scripts/msaschool_docx.py`)가 있고, Claude Code 가 그 스킬을 쓴다
- **AND** `산출물/` 아래의 .docx · .pptx 가 작업 공간에 들어가 대화에 파일 카드로 오고, Lite 에서 열린다
- **AND** 템플릿 main 에는 `산출물/` 이 없다
- **AND** 템플릿에 실행 설정(`.claude/settings.json` 등, 스킬 머리말의 `hooks` · `allowed-tools`)이 있으면 김서연(실행)의 PC 에서는 켜지지 않고 채팅에 한 번 알림이 남는다

### Requirement: 작업 공간은 템플릿에 통째로 반영되지 않는다
작업 공간은 일괄 반영 · 「이 변형 반영」으로 템플릿 main에 들어가지 않아야 한다(SHALL). 그 사람이 반영을 시도하면 409 「템플릿에서 시작한 프로젝트의 작업 공간은 통째로 반영하지 않아요. 고친 템플릿 파일만 「원본에 반영 요청」으로 보내 주세요.」, 다른 사람에게는 404다. 작업 공간은 인계하지 않는다(409). 일괄 반영에 작업 공간이 포함되면 작업본 자리를 확인하거나 작업실을 닫기 전에 거절한다. 다른 사람에게는 자리 정보 없이 404를 반환하고, 그 사람에게는 작업실을 그대로 둔 채 409를 반환한다.

#### Scenario: 작업 공간을 반영하려 한다
- **WHEN** 작업 공간을 일괄 반영에 넣는다
- **THEN** 그 사람에게는 409와 위 안내, 템플릿 주인에게는 404가 돌아가고 템플릿 main은 그대로다

### Requirement: 원본에 반영 요청은 고른 템플릿 파일만 새 변형으로 보낸다
작업 공간의 사람은 프로젝트 막대나 작업 공간 화면의 「원본에 반영 요청」을 눌러 시트를 열 수 있어야 한다(SHALL). 시트의 「템플릿에서 온 파일 중 이 프로젝트에서 바뀐 것」에는 시작 판에 있던 파일 가운데 결과물 폴더 밖에서 고쳐지거나 지워진 파일만 체크 상자로 나오고(처음엔 모두 체크), 「이 프로젝트에만 남는 결과물 · 보내지 않아요」에는 나머지(결과물 폴더 아래 · 새 파일)가 자물쇠와 함께 나온다. 요청 제목과 템플릿 주인에게 한마디(선택)를 적고 「N개 보내기」를 누르면, 고른 파일만 템플릿의 지금 main 위 한 커밋으로 담긴 보통 변형이 생기고(반영 대기, 보유자 = 보낸 사람, 출처 「<이름> 님이 프로젝트 「…」에서 보낸 반영 요청」), 템플릿의 「변형」 목록에 보인다. 결과물은 따라가지 않는다. 그 사이 템플릿 main에서 같은 파일의 다른 곳이 바뀌었으면 줄 단위로 합쳐 담고, 같은 곳이 바뀌었으면 보내지 않고 409 「템플릿에서도 그 사이 같은 곳이 바뀌었어요: <파일> — 템플릿 주인과 먼저 맞춰 주세요.」를 알린다. 템플릿 파일이 아닌 경로를 보내면 400 「템플릿에서 온 파일만 보낼 수 있어요 — 결과물은 이 프로젝트에만 남아요: …」다. 이미 main과 같으면 409다. 템플릿 소유자에게는 「<이름>님이 템플릿 「<템플릿>」에 반영을 요청했어요」 알림이 가고, 누르면 그 변형이 열린다. 주인은 그 변형을 보고 기존 「이 변형 반영」으로 넣는다. 보낸 쪽에는 「템플릿 「…」 주인에게 반영 요청을 보냈어요 · <파일> · 결과물은 이 프로젝트에만 남아요」가 보이고, 작업 공간에 보낸 요청이 기록된다.

#### Scenario: F-TF-04 양식 고침만 보내고 주인이 반영한다
- **WHEN** 김서연이 「원본에 반영 요청」 시트에서 「제안서 양식.md」(체크됨)와 「보내지 않아요」 아래의 초안을 확인하고, 한마디 「회사 주소가 옛 주소라 새 주소로 바꿨어요」를 적어 「1개 보내기」를 누른다
- **THEN** 시트가 닫히고 「주인에게 반영 요청을 보냈어요」가 보인다
- **AND** 정하윤에게 「김서연님이 템플릿 「제안서 템플릿」에 반영을 요청했어요」 알림이 가고, 그 변형에는 바뀐 파일이 「제안서 양식.md」 하나다
- **AND** 정하윤이 「이 변형 반영」 · 「반영 시작」을 누르면 템플릿 main의 양식이 새 주소가 되고, 템플릿에는 `산출물/`이 없다
- **AND** 초안 경로를 보내려 하면 400이다

#### Scenario: 템플릿도 같은 줄을 고쳤다
- **WHEN** 작업 공간과 템플릿 main이 양식의 같은 줄을 서로 다르게 고친 뒤 그 파일을 보낸다
- **THEN** 409(`tpl_conflict`)로 보내지 않고, 변형은 생기지 않는다

### Requirement: 작업 공간은 어느 길로도 다른 사람에게 읽히지 않는다
작업 공간과 그 안의 판(커밋) · 파일은 화면과 API, 에이전트 도구, 파일 멘션, git 토큰 어느 길로도 그 사람 말고는 읽을 수 없어야 한다(SHALL).
- 새 변형의 기준(`POST …/variations` 의 `base`)은 main, 그 사람이 볼 수 있는 변형의 id, 또는 그 사람이 읽을 수 있는 판(main 이나 볼 수 있는 가지에 있는 커밋)만 받는다. 남의 작업 공간 id 와 작업 공간에만 있는 판은 404, 자기 작업 공간에서도 새 변형은 만들지 않으며(409, 「원본에 반영 요청」을 안내), 가지 이름이나 git 표현(`:/…`, `main~1`, `HEAD` 등)은 400 이다.
- 판(sha)으로 읽기(raw · 파일 정보 · 파일 목록 · 열기용 사본)는 그 판이 main 에 있거나, 그 사람이 볼 수 있는 변형(목록에 있는 변형, 또는 자기 작업 공간)의 가지에 있을 때만 된다. 변형으로 기록되지 않은 가지(내 PC 에이전트의 실행 가지 등)에만 있는 판, 남의 작업 공간에만 있는 판, 어느 가지에도 없는 판은 404 다.
- 파일 멘션은 그 사람이 볼 수 있는 변형 · 판 · 블롭만 이름으로 받는다. 남의 작업 공간을 가리키면 그 파일의 지금 판(main)으로 바뀌고, main 에 없으면 404 다. 남의 작업 공간(또는 그 사람이 읽을 수 없는 판)을 가리키는 멘션은 보는 사람에게 파일 이름 · 경로와 「없음」만 보이고(폴더 · 판 · 변형 정보 없음) 그 판을 열 수 없다.
- git 토큰(프로세스 단계의 cli-agent · 데스크톱의 일과 동기화)으로는 작업 공간 가지와 다른 사람의 실행 가지(내 PC 에이전트가 올리는 `pgpt-agent/local/<사람>/<일>-…`, 예전 이름 `pgpt-agent/local-<일>-…`)를 볼 수도, 받을 수도, 밀어 넣을 수도 없다. 데스크톱 일의 토큰으로는 그 일을 맡긴 사람의 것, 즉 해당 폴더에 있는 그 사람의 작업 공간과 거기에 남은 변경, 그 사람의 실행 가지를 볼 수 있다. 내 PC 에이전트의 일이 작업 공간 · 변형 · 내 폴더의 main에 들어오면 해당 실행 가지를 지우고, 작업 공간에는 「반영하면 …」 변경 카드를 붙이지 않는다.
- 밀어 넣을 때는 해당 토큰이 읽을 수 있는 것만 쓸 수 있다. 토큰이 읽을 수 없는 것을 쓰는 밀어 넣기는 받아들이지 않는다. 한 번에 바꿀 수 있는 가지는 최대 20개다.
- 가지 가져오기(`POST …/import`)는 연결형 폴더의 `pgpt-agent/` 가지만 정확한 이름으로 받는다. 관리형 폴더에서는 400 이고, 가지 이름이 아니거나(`^0`, `:/…`, `..`) 작업 공간 가지면 가져오지 않는다. 가지가 있는지는 어디서나 정확한 이름으로만 본다.
- 작업 공간의 파일과 공유된 가지에 없는 판의 파일을 편집기 · 에이전트 · 멘션 · 내 PC 에이전트 카드에 넘길 때는 비공개 저장소에 두고 서명 주소로 전달하며, 폴더의 공개 사본 주소에는 두지 않는다. 파일 카드에는 주소를 남기지 않고 열 때마다 새 서명 주소를 받으므로 오래된 카드도 열린다.
- 템플릿 프로젝트에서 시작한 프로세스의 에이전트 단계는 작업 공간을 받지 않는다(그 결과로 모두가 보는 실행 변형 · 인스턴스 라인이 생기지 않는다).
- 반영 요청 변형에는 보낸 파일과 한마디만 남고, 어느 작업 공간 · 프로젝트에서 왔는지는 출처 문구(사람 이름 · 프로젝트 이름) 말고는 남지 않는다.
- 참조 자리를 더할 때 자리 경로가 열린 변형의 파일과 겹치는지 보는 검사는 작업 공간을 들여다보지 않고 그 이름을 대지 않는다.
- 작업 공간 가지는 프로젝트 id 전체로 이름 짓고(`var/t/<프로젝트 id>`), 같은 이름의 가지나 행이 이미 있으면 넘겨받지 않고 다음 이름을 쓴다.
- 「원본에 반영 요청」은 보통 파일(모드 100644 · 100755)만 보낸다. 링크 · 하위 저장소로 바뀐 파일은 400(`tpl_not_plain`)이고, 이름에 줄바꿈이 든 파일도 한 파일로 보낸다. 세 갈래 합치기는 git 의 종료 상태로 판단한다.

- 회사 관리자라도 템플릿 작업 공간이 꺼내져 있는 대화의 작업실은 열지 못한다(대화의 주인만).
- 작업 공간에도 변형의 작업본 자리(한 곳 — 서버 작업실 · 서버 에이전트 · PC 하나)가 있고, 그 자리는 언제나 그 사람의 것이다(그 사람의 작업실, 그 사람의 프로젝트 턴, 그 사람의 「내 PC」 일). 자리 보기 · 작업실 열기 · 「돌려 달라고 하기」 · 가져오기는 그 사람 말고는 누구에게나 없는 변형과 같이 404 이고, 폴더 소유자의 「하루 기다린 뒤 가져오기」도 작업 공간에는 없다. 템플릿 폴더 화면의 「작업실」 목록에는 그 사람에게도 작업 공간이 나오지 않는다(작업 공간은 그 프로젝트에서 연다). 자리를 잃은 곳에 남은 변경은 작업 공간과 마찬가지로 그 사람에게만 보이는 변형으로 남으며, 그 사람은 작업 공간 화면의 「PC에 남아 있던 변경」에서 해당 변형을 연다.

설치형(한 회사) 서버에서 폴더의 「작업실」 터미널을 쓰는 편집자는 폴더 저장소를 셸로 다루므로 작업 공간 가지도 git 으로 읽을 수 있다. 작업 공간을 그 사람에게만 두는 범위는 앱의 화면 · API · 에이전트 도구 · 파일 멘션 · git 토큰이다.

#### Scenario: F-TF-07 HTTP 로 돌아가는 길이 없다
- **WHEN** 박도윤이 김서연의 작업 공간 id · 그 가지 이름 · `:/제안서` · 작업 공간의 판을 새 변형의 기준으로 주고, 그 판으로 초안의 raw · 열기용 사본 · 파일 목록을 달라고 한다
- **THEN** 작업 공간 id 와 판은 404, 가지 이름과 git 표현은 400, 판으로 읽기는 모두 404 이고(정하윤에게도 404), 김서연 자신은 그 판으로 초안을 읽는다. 김서연이 자기 작업 공간을 기준으로 주면 409 다
- **AND** 정하윤이 받은 반영 요청 변형에는 보낸 파일과 한마디만 있고 작업 공간 id · 프로젝트 id 가 없다
- **AND** 정하윤(템플릿 소유자)이 김서연의 작업 공간의 자리를 보거나 「돌려 달라고 하기」 · 가져오기 · 작업실 열기를 하면 404 이고, 김서연이 보는 템플릿의 「작업실」 목록에도 작업 공간은 없다
- **AND** 김서연(실행)의 템플릿 지정 바꾸기는 403, 작업 폴더를 템플릿으로 지정하면 400, 보기 권한자의 「템플릿으로 시작」은 403 이고 프로젝트가 생기지 않는다

#### Scenario: TF-U-27 내 PC 일에서 같은 사람의 다른 일도 보인다
- **WHEN** 김서연이 「내 PC」에 맡긴 일의 git 토큰으로 템플릿 폴더의 가지 목록을 받는다
- **THEN** 김서연의 작업 공간과 남은 변경, 김서연의 다른 「내 PC」 일의 실행 가지는 보이고, 박도윤의 작업 공간과 실행 가지는 보이지 않는다
- **AND** 김서연의 다른 일 위에 쌓은 밀어 넣기는 허용되고, 박도윤의 일 위에 쌓은 밀어 넣기는 거절된다

#### Scenario: TF-U-12 ~ 27 다른 길
- **WHEN** 파일 멘션 · git 토큰 · 프로세스 단계 · 참조 자리 더하기 · 같은 앞자리의 프로젝트 · 링크로 바뀐 템플릿 파일 · 줄바꿈이 든 파일 이름으로 시도한다
- **THEN** 위 요구대로 거절되거나 그 사람 것만 보인다
