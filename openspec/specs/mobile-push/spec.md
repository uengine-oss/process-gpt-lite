# 휴대폰 알림: AI의 질문과 대화방 메시지

## Purpose
2026-11-26 사용자가 안드로이드 알림 창 화면을 보내며 다음과 같이 물었다. 화면에는 카카오톡의 대화방별 묶음 알림(「이상부, 정석진 전무, 김병곤 · 김병곤: …」, 숫자 2), Gemini의 「보고서 준비 완료」, 「Claude의 질문이 있습니다 · Claude: 정리 대상 (+1 more)」가 떠 있었다. 「퀵하게 대화방에서 온 내용 혹은 ai의 후먼인더루프 등을 모바일에서 보게할 수 있나?」

Lite는 이미 Home 카드에 표시되는 알림을 웹 푸시로 휴대폰에 보내고 있었다(`server/lib/webpush.js` · `public/sw.js` · Home의 「브라우저 알림 켜기」). 하지만 AI가 사람의 답을 기다릴 때는 알림을 보내지 않았고, 대화방 메시지는 메시지마다 알림이 따로 떴으며, 알림에서 바로 실행할 수 있는 동작은 없었다.

이 스펙은 다음 다섯 가지를 정한다. AI가 사람의 응답을 기다릴 때 휴대폰에 알리는 방법, 알림 버튼으로 바로 답하는 방법, 버튼에 사용하는 일회용 서명 토큰, 대화방 메시지를 방마다 하나로 묶는 방법, 알림을 켜고 시험하는 화면과 iPhone 안내다. 알림은 Home 카드와 같은 경로로 전달된다. process-gpt의 `notifications` 테이블에 행이 생성되면 Home이 그 행을 카드로 보여 주고, 알림 피드(`server/lib/notify.js` feedOnce)가 해당 사용자의 기기로 푸시를 보낸다.

## Requirements

### Requirement: AI가 사람의 답을 기다리면 휴대폰에 알린다
시스템은 AI가 사람의 답 없이는 더 진행하지 못하고 멈출 때, 해당 사용자에게 `notifications` 행(type `ai_ask`)을 하나 생성해야 한다(SHALL). 이 행은 Home 카드로 표시되고, 알림 피드는 해당 사용자의 각 기기에 푸시를 보낸다. Lite가 닫혀 있어도 알림이 온다. 대상은 다음과 같다.

- 채팅 · 프로젝트의 에이전트가 사람에게 질문하고 멈춘 경우(deepagents의 `human_input_required`). 질문과 선택지는 응답 메시지에 `ask`로 함께 저장된다.
- 브라우저 작업이 사람의 응답이나 조치를 기다리는 모든 경우: 선택지 중 하나를 고르는 질문, 승인(결제 · 첨부하지 않은 파일 업로드), 보관함 카드(로그인 · 카드 · 인증 코드), 로그인 요구 · 로봇 확인 · 멈춘 화면처럼 사람이 직접 처리해야 하는 화면.

알림 제목은 대기 유형에 따라 「Process GPT 의 질문이 있어요」 · 「승인이 필요해요」 · 「로그인이 필요해요」 · 「직접 확인해 주셔야 해요」 중 하나이며, 본문은 짧게 요약한 질문이다. Home 카드의 라벨은 「질문」 · 「승인」 · 「로그인」 · 「확인」이다. 「답하러 가기」를 누르면 질문이 있는 곳(메인 채팅에서 질문이 나온 대화, 해당 프로젝트, 해당 루틴의 화면)이 열린다. 카드를 여는 것만으로는 답한 것으로 처리하지 않는다. 카드는 답할 때까지 남는다.

한 줄로 표시되는 진행 상황, 중간 메모, 작업 완료는 이 알림으로 보내지 않는다(MUST NOT). 사람이 지켜보지 않는 작업(프로세스 단계에서 실행된 브라우저 작업)도 알리지 않는다. 카드 하나가 응답을 기다리는 동안에는 알림 행이 하나만 생성된다.

대기가 끝나면 해당 알림 행은 확인 상태로 바뀌고, Home 카드도 사라져야 한다(SHALL). 대기가 끝나는 경우는 카드에서 답했을 때, 채팅에 답을 입력했을 때, 알림 버튼으로 답했을 때, 작업을 취소하거나 직접 제어로 전환했을 때, 서버가 다시 시작되어 브라우저 작업이 종료됐을 때다. Home은 목록을 만들 때마다 카드가 아직 응답을 기다리는지 확인하고, 더 이상 기다리지 않는 행은 확인 처리한다. 브라우저 작업의 카드는 해당 작업이 아직 진행 중이거나 사람의 응답을 기다리는 동안에만 응답 대기 상태로 본다. 서버가 다시 시작될 때도 같은 규칙에 따라 대기가 끝난 작업의 알림만 확인 처리한다. 회사나 서버를 기준으로 구분하지 않으므로, 다른 서버에서 응답을 기다리는 작업의 알림은 남는다.

#### Scenario: 채팅 에이전트가 정리 형식을 묻는다
- **GIVEN** 정하윤이 프로젝트 방에 「이번 주 회의록 정리해 줘」를 보냈다
- **WHEN** 에이전트가 「어떤 형식으로 정리할까요?」라고 묻고 선택지 「세 줄 요약」 · 「표로 정리」를 제시한 뒤 멈춘다
- **THEN** 채팅에는 질문과 두 선택지가 보이고, 응답 메시지에 질문과 선택지가 저장된다
- **AND** 정하윤에게 `ai_ask` 알림 행이 하나 생성된다. 제목은 「Process GPT 의 질문이 있어요」, 본문은 「어떤 형식으로 정리할까요?」이다
- **AND** Home에 「질문」 라벨이 붙은 카드가 생성되고, 「답하러 가기」를 누르면 해당 프로젝트가 열린다

#### Scenario: 브라우저 작업이 결제 승인을 기다린다
- **WHEN** 브라우저 작업이 장바구니의 49,000원 결제를 앞두고 승인 카드를 띄운다
- **THEN** 알림 제목은 「승인이 필요해요」, 본문은 결제 내용이다
- **AND** 카드에서 「승인」이나 「취소」를 누르면 알림 행이 확인 처리되고 Home 카드도 사라진다

#### Scenario: 채팅에 직접 답한다
- **GIVEN** 에이전트의 질문 알림이 Home과 휴대폰에 떠 있다
- **WHEN** 정하윤이 해당 대화에 「표로 정리해 줘」라고 입력한다
- **THEN** 해당 대화의 질문 알림이 즉시 확인 처리되고 Home 카드가 사라진다

### Requirement: 알림 버튼으로 바로 답한다
시스템은 응답을 기다리는 카드의 알림에 다음 규칙에 따라 버튼을 표시해야 한다(SHALL). Android에서는 웹 알림 버튼이 최대 두 개까지 보이므로 버튼은 두 개를 넘지 않는다.

휴대폰 잠금 화면에서는 휴대폰을 든 누구나 알림 버튼을 누를 수 있다. 따라서 버튼 한 번으로 처리할 수 있는 일은 가벼운 일로 제한하며, 기본적으로 답변 버튼을 표시하지 않는다.

- 채팅 에이전트의 질문에는 언제나 「열기」만 표시한다(MUST). 질문 · 선택지 · `quick` · `refusal`은 모두 모델이 작성한 최종 텍스트(deepagents의 `done.content`)에 포함되며, 에이전트가 읽은 페이지나 파일이 이 내용을 조작할 수 있기 때문이다. 서버는 채팅 질문에 대한 토큰을 만들지 않고, 그런 토큰이 와도 답변을 처리하지 않는다(403). 알림에서 채팅 질문에 답하는 기능은 이 표시가 모델이 작성할 수 없는 경로로 전달될 때 다시 활성화한다.
- 브라우저 작업의 카드 중 작업 코드가 가벼운 선택으로 표시한(`quick: true`) 질문은 선택지가 하나 또는 둘이고 모두 24자 이하이면 선택지를 버튼으로 표시한다. 누르면 앱을 열지 않고 바로 답한다.
- 그런 표시가 없어도 카드에 거절 선택지(`refusal`)가 지정되어 있으면 「열기」와 해당 거절 버튼만 표시한다. 거절은 어디서 해도 안전하다. 거절 선택지는 선택지 중 하나여야 하고, 한 번만 나와야 하며, 첫 선택지(「승인」 · 「보내기」처럼 진행하는 쪽)가 아니어야 한다. 승인(결제 · 파일 업로드)은 언제나 이 경우에 해당하며, 승인 자체는 화면을 확인한 뒤 카드에서만 해야 한다(MUST).
- 사이트에 올릴 파일을 카드에서 고르는 질문은 승인과 동일하게 다룬다. 파일을 고르면 그 파일이 업로드되기 때문이다. 선택지가 파일 이름뿐이라 거절할 선택지가 없으므로 「열기」만 표시한다.
- 그 밖의 경우(표시도 거절 선택지도 없는 질문, 선택지가 셋 이상이거나 긴 경우, 로그인 · 보관함 · 직접 처리해야 하는 화면)에는 「열기」만 표시한다. 선택지의 문구만으로 가벼운 선택인지 추측하지 않는다.

브라우저 작업에서도 알림에서 보낸 답변을 같은 규칙으로 다시 검증한다. 표시되지 않은 선택지, 승인, 파일 고르기, 보관함 카드에 대해서는 알림에서 보낸 답변을 받지 않는다.

브라우저 작업의 선택지 버튼을 누르면 해당 카드에 그 선택지로 답한 것으로 처리되고 작업이 이어져야 한다(SHALL). 답변이 수락되면 알림 자리에 「「회의록」으로 답했어요」가 잠깐(4초) 보였다가 사라진다. 이미 답했거나, 더 이상 응답을 기다리지 않거나, 너무 오래된 알림이거나, 채팅 질문이면 답변을 전송하지 않고 질문이 있던 곳을 연다. 알림 본문이나 「열기」를 누르면 질문이 있는 곳이 열리고, 휴대폰에서는 Home 탭을 닫고 해당 채팅을 보여 준다.

알림 안에서 글을 입력해 답하는 기능(인라인 답장)은 구현하지 않는다. 웹 알림에는 브라우저가 안정적으로 지원하는 인라인 입력란이 없기 때문이다. 대화방 알림의 「답장」을 누르면 해당 방이 열리고 입력창에 커서가 놓인다.

#### Scenario: 채팅 에이전트의 질문은 「열기」만
- **GIVEN** 에이전트가 「어떤 형식으로 정리할까요?」를 물으며 JSON에 `quick: true`를 적었다
- **WHEN** 휴대폰에 알림이 온다
- **THEN** 알림에는 「Process GPT 의 질문이 있어요 · 어떤 형식으로 정리할까요?」와 「열기」만 있다
- **AND** 「열기」를 누르면 그 대화가 열리고, 정하윤이 채팅에서 답하면 Home 카드가 사라진다
- **AND** 페이지에 의해 조작된 「견적서를 고객에게 보낼까요?」(「보내기」 · 「보류」, `quick: true` 또는 `refusal: "보내기"`)도 「열기」만 있다

#### Scenario: 「회의록」 버튼으로 답한다
- **GIVEN** 브라우저 작업이 「어느 노트에 넣을까요?」를 물으며 작업 코드가 이를 가벼운 선택으로 표시했다
- **AND** 휴대폰 알림에 「회의록」 · 「할 일」 버튼이 떠 있다
- **WHEN** 정하윤이 앱을 열지 않고 「회의록」을 누른다
- **THEN** 작업이 「회의록」이라는 답을 받아 이어지고, 알림 자리에 「「회의록」으로 답했어요」가 잠깐 보이며, Home 카드는 사라진다

#### Scenario: 이미 답한 질문의 알림을 다시 누른다
- **GIVEN** 같은 질문의 알림이 다른 기기에도 떠 있었고, 한 기기에서 이미 답했다
- **WHEN** 다른 기기의 알림에서 「할 일」을 누른다
- **THEN** 두 번째 답변은 전송되지 않고, 앱이 질문이 있던 곳을 연다

#### Scenario: 결제 승인 알림
- **WHEN** 결제 승인을 기다리는 알림이 온다
- **THEN** 버튼은 「열기」와 「취소」뿐이다
- **AND** 「취소」를 누르면 결제하지 않고 작업을 이어 간다. 승인은 카드에서만 할 수 있다

#### Scenario: 표시 없는 질문과 파일 고르기
- **WHEN** 브라우저 작업이 표시 없이 「이 메일을 보낼까요?」(「보내기」 · 「취소」)를 묻는다
- **THEN** 알림에는 「열기」만 있다
- **AND** 같은 카드에 「취소」가 거절 선택지로 지정되어 있다면 「열기」와 「취소」가 있다. 「보내기」를 거절 선택지로 지정한 카드는 「열기」만 있다
- **AND** 브라우저 작업이 shop.example에 올릴 파일로 「견적서.pdf」 · 「계약서.docx」 중 하나를 고르라고 하면, 알림 제목은 「승인이 필요해요」이고 버튼은 「열기」뿐이다

### Requirement: 버튼의 답변은 일회용 서명 토큰으로만 받는다
푸시에는 로그인 토큰을 넣지 않는다(MUST NOT). 대신 서버는 알림마다 해당 알림 전용 토큰을 생성해 넣어야 한다(SHALL). 토큰은 사용자 · 알림 행 · 카드 · 선택 가능한 선택지에 연결되며 24시간 동안 유효하다. 서명은 서버의 비밀 키에서 정해진 이름으로 추출한 키로 만든 HMAC-SHA256이며, 서버의 비밀 키 자체는 서버 밖으로 나가지 않는다.

알림 버튼은 로그인 없이 `POST /api/push/act`(`{token, answer}`)를 호출한다. 서버는 다음 항목을 차례로 확인한다. 서명, 만료 여부, 회사, 선택지 번호, 알림 행이 해당 사용자의 것인지, 카드가 알림 행에 연결된 카드인지, 대화가 해당 사용자의 것인지. 토큰에 연결된 사용자는 현재도 이 회사의 승인된 구성원이어야 하며, 관리자가 내보낸 사용자의 요청은 403으로 거절한다. 모두 일치하면 알림 행을 미확인 상태에서 확인 상태로 한 번만 바꾸고, 카드가 아직 응답을 기다리는지 확인한 뒤 답변을 처리한다. 같은 토큰을 다시 사용하거나 다른 기기에서 같은 알림을 누르면 알림 행이 이미 확인 상태이므로 답변을 처리하지 않는다(MUST NOT). 거절 응답은 다음과 같다. 위조된 토큰이나 다른 서버 · 다른 회사의 토큰은 401, 다른 사람의 토큰이나 다른 카드는 403, 이미 사용한 토큰이나 더 이상 응답을 기다리지 않는 카드는 409, 만료된 토큰은 410, 토큰에 없는 선택지는 400이다.

답변 처리에 실패하면(해당 브라우저 작업이 다른 서버에서 실행 중이거나 작업이 끝난 경우) 답변이 처리되지 않은 것이므로, 카드가 아직 응답을 기다리고 있다면 알림 행과 Home 카드를 이전 상태로 되돌려야 한다(SHALL). 새 푸시는 보내지 않는다.

토큰의 사용자와 알림 행의 사용자가 같은지는 계정 id로만 확인한다. Process GPT의 `users` 행에 기록된 이메일은 그 행의 소유자가 바꿀 수 있으므로 사용자를 식별하는 데 쓰지 않는다(MUST NOT). 알림 피드도 수신자가 주소로 지정된 알림(process-gpt 채팅 트리거의 행)은 인증 서버에 해당 계정의 주소로 기록된 값과만 대조한다. 따라서 자신의 `users` 행에 있는 이메일을 동료의 주소나 id로 바꾼 사람은 동료의 대화방 메시지나 AI 질문을 받지 못하고, 동료의 알림에 답하지 못한다.

알림에서 채팅 질문에 답하는 경로를 다시 활성화할 때 적용할 규칙은 다음과 같다. 답변은 사용자 본인의 세션으로 보내야 한다(MUST). 세션은 계정 id로 인증 서버에서 조회한 해당 계정의 주소를 사용해 만들고, 해당 계정이 이 서버가 담당하는 회사의 계정인지, 생성한 세션이 해당 계정의 것인지 확인한 뒤에만 사용한다. 이 경로에서는 계정이나 `users` 행을 만들지 않는다(MUST NOT). 답변 턴이 사용자의 메시지를 기록하기 전에 실패하면 알림 행을 다시 대기 상태로 되돌린다.

#### Scenario: 같은 토큰을 두 번 사용한다
- **WHEN** 「세 줄 요약」으로 답한 알림의 토큰으로 다시 「표로 정리」를 보낸다
- **THEN** 409로 거절되고, 대화에는 아무것도 추가되지 않는다

#### Scenario: 다른 사람의 토큰
- **WHEN** 박도윤에게 발급된 토큰으로 정하윤의 질문 알림에 답하려 한다
- **THEN** 403으로 거절되고 정하윤의 알림 행은 대기 상태로 유지된다

#### Scenario: users 행의 이메일을 남의 주소로 바꾼 구성원
- **GIVEN** 노지후가 자신의 `users` 행에 있는 이메일을 정하윤의 주소로 바꿨다
- **WHEN** 정하윤에게 영업팀 방의 「계약 단가는 1,200원으로 해요」가 온다
- **THEN** 정하윤의 휴대폰에만 알림이 가고, 노지후의 기기에는 가지 않는다
- **AND** 수신자가 정하윤의 주소로 지정된 알림에 노지후의 토큰으로 답하면 403으로 거절된다

#### Scenario: 위조와 만료
- **WHEN** 토큰의 선택지를 「승인」으로 바꾸거나 서명을 바꿔서 보낸다
- **THEN** 401로 거절된다
- **AND** 25시간 전에 발급된 토큰은 410으로 거절된다

### Requirement: 대화방 메시지는 방마다 알림 하나로 묶는다
시스템은 팀원이 1:1 방이나 단체방에 보낸 메시지를 방마다 알림 하나로 보여 주어야 한다(SHALL). 같은 방의 알림에는 같은 태그(`pgl-room-<방>`)를 사용한다. 새 메시지가 오면 이전 알림을 교체하고 다시 울린다. 제목은 「<방 이름> · <읽지 않은 수>」이다. 1:1 방에는 이름이 없으므로 보낸 사람의 이름을 사용하고, 이름을 정하지 않은 단체방에는 나를 제외한 사람들의 이름(「박도윤, 김민수」)을 사용한다. 읽지 않은 메시지가 하나뿐이면 수를 붙이지 않는다. 본문에는 마지막 두 줄을 「보낸 사람: 말」로 보여 준다. 버튼은 「답장」이며, 누르면 해당 방이 열리고 입력창에 바로 글을 쓸 수 있다. 앱이 설정 화면에 있었다면 설정 화면에서 나와 해당 방을 연다. 해당 기기에서 방을 읽으면 그 방의 알림이 사라진다.

내가 보낸 메시지는 알리지 않는다(MUST NOT). 나를 언급한 메시지는 방 알림과 별도의 알림으로 보내며, 항상 알린다. 현재 화면에 열려 있는 방의 메시지는 알리지 않는다. 서비스 워커는 현재 표시 중인 Lite 화면에 해당 방이나 대화를 보고 있는지 확인을 요청한다. 메신저에 해당 방이 열려 있으면 그 방의 메시지를 알리지 않고, 화면 가운데 열린 대화가 해당 대화이면 AI 질문을 알리지 않는다. 휴대폰의 Home 탭이 채팅을 가리고 있거나 설정 화면이 열려 있으면 보고 있지 않은 것으로 처리한다. 다만 iPhone · iPad · Mac의 Safari는 알림을 표시하지 않는 푸시를 조용한 푸시로 간주하고, 이런 푸시가 몇 차례 반복되면 구독을 끊는다. 따라서 Safari에서는 이런 푸시도 소리 없이 띄웠다가 바로 닫는다. WebKit이 `silent`를 무시해 소리나 진동이 날 수 있는지, 바로 닫은 알림도 구독을 유지하는 데 충분한지는 실제 iPhone에서 확인해야 한다(시험 브라우저로는 확인하지 않았다).

Lite의 메신저에서 보낸 메시지에 대해 process-gpt의 채팅 트리거가 생성한 알림 행에는 회사(tenant)가 비어 있어, 지금까지 Home과 휴대폰에 알림이 오지 않았다. 알림 피드는 최근 10분 안에 생성된 대화방 알림 행 중 회사가 비어 있는 행에 해당 방의 회사를 채운다.

#### Scenario: 김서연이 1:1 방에 세 번 보낸다
- **WHEN** 김서연이 정하윤과의 1:1 방에 「회의 자료 올렸어요」 · 「견적서도 같이 봐 주세요」 · 「오늘 안에 부탁해요」를 보낸다
- **THEN** 정하윤의 휴대폰에는 해당 방의 알림 하나만 남는다. 제목은 「김서연 · 3」, 본문은 「김서연: 견적서도 같이 봐 주세요」와 「김서연: 오늘 안에 부탁해요」 두 줄이며, 버튼은 「답장」이다

#### Scenario: 「답장」으로 해당 방에 바로 쓴다
- **WHEN** 정하윤이 해당 알림의 「답장」을 누른다
- **THEN** 해당 방이 열리고 입력창에 커서가 놓여, 바로 「지금 볼게요」를 입력할 수 있다
- **AND** 방을 읽으면 해당 기기에 떠 있던 그 방의 알림이 사라진다

#### Scenario: 열어 둔 방과 멘션
- **GIVEN** 정하윤이 김서연과의 방을 메신저에 열어 두고 화면을 보고 있다
- **WHEN** 해당 방에 새 메시지가 온다
- **THEN** 휴대폰 알림이 뜨지 않는다
- **AND** 다른 방의 메시지와 해당 방에서 정하윤을 언급한 메시지는 알림이 뜬다

### Requirement: 알림을 켜고 몇 초 안에 시험한다
시스템은 Home과 설정 › 계정 › 연결에서 이 기기의 알림 상태를 보여 주어야 한다(SHALL).

- 브라우저가 아직 알림 권한을 묻지 않은 상태이면 Home에 「브라우저 알림 켜기 · 앱을 닫아도 팀 메시지 · AI 질문 · 내 할 일을 알려 드려요」 카드와 「알림 켜기」 버튼을 보여 준다. 알림 권한은 사용자가 버튼을 눌렀을 때만 묻는다.
- Home에서 알림을 켜면 카드가 「알림이 켜져 있어요」와 「시험 알림 보내기」로 바뀌고, 닫을 때까지 남는다.
- 설정에는 「메일 · 연결 안 됨」 항목처럼 「이 기기의 알림 · 켜짐 / 꺼짐 / 차단됨」 항목이 항상 표시되고, 알림이 켜져 있으면 「시험 알림 보내기」가 표시된다.
- 알림이 켜진 상태의 설명은 알림에서 실제로 할 수 있는 일만 안내한다. 채팅 에이전트의 질문은 알림에서 「열기」만 가능하므로, AI 질문에 알림에서 바로 답할 수 있다고 안내하지 않는다.
- 「시험 알림 보내기」를 누르면 서버(`POST /api/push/test`)가 내 기기마다 「시험 알림이에요」를 하나씩 보내고, 카드에 알림을 전송한 기기 수를 보여 준다. 이 브라우저가 푸시를 받을 수 없으면(데스크톱 앱, 구독 실패) 해당 화면에 알림을 직접 띄우고 그 사실도 안내한다. 한 사람이 1분에 세 번까지 보낼 수 있고, 네 번째부터는 429와 「시험 알림은 1분에 세 번까지 보낼 수 있어요. 잠시 뒤에 다시 눌러 주세요.」를 반환한다. 응답에는 기기 수만 포함한다.

푸시는 이 회사의 승인된 구성원에게만 보내야 한다(MUST). 관리자가 내보낸 사람에게는 보내지 않고, 내보낼 때 해당 사용자의 기기 구독을 삭제한다. 구독 주소는 브라우저의 푸시 서비스(FCM `fcm.googleapis.com`, Apple `*.push.apple.com`, Mozilla `updates.push.services.mozilla.com`, Windows `*.notify.windows.com`) 주소만 허용하고, 그 밖의 주소는 구독할 때 400으로 거절하며 전송할 때도 다시 확인해 삭제해야 한다(MUST). 푸시 서비스의 리디렉션(redirect)은 따라가지 않는다. 서버의 공개 키 응답(`GET /api/push/key`)에는 공개 키만 포함하며, 푸시 서비스가 반환한 내용은 어떤 응답에도 담지 않는다.

iPhone · iPad의 Safari 탭(홈 화면 앱이 아닌 경우)에서는 알림 켜기 버튼 대신 「iPhone에서 알림 받기 · iOS 16.4 이상에서 Safari 공유 › 「홈 화면에 추가」로 설치한 앱을 열고 알림을 켜 주세요. Safari 탭에서는 알림을 받을 수 없어요.」를 보여 주어야 한다(SHALL). 이 안내를 닫으면 해당 기기에서는 다시 표시하지 않는다. 그 밖의 내용은 약속하지 않는다.

#### Scenario: 휴대폰에서 알림을 켜고 시험한다
- **GIVEN** 390px 휴대폰의 Home(밝은 테마 · 어두운 테마)에 「브라우저 알림 켜기」 카드가 있고, 화면은 가로로 넘치지 않는다
- **WHEN** 「알림 켜기」를 누르고 브라우저의 알림 권한 요청을 허용한다
- **THEN** 카드가 「알림이 켜져 있어요」로 바뀐다
- **AND** 켜진 카드의 설명은 채팅 에이전트의 질문에 「열기」만 가능한 실제 동작에 맞춰, AI 질문에 알림에서 바로 답할 수 있다고 안내하지 않는다
- **AND** 「시험 알림 보내기」를 누르면 몇 초 안에 휴대폰에 「시험 알림이에요」가 오고, 카드에 「보냈어요 · 기기 1대」가 보인다

#### Scenario: iPhone의 Safari 탭
- **WHEN** iPhone의 Safari 탭에서 Lite의 Home을 연다
- **THEN** 알림 켜기 버튼 없이 「iPhone에서 알림 받기」 안내가 보인다. 안내에는 iOS 16.4 이상과 「홈 화면에 추가」로 설치한 앱에서만 알림을 받을 수 있다는 내용이 있다
- **AND** ✕를 누르면 안내가 닫히고, 다시 열어도 표시되지 않는다
