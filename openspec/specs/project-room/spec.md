# 프로젝트 방의 응답 · 바로잡는 말 · 소리 파일 · 프로젝트 안의 주제 · 프로젝트 계획

## Purpose
이 스펙은 새 프로젝트를 만들 때 즉시 응답하는 방식, 작업 중 방법을 바로잡는 요청이 왔을 때 앞 작업을 정리하는 방식, 만들어진 소리 파일을 그 자리에서 듣는 방식을 정한다. 근거는 2026-11-21 휴대폰 녹화(결정 D-1121-09)다.

2026-11-25에 「프로젝트 안의 주제」를 추가했다. 사용자 요청은 다음과 같다: 「홈 채팅에서 주제를 자동 분류하듯이 하나의 프로젝트 내에서도 서브 레벨로 주제들이 자동 분류될 수 있어야 한다. 한 프로젝트 내에서도 많은 내용들이 있을 수 있기 때문에.」 메인 채팅에서 판단 모델(context-router)로 대화를 나누는 방식(스펙 `chat-thread-list`)을 프로젝트 안에도 적용한다. 후보에는 해당 프로젝트의 주제만 포함한다. 주제마다 에이전트 대화가 따로 있으며, `context_threads` 테이블에 프로젝트 키(`<사람>/project/<프로젝트>`)로 저장된다. 따라서 메인 채팅의 대화 목록과 섞이지 않는다. 서버 코드는 `server/lib/projectTopics.js`, 화면의 순수 규칙은 `src/projectTopics.js`, 화면 코드는 `src/components/ConversationBar.vue`(프로젝트에서는 주제 막대)와 `src/components/ProjectList.vue`(열린 프로젝트 아래 주제 행)에 있다. SQL은 바뀌지 않았다. 테스트와 증거는 `e2e/README.md`에 있다.

2026-11-27에 「프로젝트 계획」을 추가했다(설계 turnplan §4 · P2). 프로젝트마다 목적 · 만들 것 · 쓰는 도구 · 지킬 것 · 정한 것을 적어 두고, 그 방의 모든 대화 · 규칙 실행 · 에이전트 · 브라우저 작업이 먼저 읽는다. 방 판정이 계획을 읽는 방식은 스펙 `room-rules` 에 있다.

## Requirements

### Requirement: 새 프로젝트는 바로 열린다
시스템은 새 프로젝트 요청을 받으면 방을 바로 만들어 응답해야 한다(SHALL). 제목을 짓는 모델을 기다려서는 안 된다(MUST NOT). 처음에는 요청의 첫 줄을 짧게 잘라 임시 제목으로 쓰고, 첫 줄이 비어 있으면 「새 프로젝트」를 쓴다. 나중에 모델이 만든 제목으로 바꾸고 `thread` 이벤트로 알린다. 그사이 사용자가 이름을 바꿨거나, 모델이 제목 대신 긴 답을 내놓았거나, 제목 생성에 실패하면 임시 제목을 그대로 둔다. 화면은 방이 만들어지기 전에도 보낸 메시지와 진행 표시를 바로 보여 주어야 한다(SHALL). 방을 만들지 못하면 보낸 글을 입력창에 돌려놓고 실패를 알린다.

#### Scenario: 모델이 느리다
- **GIVEN** 제목 모델이 응답하는 데 5초가 걸린다
- **WHEN** `POST /api/threads`로 새 프로젝트를 만든다
- **THEN** 1초 안에 방 생성 응답이 돌아오고, 몇 초 뒤 제목이 모델이 만든 제목으로 바뀐다

#### Scenario: 보내자마자 보인다
- **GIVEN** 방 생성 응답이 늦어진다
- **WHEN** 새 프로젝트 화면에서 글을 보낸다
- **THEN** 1.5초 안에 내 메시지와 「생각하는 중」이 보인다
- **AND** 서버에 저장된 메시지가 도착해도 같은 메시지가 두 번 보이지 않는다

#### Scenario: 방을 만들지 못했다
- **WHEN** 방을 만들지 못한다
- **THEN** 보낸 글이 입력창으로 돌아오고, 실패했다는 안내가 보인다

### Requirement: 바로잡는 말로 시작한 사이트 작업은 앞 작업을 대신한다
시스템은 같은 방에서 에이전트 작업이 실행 중이거나 대기 중일 때, 해당 요청을 사이트에서 처리하라는 말에 따라 서버 브라우저 작업이 시작되면 앞 작업을 멈춰야 한다(SHALL). 멈춘 작업의 답에는 이유를 남겨야 한다(SHALL). 예: 「notebook.google.com에서 하는 브라우저 작업으로 바꿔서 이전 작업은 멈췄어요.」 멈춘 작업은 「완료했습니다」 같은 답을 내서는 안 된다(MUST NOT). 대기 중이던 작업은 에이전트 서비스에 보내지 않는다. 앞 작업이 이미 만든 파일은 지우지 않는다.

- 프로젝트 방도 메인 채팅처럼 여러 주제로 나뉠 수 있으므로 같은 규칙을 따른다.
- 메인 채팅과 프로젝트 방에서는 여러 작업이 동시에 진행된다. 따라서 진행 중인 작업이 있을 때 사이트 작업이 시작되면 모델에게 「진행 중인 요청을 바로잡는 말인가」를 판정하게 한다. 판정값이 0.7 이상인 해당 작업 하나만 멈춘다. 판정을 받지 못하면 멈추지 않는다.

바로잡는 말이 오면 라우터 모델은 대화 기록을 보고 사이트에서 수행할 작업을 작성한다. 따라서 링크를 다시 보내지 않아도 앞서 올린 링크가 작업 내용에 포함되어야 한다(SHALL). 사용할 브라우저 스킬도 라우터가 스킬 목록(이름·설명)에서 고르며, 해당 스킬의 주소를 시작 주소로 쓴다. 앞서 올린 첨부 파일은 메시지 종류를 기준으로 찾아 함께 전달한다.

#### Scenario: 녹화의 순서
- **GIVEN** 규칙이 없는 프로젝트 방에서 유튜브 링크와 「파워포인트·대본·mp3 를 만들어 줘」를 보내 에이전트가 작업 중이다
- **WHEN** 「노트북엘엠 사이트에 들어가서 생성해야」를 보낸다
- **THEN** 라우터가 `notebooklm` 스킬로 사이트 작업을 시작하고, 앞 작업의 답은 작업을 멈춘 이유로 끝난다
- **AND** NotebookLM 작업 내용에 앞서 올린 유튜브 링크가 포함된다
- **AND** 그 방에 「완료했습니다」라는 답이 나오지 않는다

#### Scenario: 메인 채팅의 다른 요청
- **GIVEN** 메인 채팅에서 요약 문서를 만드는 중이다
- **WHEN** 「노트북엘엠에서 내 노트북 목록 보여 줘」처럼 진행 중인 요청을 바로잡는 말이 아닌 요청이 온다
- **THEN** 앞 작업은 멈추지 않고 끝까지 진행된다

### Requirement: 소리 파일은 그 자리에서 재생된다
시스템은 채팅의 파일 카드가 소리 파일(mp3·m4a·wav·ogg·aac·opus·flac)이면 카드 아래에 바로 재생할 수 있는 플레이어를 보여 주어야 한다(SHALL). 소리·영상 파일을 저장소에 올릴 때는 해당 형식(`audio/*`, `video/*`)을 지정해 휴대폰 브라우저에서 재생할 수 있게 한다. 주소 없이 작업 공간 경로만 있는 파일은 화면에 표시될 때 주소를 받아 온다. 슬라이드 파일은 지금처럼 누르면 편집기로 열린다. 파일 이름에 확장자가 없어도 저장된 형식이 `audio/*`이면 같은 플레이어를 보여 준다. 영상 파일(mp4·m4v·webm·mov 또는 형식 `video/*`)은 카드 아래에 영상 플레이어를 보여 주며, 휴대폰에서도 화면 안에서 재생한다. PDF · 슬라이드 · 문서 파일을 누르면 이음오피스 편집기로 열린다.

#### Scenario: 팟캐스트 MP3
- **WHEN** 작업 중 생성된 mp3 파일의 카드가 대화에 올라온다
- **THEN** 카드 아래 플레이어로 바로 들을 수 있다. 구간 요청에 206으로 응답해 원하는 구간으로 넘겨 들을 수 있다

#### Scenario: 이름 없이 받은 오디오 개요
- **WHEN** NotebookLM이 이름 없이(「download」) 제공한 오디오 개요가 파일 카드로 올라온다
- **THEN** 카드는 서버가 파일 내용을 확인해 정한 이름(`download.m4a`)과 형식(`audio/mp4`)으로 표시되고, 카드 아래 플레이어로 바로 들을 수 있다

#### Scenario: 영상 개요
- **WHEN** mp4 파일 카드가 올라온다
- **THEN** 카드 아래 영상 플레이어로 그 자리에서 볼 수 있다

### Requirement: 프로젝트의 메시지는 그 프로젝트의 주제로 나뉜다
시스템은 맥락 라우터가 켜져 있으면 사용자가 프로젝트에 메시지를 보낼 때마다 판단 모델에게 이 메시지가 해당 프로젝트의 어느 주제로 이어지는지, 아니면 새 주제인지 물어야 한다(SHALL). 후보에는 해당 프로젝트의 주제(최근 것부터)와 해당 프로젝트에서 아직 답변 중인 요청만 포함한다. 메인 채팅의 대화와 다른 프로젝트의 주제는 후보에 포함해서는 안 된다(MUST NOT). 판단 모델에게는 사용자가 쓴 말만 보내고, Lite가 에이전트에게 덧붙이는 안내는 보내지 않는다. 선택된 주제가 있으면 해당 주제의 대화에서 답하고, 새 주제면 새 대화에서 답한다. 판단이 애매하면 프로젝트의 현재 주제에 그대로 둔다. 메시지가 무엇에 관한 것인지는 판단 모델이 정하고, Lite는 후보만 정한다. 예약 실행, 메일 · 팀원의 백그라운드 작업, 스킬 만들기, 프로세스 설계 중의 메시지는 주제별로 나누지 않는다. 이런 메시지는 이전처럼 프로젝트의 현재 대화로 보낸다. 답변이 속한 주제는 그 답 위에 「↳ 주제」로 표시하고, 새 주제면 「↳ 새 주제 · 제목」으로 표시한다.

#### Scenario: 두 주제로 나뉨
- **GIVEN** 한서윤의 메인 채팅에 「주간 보고서 초안」 대화가 있고, 다른 프로젝트에 「출시 강의 영상」 주제가 있다
- **WHEN** 새 프로젝트 「클라우다이크 강의 준비」에 「클라우다이크 강의 준비안을 정리해 줘」, 「견적서 내용을 검토해 줘」, 「강의 표지도 만들어 줘」를 차례로 보낸다
- **THEN** 판단 모델은 세 번 호출되며, 받은 후보는 이 프로젝트의 두 주제뿐이다(「주간 보고서 초안」과 「출시 강의 영상」은 없다)
- **AND** 첫째 메시지와 셋째 메시지는 같은 에이전트 대화에서, 둘째 메시지는 다른 에이전트 대화에서 답한다
- **AND** 둘째 답 위에 「↳ 새 주제 · 견적서 내용을 검토해 줘」가 보인다

### Requirement: 주제의 기록은 프로젝트에 속한다
시스템은 주제마다 제목(해당 주제의 첫 요청의 첫 줄), 최근 요청과 답의 요약, 이전 요청들을 간추린 요지, 요청 수, 마지막으로 대화가 이어진 시각을 기록해야 한다(SHALL). 이 기록은 해당 프로젝트에 속한다. 메인 채팅의 대화 목록(`GET /api/conversations`)에는 표시해서는 안 된다(MUST NOT). `GET /api/threads/:프로젝트/topics`는 프로젝트의 주제를 최근 순으로 반환한다. 마지막 턴이 속한 주제가 프로젝트의 현재 주제가 되며, 다음 메시지의 주제가 불분명하면 그 주제에 그대로 둔다.

#### Scenario: 같은 주제로 이어진 요청
- **WHEN** 「강의 표지도 만들어 줘」가 「클라우다이크 강의 준비안을 정리해 줘」 주제로 이어진다
- **THEN** 해당 주제의 요청 수는 2이고, 요약은 「최근 요청: 강의 표지도 만들어 줘」로 시작하며, 요지는 「클라우다이크 강의 준비안을 정리해 줘」다
- **AND** 메인 채팅의 대화 목록에는 「주간 보고서 초안」 하나만 그대로 남는다

### Requirement: 프로젝트 화면의 주제 — 채팅 위 막대와 목록의 한 단계 아래
시스템은 프로젝트에 주제가 두 개 이상이면 프로젝트 채팅 위에 「주제 N개 · 주제별로 보기」 막대를 보여 주어야 한다(SHALL). 막대를 누르면 「판단 모델이 이 프로젝트에서 나눈 주제」 아래에 주제가 최근 순으로 나온다. 각 줄에는 제목, 마지막으로 대화가 이어진 시각, 메시지 수, 한 줄 요약이 표시된다. 넓은 화면의 왼쪽 프로젝트 목록에서는 열린 프로젝트 아래에 주제 행을 한 단계 들여써서 표시한다. 각 행에는 제목, 시각, 메시지 수가 표시된다. 주제가 하나뿐이거나 없으면 막대와 주제 행을 표시하지 않는다. 메시지 수에는 해당 주제의 요청과 답, 해당 턴이 남긴 파일 카드를 포함한다. 다음 메시지가 먼저 들어온 뒤에 도착한 앞 턴의 카드도 앞 턴의 주제에 포함해 센다.

#### Scenario: 막대와 주제 행
- **WHEN** 위 세 메시지에 대한 답과 파일 카드가 도착한 뒤 프로젝트를 본다
- **THEN** 채팅 위에 「주제 2개 · 주제별로 보기」가 보인다
- **AND** 왼쪽 목록의 프로젝트 아래에 「클라우다이크 강의 준비안을 정리해 줘 · 6」과 「견적서 내용을 검토해 줘 · 3」이 최근 순으로 보인다

#### Scenario: 주제가 하나
- **WHEN** 새 프로젝트의 첫 메시지에 답이 온다
- **THEN** 주제 막대는 아직 보이지 않는다

### Requirement: 주제 하나로 좁히고 「전체」로 돌아간다
시스템은 막대의 주제, 왼쪽 목록의 주제 행, 답 위의 「↳ 주제」 가운데 하나를 누르면 프로젝트 채팅에 해당 주제의 메시지만 표시해야 한다(SHALL). 주소는 /projects/:프로젝트/t/:주제다. 막대에는 해당 주제의 제목, 「이 주제의 메시지 N개 · 여기서 물으면 이 주제에 이어져요」, 「전체」, 「다른 주제 ▾」가 보인다. 왼쪽 목록에서는 해당 주제 행이 강조된다. 입력창의 안내는 「이 주제에 이어서 묻기」다. 오른쪽 산출물 목록은 「이 주제의 산출물」로 바뀌고 해당 주제의 파일만 보여 준다. 주제별 화면에서 보낸 메시지는 판단 모델에 묻지 않고 해당 주제로 이어진다. 이 메시지는 보내자마자 주제별 화면에 보인다. 이 프로젝트의 주제가 아닌 대화를 지정해 보내면 그 지정을 받아들이지 않고 일반 메시지처럼 주제를 나눈다. 「전체」나 왼쪽 목록의 프로젝트 이름을 누르면 프로젝트 전체(/projects/:프로젝트)로 돌아간다.

#### Scenario: 강의 주제만
- **WHEN** 막대에서 「클라우다이크 강의 준비안을 정리해 줘」를 고른다
- **THEN** 견적서 메시지는 보이지 않고, 산출물 목록에는 「이 주제의 산출물」이라는 제목 아래 클라우다이크_강의준비안.md와 강의_표지_문구.md 두 개만 보인다
- **AND** 그 화면에서 「목차를 두 장으로 줄여 줘」를 보내면 판단 모델을 호출하지 않고 해당 주제의 에이전트 대화에서 답하며, 해당 주제의 요청 수가 3이 된다

#### Scenario: 다른 주제와 전체
- **WHEN** 왼쪽 목록에서 「견적서 내용을 검토해 줘」를 누르고, 이어서 막대의 「전체」를 누른다
- **THEN** 먼저 견적_검토표.csv 하나만 산출물로 보이고, 「전체」를 누르면 주소가 /projects/:프로젝트로 바뀌며 모든 주제의 메시지와 파일이 다시 보인다

#### Scenario: 답 위의 표시
- **WHEN** 전체 화면에서 「↳ 새 주제 · 견적서 내용을 검토해 줘」를 누른다
- **THEN** 프로젝트 채팅에 해당 주제의 메시지만 보인다

### Requirement: 주제가 생기기 전부터 있던 프로젝트
시스템은 주제 기록은 없지만 이미 대화가 있는 프로젝트에 메시지가 오면, 기존 대화를 프로젝트 이름을 제목으로 하는 주제로 후보에 넣어야 한다(SHALL). 판단 모델이 응답하면 기존 대화는 해당 프로젝트의 첫 주제로 기록되고, 이전 메시지도 그 주제에 속한다. 판단 모델이 응답하지 않으면 아무 기록도 남기지 않는다.

#### Scenario: 이음오피스 수정
- **GIVEN** 「이음오피스 수정」 프로젝트는 주제 없이 「구글 문서 링크 읽어 줘」로 대화해 왔다
- **WHEN** 「견적 단가표 초안 써 줘」를 보내고, 이어서 「구글 문서 다시 요약해 줘」를 보낸다
- **THEN** 첫 메시지를 처리할 때 판단 모델이 받은 후보는 「이음오피스 수정」 하나다. 첫 메시지는 새 주제에서, 둘째 메시지는 기존 대화에서 답한다
- **AND** 주제 행에 「이음오피스 수정」과 새 주제가 표시되고, 「이음오피스 수정」을 고르면 이전 메시지인 「구글 문서 링크 읽어 줘」가 보인다

### Requirement: 프로젝트의 기존 동작은 유지된다 — 폴더의 변형, 한 번에 한 턴
시스템은 주제가 나뉘어도 프로젝트의 폴더 작업 방식을 기존대로 유지해야 한다(SHALL). 폴더에서 작업하는 프로젝트의 변형은 주제와 상관없이 프로젝트당 하나다. 각 턴에서는 해당 변형을 그 턴이 속한 주제의 대화 폴더에 꺼내 놓고, 에이전트가 그 안에서 작업한다. 프로젝트의 턴은 주제가 달라도 한 번에 하나씩 순서대로 실행된다. 다음 턴은 앞 턴의 작업 내용을 변형에 담는 과정이 끝난 뒤 시작한다. 폴더 막대(「반영」), 프로젝트에서 시작한 프로세스, 방 규칙은 기존과 같다.

#### Scenario: 폴더 프로젝트의 두 주제
- **WHEN** 새 폴더에서 작업하는 프로젝트에 「강의 목차를 정리해 줘」와 「견적 비교표를 검토해 줘」를 잇달아 보낸다
- **THEN** 두 턴은 서로 다른 에이전트 대화로 전달된다. 각 턴의 작업 폴더는 해당 턴의 대화 폴더 안(`/workspace/.bpmn/<그 주제>/folders/…`)에 있으며, 두 턴 모두 프로젝트의 같은 변형 브랜치에서 작업한다
- **AND** 변형은 하나뿐이고, 폴더 막대와 「주제 2개」 막대가 함께 보인다

### Requirement: 라우터가 없거나 연결되지 않으면 기존대로 처리한다
시스템은 맥락 라우터가 설정되어 있지 않거나 연결되지 않으면 기존처럼 프로젝트의 현재 대화에서 메시지에 답해야 한다(SHALL). 연결 실패, 오류 응답, 해당 프로젝트에 속하지 않는 대화를 반환한 응답은 모두 라우터에 연결되지 않은 경우로 처리한다. 이때 실패 답을 표시해서는 안 되며(MUST NOT), 주제 기록도 남기지 않는다. 주제가 없는 프로젝트에는 막대와 주제 행을 표시하지 않는다.

#### Scenario: 라우터에 연결되지 않는 동안
- **WHEN** 주제가 둘인 프로젝트에서 라우터에 연결되지 않은 상태로 「참고할 만한 점을 짧게 알려 줘」를 보낸다
- **THEN** 프로젝트의 현재 주제에 해당하는 에이전트 대화로 답이 온다. 주제 기록은 바뀌지 않고, 「처리하지 못했어요」 같은 실패 답은 나오지 않는다

#### Scenario: 처음부터 라우터 없이
- **WHEN** 라우터에 연결되지 않은 상태로 새 프로젝트 「팟캐스트 대본」에 메시지 두 개를 보낸다
- **THEN** 두 답은 같은 에이전트 대화로 오고, 주제 기록은 없으며, 주제 막대와 주제 행은 보이지 않는다

### Requirement: 휴대폰과 밤 테마에서도 주제를 고른다
시스템은 390px 휴대폰에서 주제 막대와 주제 창을 화면 폭 안에 표시하고, 페이지가 옆으로 밀리지 않게 해야 한다(SHALL). 창에서 주제를 누르면 해당 주제의 메시지만 보인다. 밤 테마에서는 선택한 주제 행의 제목에 테마의 기본 글자색을 적용한다.

### Requirement: 프로젝트 계획 — 이 프로젝트의 모든 대화가 먼저 읽는다
시스템은 프로젝트 방마다 「프로젝트 계획」을 두어야 한다(SHALL). 계획은 목적(200자) · 만들 것(5개) · 쓰는 도구(8개 — 이름 · 종류 · 등록된 이름 `ref` · 쓰는 방법) · 지킬 것(6개) · 정한 것(6개)이다. 도구의 `ref` 에는 등록된 브라우저 스킬의 이름만 들어가고, 다른 이름은 비운다. 계획은 방의 메시지 행 하나로 저장한다(`role system`, `kind note`, `content.projectNote` — SQL 없음). 가장 새 행이 계획이고, 그 앞의 20개가 이력이다. 계획 행은 채팅 목록(`GET /api/threads/:id/messages`)에 나오지 않는다. 계획을 보고 고치는 사람은 방의 주인뿐이다(사용자 결정 2026-11-25 「주인만」). 다른 사람에게는 읽기 · 고치기 · 되돌리기가 모두 404 다. 근거는 2026-11-27 녹화다: 「이 프로젝트의 방향이 목적이 이렇다 라고 하는 것을 … 클로드MD처럼 뭔가 마스터 플랜 같은 이런게 있어야 되겠죠」. 서버는 `server/lib/projectNote.js` · `server/routes/projectNote.js`, 질문 · 프롬프트는 스킬 `skills/project-plan`, 화면은 `src/components/ProjectNote.vue` 다.

#### Scenario: 방 맨 위의 칩과 시트
- **WHEN** 계획이 있는 프로젝트 방을 연다
- **THEN** 방 맨 위(규칙 막대 아래)에 「프로젝트 계획 · <목적>」 칩이 있고, 누르면 머리에 「이 프로젝트의 모든 대화가 먼저 읽어요」가 있는 시트가 열린다. 시트에는 목적 · 쓰는 도구 · 만들 것 · 지킬 것 · 정한 것 다섯 칸이 있다
- **AND** 390px 휴대폰에서는 아래 시트로 열리고, 「저장」이 화면 안에 있으며, 페이지가 옆으로 밀리지 않는다(밝은 · 밤 테마)

#### Scenario: 사람이 고친 항목은 낱말 그대로 남는다
- **WHEN** 사람이 시트에서 항목 하나를 고치고 하나를 더해 저장한다
- **THEN** 고치거나 더한 항목에만 「고정」 표시가 붙고, 그대로 둔 항목은 고정되지 않는다
- **AND** 그 뒤 AI 가 계획을 고치며 그 항목을 빼거나 바꿔 써도, 서버가 고정한 항목을 낱말 그대로 제자리에 되돌린다

#### Scenario: 1,200자를 넘는 계획
- **WHEN** 계획을 글로 옮기면 1,200자를 넘는다
- **THEN** 고정하지 않은 가장 오래된 「정한 것」부터, 그다음 「지킬 것」을 빼서 1,200자 안으로 맞추고, 고정한 항목은 남는다

#### Scenario: 다른 사람
- **WHEN** 다른 계정이 그 방의 계획을 읽거나 고치거나 되돌리려 한다
- **THEN** 404 를 받고 계획은 바뀌지 않는다

### Requirement: 계획이 없는 방은 첫 턴에 지난 대화에서 계획을 채운다
시스템은 계획이 없는 프로젝트 방에 사람이 메시지를 보내면, 방의 처음 메시지 6개(미션은 대개 처음에 말한다) · 규칙을 정한 모든 메시지(지금은 꺼진 것도) · 마지막 40개 메시지 · 하위 대화의 제목과 요지 · 지금 규칙 · 방 이름을 읽어 계획을 채워야 한다(SHALL). 그 사이를 뺐으면 뺐다고 적는다. 몇 초(기본 8초) 안에 채워지면 그 턴의 방 판정부터 계획을 읽는다. 늦으면 채워지는 대로 저장하고 다음 턴부터 읽는다. 처음의 미션이 뒤의 세부 지시에 묻히지 않도록, 세부 지시는 「지킬 것」으로 간다. 채운 계획은 칩 「프로젝트 계획을 채웠어요: <목적>」(「계획 보기」만, 되돌리기 없음)으로 알린다. 다음 턴에는 다시 채우지 않는다.

#### Scenario: 「링크 슬라이드 팟캐스트」 같은 방
- **GIVEN** 첫 메시지가 「이 방에서 내가 주는 url이 있으면 … 노트북엘엠으로 슬라이드를 만들고 그 팟캐스트를 하나 만들어 주면 돼」이고, 뒤에 「미디엄은 … 내 계정으로 접근해서 인쇄시킨 후, pdf 등으로 만든후에 노트북엘엠에 넣어야 해.」가 있으며, 방의 규칙은 그 세부 지시로 덮어써져 있다
- **WHEN** 사람이 링크 하나를 보낸다
- **THEN** 계획의 목적은 「링크 · 파일을 NotebookLM 슬라이드 · 팟캐스트로」이고, 지킬 것에 「미디엄은 내 계정으로 인쇄해 PDF 로 넣는다」가 있다(실제 사내 모델 frentis · Sonnet 둘 다, 4초 안팎)
- **AND** 그 턴의 방 판정이 채운 계획의 목적을 읽는다

### Requirement: 대화가 아무리 길어도 계획은 휘발되지 않는다
시스템은 프로젝트 방의 모든 턴에 계획을 계획의 행에서 직접 읽어 넘겨야 한다(SHALL). 최근 대화의 창(라우터 8개, 앞단 4개)이나 기록을 줄이는 것에 기대서는 안 된다(MUST NOT). 방 판정 · 라우터 · 규칙 실행 · 에이전트에게 가는 메시지(하위 대화 포함) · 브라우저 작업이 모두 그렇다. 근거는 2026-11-27 사용자다: 「그리고 프로젝트 룸에서 어떠한 지시 … 같은 초기 지시가 들어간 프로젝트가 있다 - 이 경우 자꾸 이후에 그 프로젝트에서 언급한 일종의 원칙이나 규칙, 목표 등이 뒤로 갈수록 휘발되는 경우가 있다 … 각 프로젝트별로 어떠한 목적이나 원칙 등이 CLAUDE.md 처럼 관리되는 뭔가가 있어야 할거 같고, 중간중간 방향을 개선하거나 수정한 내용 등이 이 파일에 관리되어야 한다.」

#### Scenario: 미션 뒤로 64개 메시지가 쌓인 방
- **GIVEN** 첫 메시지가 미션(「… url이 있으면 … 노트북엘엠으로 슬라이드를 만들고 그 팟캐스트를 …」)이고, 그 뒤로 다른 이야기 64개가 쌓였으며, 계획도 규칙도 없다
- **WHEN** 링크만 보낸다
- **THEN** 처음 채우기가 첫 메시지의 미션을 읽어 계획의 목적을 그 미션으로 채운다(마지막 40개에는 미션이 없다 — 실제 사내 모델로도 목적 「사람이 주는 URL · 링크를 받아 NotebookLM으로 슬라이드와 팟캐스트를 만들어 주는 곳」)
- **AND** 미션이 라우터의 최근 대화에 없어도 라우터의 프롬프트에는 계획이 있어, 일반 요약이 아니라 계획의 도구(그 브라우저 스킬)로 브라우저 작업이 시작된다
- **AND** 그 뒤 같은 방의 에이전트 턴과 규칙 실행에도 계획이 들어 있고, 모델이 빈 답을 내도 계획은 비지 않는다

### Requirement: 대화가 이어지며 계획이 고쳐진다
시스템은 프로젝트 턴이 끝났을 때 앞단 계획이 「계획에 남길 말」(memory)이라고 했거나, 계획이 읽은 마지막 메시지 뒤로 사람의 메시지가 5개를 넘었으면, 지금 계획과 그 뒤의 메시지(12개까지, 600자씩)로 계획 전체를 뒤에서 다시 써야 한다(SHALL). 바뀐 것이 있으면 칩으로 알린다: 「계획에 넣었어요: …」 · 「계획의 목적을 바꿨어요: …」 · 「계획에서 뺐어요: …」, 그리고 「되돌리기」 · 「계획 보기」. 「되돌리기」는 계획을 그 변경 바로 앞의 행으로 돌린다(그 뒤에 다른 변경이 있었으면 그 변경이 한 것만 되돌린다). 한 칩은 한 번만 되돌린다(409). 바뀐 것이 없으면 행을 새로 만들지 않는다.

#### Scenario: 대화가 도구를 정했다
- **GIVEN** 계획에 쓰는 도구가 없다
- **WHEN** 「이 방은 앞으로 오디오는 NotebookLM 을 서버 브라우저로 써서 만들자」라고 말하고 턴이 끝난다(앞단 계획 memory)
- **THEN** 계획의 쓰는 도구에 NotebookLM(`ref` notebooklm, 종류 browser_skill)이 들어가고, 칩 「계획에 넣었어요: NotebookLM — …」이 보인다

#### Scenario: 되돌리기
- **WHEN** 「계획에 넣었어요」 칩의 「되돌리기」를 누른다
- **THEN** 계획은 그 앞의 행의 내용으로 돌아가고(되돌린 것도 기록의 한 줄로 남는다), 칩은 「되돌렸어요」가 된다

### Requirement: 중간에 바꾼 방향은 계획의 바뀐 기록으로 남는다
시스템은 계획이 바뀔 때마다 그 변경을 계획의 기록 한 줄로 남겨야 한다(SHALL): 언제, 누가(사람 · AI), 무엇이 바뀌었는지(글과 바뀐 항목), 어느 메시지에서 나왔는지(방에서 넣은 것 · 규칙을 정한 것 · AI 가 대화를 읽고 고친 것은 그 메시지, 직접 고친 것 · 처음 채운 것은 없음). 중간에 고친 방향은 지킬 것 · 정한 것 항목이 되고, 목적이 정말 바뀌면(규칙을 새로 정함) 목적이 바뀐다. 계획 시트에는 「바뀐 기록」이 있고, 기록마다 「되돌리기」가 있다. 가장 새 변경을 되돌리면 그 앞의 내용으로, 뒤에 다른 변경이 있으면 그 변경이 한 것만 되돌린다. 되돌린 것도 기록이 되고, 되돌린 기록은 다시 되돌리지 않으며(409 · 400), 그 변경을 알린 칩도 「되돌렸어요」가 된다. 바뀐 것 없는 저장은 기록을 만들지 않는다. 방의 주인은 언제든 직접 고칠 수 있다. 기록은 계획의 행에 있다(`content.projectNote.change`, 20개 — SQL 없음). 근거는 같은 날 사용자다: 「중간중간 방향을 개선하거나 수정한 내용 등이 이 파일에 관리되어야 한다」.

#### Scenario: 방에서 넣고, 직접 고치고, 기록에서 되돌린다
- **GIVEN** 방에서 「앞으로 팟캐스트는 10분 안으로 하자」로 계획에 넣었고, 시트에서 만들 것에 「팟캐스트 MP3」를 직접 더했다
- **WHEN** 시트의 「바뀐 기록」을 본다
- **THEN** 맨 위에 「나 · <시각> · 직접 고쳤어요: 팟캐스트 MP3」, 그 아래 「나 · <시각> · 계획에 넣었어요: 팟캐스트는 10분 안으로 만든다 · 보낸 메시지 "앞으로 팟캐스트는 10분 안으로 하자"」가 있다
- **AND** 그 아래 줄의 「되돌리기」를 누르면 그 결정만 빠지고 「팟캐스트 MP3」는 남으며, 맨 위에 「되돌렸어요: …」 줄이 생기고 그 줄은 「되돌렸어요」로 표시되며, 채팅의 그 칩도 「되돌렸어요」가 된다

### Requirement: 프로젝트의 모든 일이 계획을 받는다
시스템은 프로젝트 방에서 시작하는 일에 계획을 글(1,200자 안, 머리 「[프로젝트 계획] … 이번 메시지가 무엇을 할지 정한다」)로 함께 주어야 한다(SHALL). 받는 곳은 방 판정(목적 · 지킬 것), 앞단 계획(계획 카드), 라우터, 규칙 받아 적기, 규칙 실행, 에이전트에게 가는 메시지(턴마다 · 하위 대화마다 — 하위 대화는 기록이 따로이고 계획은 바뀌기 때문), 브라우저 작업의 할 일이다. 계획은 배경이고 이번 메시지가 결정한다. 계획의 쓰는 도구가 서버 브라우저 스킬이면, 연결 서비스로 가는 지름길과 문서 지름길을 건너뛰고 라우터가 계획을 읽어 고른다(구조적 조건이고 말의 뜻을 코드로 읽지 않는다).

#### Scenario: 규칙 없이 링크만
- **GIVEN** 규칙이 없고, 계획의 쓰는 도구에 NotebookLM(서버 브라우저 스킬)이 있다
- **WHEN** 유튜브 링크만 보낸다
- **THEN** 라우터가 계획을 읽고 그 스킬로 브라우저 작업을 시작한다. 계획 카드의 처리 주체는 「브라우저 · NotebookLM」이고, 작업의 할 일에 계획이 붙는다

#### Scenario: 새 하위 대화
- **WHEN** 프로젝트에서 새 하위 대화가 시작된다
- **THEN** 그 하위 대화의 첫 메시지에 계획이 들어 있다

#### Scenario: 스킬 없는 규칙의 실행
- **WHEN** 스킬이 없는 규칙대로 에이전트가 일한다
- **THEN** 에이전트에게 가는 메시지에 계획이 한 번 들어 있다
