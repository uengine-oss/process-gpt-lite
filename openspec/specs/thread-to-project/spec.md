# 걸러 본 대화를 통째로 프로젝트로 옮기기 — 채팅에서는 사라지고 프로젝트에서만 이어 가기

## Purpose
2026-11-28 사용자는 휴대폰 채팅 탭에서 대화 하나만 걸러 본 화면(「‹ 전체 대화」, 대화 제목, 「이 대화의 메시지 22개 · 여기서 물으면 이 대화에 이어져요」, 「비공개」, 「다른 대화 ▾」)을 보며 이렇게 말했다. 「필터링된 채팅방 자체를 프로젝트로 이관하는 기능. 이관 후엔 이 채팅 내용은 프로젝트에서만 볼 수 있음. 기존 채팅 목록에서는 제거됩니다... 라는 알림도 줘야」.

스펙 `chat-to-project`(「프로젝트로 시작」)는 원래 대화를 그대로 둔 채 프로젝트에서 이어 간다. 반면 이 스펙은 대화를 이루는 메시지 · 산출물 · 첨부를 복사하지 않고 프로젝트로 **옮긴다**. 옮긴 대화는 해당 프로젝트의 주제(스펙 `project-room` 「프로젝트 안의 주제」) 하나가 되고, 채팅 목록 · 전체 대화 · 검색의 채팅 영역에서는 사라진다. 옮기기 전에 무엇이 달라지는지 안내한다. 프로젝트가 다른 사람도 구성원으로 참여하는 공유 폴더를 사용하면 그 사실을 한 번 더 확인받는다. 프로젝트에서 「채팅으로 되돌리기」를 눌러 되돌릴 수 있다.

어디서 시작하든 같은 확인 화면을 사용한다.
- 단추: 걸러 본 대화 상단의 「다른 대화 ▾」 → 「프로젝트로 옮기기」.
- 말: 「이 대화 프로젝트로 옮겨 줘」 → 채팅의 라우터 모델이 도구 `move_to_project`를 선택하면 해당 대화에 카드가 생성되고, 카드의 단추를 누르면 같은 확인 화면이 열린다. 요청의 의미는 낱말이나 정규식으로 판단하지 않는다. 사용자가 말한 프로젝트 이름이 어느 프로젝트를 가리키는지는 판정 모델이 판단하며, 판정 결과는 추천에만 사용한다.
- 새 프로젝트: 「새 프로젝트로 옮기기」는 `chat-to-project`의 확인 카드(이름 · 목적 · 템플릿 추천)를 대화 전체에 적용한다. 「만들고 옮기기」를 누르면 프로젝트를 만든 다음 대화를 옮긴다.

서버 코드는 `server/lib/conversationMove.js` · `server/routes/conversationMove.js`와 `lib/store.js`의 addMessage · `lib/conversations.js`의 topicOf · `lib/chatProject.js` · `lib/search.js` · `lib/agent.js`의 도구 `move_to_project`에 있다. 화면 코드는 `src/components/ConversationBar.vue` · `ConversationMoveSheet.vue` · `ConvMoveCard.vue` · `ProjectOfferCard.vue` · `Message.vue` · `src/convMove.js` · `src/projectTopics.js` · `src/views/MainView.vue`에 있다. 질문과 프롬프트는 스킬 `skills/chat-to-project`(`prompts/pick-project.md`, `rules.json`의 `move`)에 있다. 새 테이블과 SQL은 없다. 대화의 `context_threads` 행은 해당 사용자의 키에서 프로젝트의 키(`<사람>/project/<프로젝트>`)로 옮긴다.

프로젝트를 지우는 기능은 아직 없다. 그 기능을 추가할 때는 옮겨 온 대화를 먼저 채팅으로 되돌린 뒤 프로젝트를 지운다.

## Requirements

### Requirement: 걸러 본 대화의 「다른 대화 ▾」에 「프로젝트로 옮기기」가 있고, 옮길 수 있는 프로젝트만 고를 수 있다
시스템은 메인 채팅에서 대화 하나를 걸러 본 화면(`/chat/c/:cid`)의 「다른 대화 ▾」 맨 위에 「프로젝트로 옮기기 · 이 대화를 통째로 프로젝트로 옮겨요 · 채팅 목록에서는 빠져요」를 보여 주어야 한다(SHALL). 이를 누르면 선택 화면에 대화 제목과 메시지 수(화면의 「이 대화의 메시지 N개」와 같은 규칙으로 센 수)를 표시하고, 「옮긴 대화는 고른 프로젝트에서만 볼 수 있어요. 채팅 목록과 전체 대화에서는 사라져요.」를 보여 준다. 그 아래에는 「새 프로젝트로 옮기기」와 해당 사용자의 프로젝트 목록을 둔다. 프로젝트마다 사용하는 공유 폴더(또는 템플릿 전용 작업 공간)를 표시하고, 다른 구성원이 있으면 「구성원 N명」을 보여 준다. 해당 사용자가 더는 사용할 수 없는 프로젝트(사용하는 폴더의 권한이 「실행」보다 낮음)는 선택할 수 없으며, 「이 프로젝트의 폴더 「…」에 쓸 권한이 없어요.」라는 이유를 보여 준다. 예약 작업 · 브리프의 대화(새 실행이 계속 채팅으로 들어옴)와 답변을 작성 중이거나 기다리는 대화는 옮길 수 없으며, 선택 화면에 그 이유를 보여 준다.

#### Scenario: F-TM-01 · TM-I-01 고르기
- **GIVEN** 정하윤의 채팅에 「가나정밀 교육 요청 조사」(요청 · 문서 답변 · 파일 · 후속 질문 · 그 답변, 5개)가 있다. 프로젝트로는 「영업 자료 정리」(공유 폴더 「영업 자료」, 김서연도 구성원), 「규정 검토」(폴더 「규정집」 — 정하윤은 보기 권한만 있음) 등이 있다.
- **WHEN** 해당 대화를 걸러 본 뒤 「다른 대화 ▾」 → 「프로젝트로 옮기기」를 누른다.
- **THEN** 「「가나정밀 교육 요청 조사」 · 메시지 5개」와 안내가 보인다. 「영업 자료 정리」에는 「공유 폴더 「영업 자료」 · 구성원 1명」이 표시되고, 「규정 검토」는 선택할 수 없으며 「「규정집」에 쓸 권한이 없어요」가 보인다.

#### Scenario: TM-I-05 옮길 수 없는 대화
- **WHEN** 예약 작업 「주간 시장 동향」의 대화나 답변을 작성 중인 대화를 옮기려고 한다.
- **THEN** 각각 409(`standing` · `busy`)를 반환하고 아무것도 옮기지 않는다.

#### Scenario: TM-I-11 대화를 아직 모르는 턴
- **GIVEN** 채팅에 라우터가 아직 답하지 않은 턴(해당 대화의 턴일 수도 있음)이나, 어느 대화에 속하는지 모른 채 대기 중인 턴이 있다.
- **WHEN** 대화를 옮기려고 한다.
- **THEN** 409(`busy`)를 반환하고 선택 화면에서도 옮길 수 없다고 안내한다. 옮긴 뒤 해당 턴의 답변이 채팅에 남거나 채팅 키의 행이 다시 생기는 일은 없다. 다른 대화에 속한다고 이미 확인된 턴은 이동을 막지 않는다.

#### Scenario: TM-I-13 브라우저 작업이 진행 중인 대화
- **GIVEN** 대화에 대기 · 진행 · 입력 기다림 상태인 브라우저 작업 카드가 있다.
- **WHEN** 대화를 옮기거나 프로젝트에서 되돌리려고 한다.
- **THEN** 409(`busy_task`)를 반환한다. 작업이 끝나면 옮기고 되돌릴 수 있다. 작업의 질문 · 파일 · 결과가 이전 방에 남지 않게 하기 위해서다.

#### Scenario: TM-I-11 바쁜 까닭을 바르게 말한다
- **WHEN** 대화를 아직 모르는 채팅의 턴 때문에 옮기지 못한다.
- **THEN** 「채팅에서 아직 답을 쓰고 있어요. 답이 끝나면 다시 옮겨 주세요.」라고 말한다. 그 대화의 턴이면 「이 대화에서 아직 답을 쓰고 있어요. …」, 되돌리기를 막는 프로젝트의 턴이면 「프로젝트에서 아직 답을 쓰고 있어요. 답이 끝나면 다시 되돌려 주세요.」라고 말한다.

### Requirement: 대화 목록의 행에서도 「프로젝트로 옮기기」를 연다
2026-11-28 사용자: 「쓰레드 내용을 곧바로 프로젝트로 만드는 기능 어떻게 되고 있니?」. 기존에는 특정 대화만 보는 상태에서 「다른 대화 ▾」를 통해서만 옮기기 기능을 사용할 수 있었다. 시스템은 대화 목록의 행에서도 같은 「프로젝트로 옮기기」 창을 열 수 있어야 한다(SHALL). 휴대폰에서는 행을 길게 누르고, 넓은 화면에서는 행에 포인터를 올리면 나타나는 폴더 단추를 누르거나 마우스 오른쪽 단추로 행을 누른다. 행을 짧게 누르면 지금처럼 해당 대화만 보여 준다. 목록의 안내 문구인 「… 길게 누르면 프로젝트로 옮길 수 있어요.」(넓은 화면은 「오른쪽 단추로 누르면」)로 이 동작을 알린다. 「전체 대화」, 예약 작업 · 브리프의 대화, 메시지가 없는 대화에는 이 동작을 제공하지 않는다. 창은 열리자마자 초점을 받아 프로젝트 목록을 불러오는 중에도 Esc로 닫을 수 있다. 창을 닫아도 목록은 그대로 남는다.

#### Scenario: F-TM-08 휴대폰에서 행을 길게 누른다
- **WHEN** 390px 휴대폰에서 대화 목록의 행을 길게 누른다
- **THEN** 해당 대화의 이름이 적힌 「프로젝트로 옮기기」 창이 열리고 옮길 수 있는 프로젝트들이 보인다
- **AND** 창을 닫아도 목록은 그대로 남고, 행을 누르면 해당 대화만 보여 준다

#### Scenario: F-TM-09 넓은 화면에서 폴더 단추 · 오른쪽 단추
- **WHEN** 1280px(어두운 화면)에서 행에 포인터를 올려 폴더 단추를 누르고, 창을 닫은 뒤 마우스 오른쪽 단추로 행을 누른다
- **THEN** 두 번 모두 해당 대화의 「프로젝트로 옮기기」 창이 열리고 Esc로 닫을 수 있다
- **AND** 「전체 대화」에는 폴더 단추가 없고, 마우스 오른쪽 단추로 눌러도 창이 열리지 않는다

### Requirement: 옮기기 전에 무엇이 달라지는지 알리고, 구성원이 있는 프로젝트는 한 번 더 확인받는다
시스템은 프로젝트를 선택하면 옮기기 전에 「옮기면 이 대화(메시지 N개)는 프로젝트 「…」에서만 볼 수 있어요. 채팅 목록과 전체 대화에서는 사라져요.」를 보여 주어야 한다(SHALL). 「프로젝트의 이 대화에서 「채팅으로 되돌리기」를 누르면 다시 채팅으로 가져와요.」도 함께 보여 준다. 해당 프로젝트가 다른 사람도 구성원으로 참여하는 공유 폴더를 사용하면(템플릿 전용 작업 공간은 해당 사용자만 볼 수 있으므로 해당하지 않음) 「이 프로젝트는 공유 폴더 「…」를 사용해요. 옮긴 뒤 이 대화에서 만드는 파일은 프로젝트 구성원 N명(이름 셋까지 · 외 N명)도 볼 수 있어요.」를 눈에 띄게 보여 주고, 「구성원도 볼 수 있다는 것을 확인했어요」에 체크해야 「옮기기」를 누를 수 있게 한다. 서버도 이 확인이 없는 요청은 409(`confirm_members`, 구성원 목록 포함)로 거절한다. Lite 프로젝트 방의 메시지는 소유자만 볼 수 있으므로 「구성원도 이 대화를 볼 수 있어요」라고 쓰지 않고, 실제로 볼 수 있게 되는 대상(해당 폴더의 프로젝트 변형에 쌓이는 파일)을 안내한다.

#### Scenario: F-TM-01 · TM-I-03 구성원이 있는 프로젝트
- **WHEN** 「영업 자료 정리」를 선택한다.
- **THEN** 「옮기면 이 대화(메시지 5개)는 프로젝트 「영업 자료 정리」에서만 볼 수 있어요. 채팅 목록과 전체 대화에서는 사라져요.」와 「… 프로젝트 구성원 1명(김서연)도 볼 수 있어요.」가 보이고, 체크하기 전까지는 「옮기기」를 누를 수 없다.
- **AND** 확인 없이 서버에 옮기기를 요청하면 409(`confirm_members`)를 반환하고 아무것도 옮기지 않는다.

#### Scenario: F-TM-02 구성원 없는 프로젝트
- **WHEN** 폴더가 없는 「가나정밀 1차 교육」을 선택한다.
- **THEN** 알림만 보이고 구성원 문구와 체크 칸은 없으며, 「옮기기」를 바로 누를 수 있다.

#### Scenario: TM-I-16 빠진 폴더
- **WHEN** 프로젝트가 사용하던 공유 폴더에서 해당 사용자가 빠진다.
- **THEN** 해당 프로젝트는 고를 수 없고, 해당 폴더의 구성원 이름도 보이지 않는다.

### Requirement: 옮긴 대화는 한 곳에만 있다 — 프로젝트의 주제로 보이고 채팅 목록 · 전체 대화 · 검색의 채팅 쪽에서 빠진다
시스템은 「옮기기」를 누르면 해당 대화의 메시지를 복사하지 않고 프로젝트의 방으로 옮겨야 한다(SHALL). 옮기는 범위는 화면에서 해당 대화로 묶는 모든 메시지(사용자의 말 · 첨부, 답변, 파일 카드, 카드)다. 각 메시지에는 주제(`content.conv`)와 이동 기록(`content.moved` — 원래 방 · 옮긴 사람 · 시각 · 이전 주제 표시)을 남긴다. 대화의 `context_threads` 행은 프로젝트의 키로 옮긴다. 그러면 해당 대화는 채팅의 대화 목록 · 「다른 대화 ▾」 · 전체 대화 · 라우터의 후보에서 빠지고, 프로젝트의 주제 목록에 들어간다. 옮긴 메시지는 해당 주제로만 묶이며, 프로젝트에 원래 있던 메시지는 그 주제에 포함하지 않는다(`lib/conversations.js` topicOf = `src/projectTopics.js`). 프로젝트의 해당 주제에는 「채팅에서 옮겨 온 대화예요 · 메시지 N개」 칩이 남는다. 채팅에서 해당 대화를 현재 대화로 사용 중이었다면 `pro_threads.conversation_id`를 비운다. 검색에서는 해당 메시지를 프로젝트의 해당 주제로 찾을 수 있고, 채팅에서는 찾을 수 없다. 화면은 프로젝트의 해당 대화(`/projects/:id/t/:cid`)로 이동하며, 「프로젝트 「…」로 옮겼어요 · 채팅 목록에서는 빠졌어요」를 보여 준다. 해당 사용자의 다른 화면에도 실시간 이벤트(`conversation.moved`)로 변경 사항을 반영한다.

#### Scenario: F-TM-01 · TM-I-02 옮김
- **WHEN** 확인 칸에 체크하고 「옮기기」를 누른다.

- **AND** 프로젝트에 원래 있던 「프로젝트 계획을 채웠어요」는 해당 주제로 묶이지 않는다.

#### Scenario: TM-I-02b 채팅에서 현재 사용 중이던 대화
- **WHEN** 채팅에서 현재 대화로 사용 중인 대화를 옮긴다.
- **THEN** 채팅의 현재 대화가 비워지고, 다음 메시지가 옮긴 대화로 이어지지 않는다.

#### Scenario: TM-I-11 · TM-I-14 · TM-I-15 한 곳에만 남는다
- **WHEN** 대화를 옮긴 뒤 채팅 쪽에서 늦게 도착한 해당 대화의 답변이 대화 행을 다시 쓰려고 한다(`fileConversation`).
- **THEN** 프로젝트 키에 행이 있으므로 사용자 키의 행을 만들지 않고, 채팅 목록에도 다시 나타나지 않는다.
- **AND** 「채팅에서 옮겨 온 대화예요」 칩은 행 · 메시지를 옮기는 문장 안에서 함께 생성된다. 칩이 남지 않았더라도 옮긴 메시지의 표시(`content.moved`)로 되돌릴 수 있다.

### Requirement: 옮긴 대화를 가리키던 링크 · 따로 묶여 오는 줄은 프로젝트로 이어진다
시스템은 옮긴 대화를 가리키는 채팅 링크(`/chat/c/:cid` — 알림 · Home 카드 · 「원래 대화 열기」 칩 · 공유 카드에서 여는 경로)를 열면 깨진 빈 화면 대신 해당 프로젝트의 해당 주제로 이동하고, 「이 대화는 프로젝트 「…」로 옮겼어요」를 보여 주어야 한다(SHALL, `GET /api/conversations/:cid/place`). 옮긴 뒤 해당 대화로 따로 묶여 들어오는 줄(메일 답장 · 일정 줄 같은 `context.action: 'aside'`)은 채팅이 아니라 해당 프로젝트의 해당 주제로 들어간다(`lib/store.js` addMessage). 해당 대화를 열어 둔 이전 화면에서 메시지를 보내면 채팅에서 답하지 않고 409(`moved`, 옮긴 곳 포함)를 반환한다. 다른 사람의 대화 · 프로젝트를 조회하거나 옮기려고 하면 존재 여부도 알리지 않고 404를 반환한다.

#### Scenario: F-TM-01 · TM-I-02 옛 링크와 늦게 온 줄
- **WHEN** 옮긴 뒤 `/chat/c/<그 대화>`를 연다. 또한 해당 대화로 따로 묶인 메일 줄이 새로 들어온다.
- **THEN** 화면은 「영업 자료 정리」의 해당 주제로 바뀌고, 「이 대화는 프로젝트 「영업 자료 정리」로 옮겼어요」가 보인다. 새 줄은 해당 프로젝트의 해당 주제로 들어가며, 다른 대화로 묶인 줄은 채팅에 그대로 남는다.

#### Scenario: F-TM-06 옛 화면에서 보낸 말
- **GIVEN** 다른 화면에서 해당 대화를 열어 둔 상태로 실시간 이벤트를 받지 못했다.
- **WHEN** 그 화면에서 말을 보낸다.
- **THEN** 서버는 409(`moved`, 옮긴 곳)를 반환하고, 화면은 보내기 실패 상태로 남지 않고 프로젝트의 해당 주제로 이동한다. 보낸 말은 입력창에 다시 들어가고 「이 대화는 프로젝트 「…」로 옮겼어요 · 보낸 말은 입력창에 다시 넣었어요」가 보인다. 선택 시트도 409(`moved`)를 받으면 해당 위치로 이동한다.

#### Scenario: F-TM-06 · F-TM-07 줄 서 있던 말과 다른 화면
- **WHEN** 옛 화면에서 말을 두 번 보내 둘째가 첫째 뒤에 줄 서 있다가 409(`moved`)를 받는다.
- **THEN** 두 말이 보낸 순서대로 한 입력창에 다시 들어가고, 그 말에 붙어 있던 파일도 입력창에 돌아온다.
- **AND** 그 사이 사람이 다른 화면으로 갔으면 그 화면을 바꾸지 않고 「이 대화는 프로젝트 「…」로 옮겼어요 · 그 대화를 열면 보낸 말이 입력창에 다시 들어가요」만 보인다. 나중에 그 대화를 열면 말이 입력창에 들어간다.

### Requirement: 옮긴 대화에서 계속 물으면 그 프로젝트의 맥락으로 이어진다
시스템은 프로젝트의 해당 주제에서 보낸 메시지를 해당 대화의 deepagents 대화(같은 id, 이어지는 기록)로 보내고, 해당 프로젝트의 계획(스펙 `project-room` 「프로젝트 계획」)과 폴더를 함께 제공해야 한다(SHALL). 사용자의 말과 답변은 해당 주제로 묶이고, 채팅에는 아무것도 들어가지 않는다.

#### Scenario: TM-I-10 이어 묻기
- **GIVEN** 「가나정밀 1차 교육」의 계획 목적은 「가나정밀 1차 교육의 교안과 실습 목록을 만든다」이다.
- **WHEN** 옮긴 「가나정밀 교육 요청 조사」 주제에서 「2일차 실습에 쓸 예제 데이터도 정해 줘」를 보낸다.
- **THEN** 에이전트는 같은 대화 id로 계획 블록(「[프로젝트 계획] … 목적: …」)과 함께 요청을 받고, 사용자의 말과 답변은 해당 주제로 묶이며 채팅에는 나타나지 않는다.

### Requirement: 동시 요청은 한 문장의 조건부 갱신으로 하나만 통과한다
시스템은 같은 대화를 두 번 눌러 옮기거나 두 화면에서 서로 다른 프로젝트로 동시에 옮기더라도, 대화를 한 프로젝트에만 옮겨야 한다(SHALL). 대화의 행을 옮기는 갱신을 기준으로 삼아, 행과 메시지를 데이터 수정 CTE 한 문장으로 함께 옮긴다. advisory lock을 사용하거나 데이터베이스 연결을 유지하지 않는다. 같은 프로젝트로 옮기기를 다시 누르면 추가 작업 없이 「이미 옮겼어요」(`already`)를 반환하며, 칩도 하나만 남는다. 다른 프로젝트로 옮기기를 누르면 409(`moved`, 옮긴 곳 포함)를 반환한다.

#### Scenario: TM-I-04 동시에 두 프로젝트로
- **WHEN** 「견적 비교」를 두 화면에서 「가나정밀 1차 교육」과 「견적 모음」으로 동시에 옮긴다.
- **THEN** 한쪽으로만 옮겨지고, 메시지와 행은 해당 프로젝트에만 하나씩 존재한다. 다른 쪽은 409(`moved`)를 반환하며, 같은 프로젝트로 옮기기를 다시 누르면 `already`를 반환하고 칩은 하나만 남는다.

### Requirement: 「채팅으로 되돌리기」는 옮긴 사람만, 프로젝트에서 이어 나눈 이야기와 함께
시스템은 옮긴 대화의 칩에 「채팅으로 되돌리기」를 옮긴 사람에게만 보여 주고, 「채팅으로 되돌릴까요? 프로젝트에서 이어서 나눈 이야기도 함께 옮겨요」로 한 번 더 확인한 뒤 되돌려야 한다(SHALL). 되돌릴 때는 프로젝트에서 해당 주제로 묶인 모든 메시지(옮겨 온 메시지와 프로젝트에서 이어 나눈 메시지)를 채팅으로 옮긴다. 각 메시지는 해당 대화로 따로 묶이므로(`context.action: 'aside'`), 채팅의 다른 대화를 함께 묶거나 채팅에서 현재 사용 중인 대화를 바꾸지 않는다. 행은 해당 사용자의 키로 되돌리고, 칩은 지운다. 화면은 채팅의 해당 대화로 이동하며, 「채팅으로 되돌렸어요 · 채팅 목록에 다시 있어요」를 보여 준다. 프로젝트에서 시작한 주제(채팅에 있던 적이 없음)는 409(`not_moved`)를 반환하고, 다른 사람이 되돌리려고 하면 404를 반환한다. Lite 프로젝트는 소유자 한 사람의 방이며 해당 사용자만 옮길 수 있으므로, 「구성원이 있는 프로젝트에서 되돌리기는 옮긴 사람만」이라는 제한은 칩에 남긴 이동자 정보와 서버의 확인(403 `not_mover`)으로 지킨다.

#### Scenario: F-TM-02 · TM-I-06 되돌리기
- **GIVEN** 「출장 일정 정리」를 「가나정밀 1차 교육」으로 옮긴 뒤, 해당 주제에 「출장 숙소도 찾아 줘」와 그 답변, 파일이 추가되었다.
- **WHEN** 「채팅으로 되돌리기」 → 「되돌리기」를 누른다.
- **THEN** 다섯 메시지가 모두 채팅의 「출장 일정 정리」로 돌아오고, 해당 대화가 채팅 목록에 다시 나타난다. 프로젝트의 주제 목록과 칩에서는 빠진다. 다시 옮길 수도 있다.

#### Scenario: TM-I-11 · TM-I-12 · TM-I-15 되돌리기가 막히지 않는다
- **WHEN** 옮긴 뒤 다른 서비스(라우터)가 해당 대화의 행을 사용자 키로 다시 쓴다.
- **THEN** 되돌릴 때는 해당 행을 프로젝트의 행에 합친 뒤(더 큰 턴 수 · 더 늦은 시각) 되돌리며, 같은 키의 충돌로 계속 실패하지 않는다.
- **AND** 프로젝트의 턴이 아직 어느 주제에 속하는지 모르면(`PT.routeProject`가 이 주제를 고를 수도 있음) 409(`busy`)를 반환한다. 프로젝트 계획 변경 칩(`planChange`)은 프로젝트에 남는다.

#### Scenario: TM-I-19 두 화면에서 거의 동시에 되돌리기
- **WHEN** 두 화면에서 0–15 ms 차이로 「채팅으로 되돌리기」를 누른다(40번).
- **THEN** 한쪽이 되돌리고, 다른 쪽은 「이미 되돌렸어요」(`already`)나 404를 받는다. 대화의 행(제목 · 요약 · 턴 수)은 한 번도 사라지지 않는다. 다시 생긴 행을 합치는 일은 프로젝트의 행이 아직 있을 때만, 그 행을 잠근 채 한다.

### Requirement: 「새 프로젝트로 옮기기」는 「프로젝트로 시작」의 확인 카드를 다시 쓰고, 만든 뒤 곧바로 옮긴다
시스템은 「새 프로젝트로 옮기기」를 누르면 `chat-to-project`의 확인 카드를 해당 대화 전체(마지막 메시지까지)에 적용하고, 해당 대화로 따로 묶어 두어야 한다(SHALL). 카드의 제목은 「이 대화를 새 프로젝트로 옮길까요?」이다. 「옮길 대화 「…」 · 메시지 N개」와 「만들면 이 대화(메시지 N개)를 새 프로젝트로 옮겨요. 옮긴 대화는 그 프로젝트에서만 볼 수 있고, 채팅 목록과 전체 대화에서는 사라져요.」를 보여 주며, 대화를 통째로 옮기므로 첫 문서는 만들지 않는다. 단추는 「만들고 옮기기」이다. 대화마다 열린 카드는 하나만 둔다. 「만들고 옮기기」를 누르면 프로젝트(선택한 템플릿이 있으면 해당 작업 공간)와 계획을 만든 뒤, 카드까지 포함한 대화를 옮긴다. 카드는 「프로젝트를 만들고 대화를 옮겼어요 · 대화(메시지 N개)를 이 프로젝트로 옮겼어요」로 바뀐다. 화면은 새 프로젝트의 해당 주제로 이동한다. 옮기지 못하면 프로젝트는 남겨 두고 그 이유를 카드에 보여 준다.

#### Scenario: F-TM-03 · TM-I-07 새 프로젝트로
- **WHEN** 「거래처 미팅 메모」에서 「새 프로젝트로 옮기기」 → 카드의 「만들고 옮기기」를 누른다.
- **THEN** 프로젝트 「거래처 미팅 후속」이 생성되고, 화면은 해당 프로젝트의 「거래처 미팅 메모」 주제로 이동하며 「채팅에서 옮겨 온 대화예요 · 메시지 3개」(두 줄과 카드)가 보인다. 채팅 목록에는 해당 대화가 없다.

#### Scenario: TM-I-17 다른 경로로 먼저 옮긴 대화
- **GIVEN** 「새 프로젝트로 옮기기」 카드가 열려 있다.
- **WHEN** 같은 대화를 선택 시트에서 다른 프로젝트로 옮긴 뒤 해당 카드의 「만들고 옮기기」를 누른다.
- **THEN** 카드는 대화를 옮길 때 「이 대화는 다른 프로젝트로 옮겼어요 · 열기」로 닫힌 상태이며, 「만들고 옮기기」는 409를 반환하고 빈 프로젝트를 만들지 않는다.

### Requirement: 말로 해도 같은 확인을 거친다 — 「이 대화 프로젝트로 옮겨 줘」
시스템은 채팅의 라우터 모델이 `move_to_project`를 선택하면 해당 턴에서 걸러 본 대화(없으면 채팅에서 현재 사용 중인 대화)에 「이 대화를 프로젝트로 옮길까요?」 카드를 따로 묶어 표시해야 한다(SHALL). 이 단계에서는 아무것도 옮기지 않는다. 사용자가 프로젝트 이름을 말했으면 판정 모델이 옮길 수 있는 프로젝트 가운데 어느 것을 가리키는지 첫 글자 확률로 판단한다(`move.minP` 0.7 이상일 때만, 스킬 `prompts/pick-project.md`). 선택한 프로젝트가 있으면 카드에 「「…」로 옮기기」와 「다른 프로젝트 고르기」를, 없으면 「프로젝트 고르기」를 둔다. 어느 단추를 누르든 메뉴의 단추로 시작할 때와 같은 확인 화면(알림 · 구성원 확인)을 거친다. 「아니요」를 누르면 「옮기지 않았어요」로 바뀐다. 대화를 옮기면 카드도 함께 옮겨 가며 「대화를 프로젝트로 옮겼어요 · 열기」로 바뀐다. 프로젝트 안에서 같은 말을 하면 「이 대화는 이미 프로젝트 안에 있어요」라고 답한다.

#### Scenario: F-TM-04 · TM-I-08 말로
- **WHEN** 「견적 항목」 대화에서 「이 대화 견적 모음 프로젝트로 옮겨 줘」를 보낸다.
- **THEN** 카드에 「「견적 모음」으로 옮기기」가 보이고, 해당 대화는 아직 채팅에 있다. 이를 누르면 「견적 모음」의 알림 화면이 열리고, 「옮기기」를 누르면 「견적 모음」의 해당 주제로 이동한다. 판정 확률이 0.7 미만이면 추천하지 않는다.
- **AND** 대화를 걸러 본 화면에서 한 말과 안내 한 줄도 해당 대화에 묶이므로(라우터 도구의 안내도 해당 대화에 속함), 대화를 옮길 때 함께 옮겨 간다.

#### Scenario: TM-I-18 말로 한 요청의 대상
- **WHEN** 대화 하나를 걸러 본 화면에서 「이 대화 프로젝트로 옮겨 줘」를 보낸 뒤, 전체 채팅에서 다른 대화를 이어 가다 같은 말을 보낸다.
- **THEN** 두 번째 카드는 현재 대화를 대상으로 한다. 대상은 해당 메시지를 보낸 화면에서 걸러 본 대화(해당 사용자의 것으로 확인된 것)뿐이며, 앞 턴이 남긴 고정 대화를 사용하지 않는다(`start_project`도 같다).
- **AND** 걸러 본 화면에서 고른 라우터 도구의 안내 한 줄은 어느 도구든 해당 대화에 묶인다.
