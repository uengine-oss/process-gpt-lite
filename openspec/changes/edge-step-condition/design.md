## Context

조건(꼭 · 선택 · 사안에 따라)이 지금 두 곳에 있다.

```
 태스크 「재무 검토」 ─┬─ 다듬기 「단계 가르기」 gate ─ 확정하면 태스크 고정(pinned) ─ 모든 프로세스의 스냅샷에 걸림
                       └─ 「단계 규칙」 pro_step_requirements (proc_key, task) ─ 그 프로세스에만 걸림
```

- 결함 1: 관문 확정이 태스크를 고정해, 같은 태스크를 쓰는 다른 프로세스의 스냅샷(run.js unfold 의 「고정을 돌아가는 길 버림」)이 바뀌었다.
- 결함 2: 두 설정이 부딪쳐도 저장되고, 스냅샷은 고정을, 단계 카드(runmode.js gateStep → steprule.forStep)는 단계 규칙을 따랐다.

그래프에는 이미 이벤트 → 태스크 간선(TRIGGERS)이 있다. 시작 이벤트(요청 메일 · 채팅 요청 · 타이머)와 결과물 이벤트(`artifact:<앞 태스크>:<종류>`)에서 나간다. 다만 두 가지가 부족하다.
- 간선은 (이벤트, 태스크) 하나뿐이고 여러 프로세스가 함께 쓴다. 로컬 그래프 기준으로 「제안서 작성 결과물(문서) → 견적서 작성」은 프로세스 6개에 있다.
- 결과물을 내지 않은 단계 뒤에는 이벤트가 없다(평면도 작성 · 팀장 승인 · 생산 가능 검토 등).

Lite 의 실행 방식은 두 가지다. 전제가 다르다.
- map 엔진(「지도에서 바로」): 정해진 스냅샷대로 실행하지 않는다. 건은 중간 태스크부터 시작될 수 있고, 갱신된 규칙은 실행 중인 건에도 적용된다.
- bpm 엔진(「프로세스 정의로」): 인스턴스마다 만든 스냅샷대로 실행한다. 갱신된 규칙은 새 스냅샷부터 적용된다.

## Goals / Non-Goals

**Goals:**
- 조건을 이벤트 → 태스크 간선에서 정하고 (프로세스, 이벤트, 태스크) 단위로 저장한다.
- 모든 태스크 진입에 조건을 정할 간선이 있게 한다(「앞 단계 완료」 이벤트).
- 실행이 건이 들어온 간선의 조건을 따른다. map 엔진은 그때의 설정(중간 시작 · 실행 중 변경 포함), bpm 엔진은 스냅샷 때의 설정.
- 단계 분류도 같은 간선에서 정하고, 실행이 진입 간선의 분류로 담당을 정한다.
- 설정하는 곳을 하나로 만든다(「단계 가르기」 · 「단계 규칙」 설정 기능 제거, 분류 · 조건 값은 유지, 기존 설정 이전).

**Non-Goals:**
- 다듬기의 「바로잡기」(길 뒤집기 · 끊기 · 잇기 · 이름 바꾸기 등)는 바꾸지 않는다.
- 갈림길 조건(pro_branch_conditions, NEXT 간선의 배운 금액 조건)은 "어느 갈래로 가는가"이고, 이번 조건은 "들어온 태스크를 꼭 하는가"다. 갈림길 조건은 그대로 둔다.
- bpm 엔진으로 이미 만들어진 인스턴스에 바뀐 설정을 적용하지 않는다. 스냅샷대로 실행하는 것이 bpm 엔진의 전제다.

## Decisions

### 1. 저장: 새 표 pro_edge_conditions, 그래프 간선에는 쓰지 않는다
task 는 지도의 일 key(다듬은 흐름의 origin)로 저장해, 다듬기에서 이름을 바꿔도 설정이 이어진다. 저장할 때마다 행을 덧붙이는 이력 표다. (tenant_id, proc_key, event, task)마다 가장 늦은 행이 지금 설정이고, bpm 엔진은 at 이 스냅샷 때 이전인 가장 늦은 행을 읽는다(결정 4). 열은 `requirement`(required · optional · null), `rules`(jsonb, 기존 normRule 형식 그대로), `class`(jsonb, 기존 classes 한 칸 형식 `{class, why, by, decided, ai}` — human · ai · drop · skipped), `reason`, `by_user`, `at`. 관문(gate)은 분류로 따로 두지 않고 `requirement = required`로 저장한다. 같은 간선에 관문과 꼭을 따로 두면 다시 두 값이 부딪치기 때문이다. 바꿀 때마다 결정 원장(review.js ledger)에 남긴다.
- 대안: TRIGGERS 간선 속성에 `conditions: {proc_key: …}`로 저장 → 간선이 다시 셀 때 다시 쓰이고(build.js upsertRel), 프로세스 키가 그래프 속성 안에 묻혀 조회 · 이전이 어렵다. 결함 1과 같은 "공용 객체에 프로세스별 설정"을 반복한다.
- 대안: pro_step_requirements 에 event 열 추가 → 기본키가 바뀌고 기존 읽기(validAt)가 섞인다. 이전 뒤 표를 비우는 편이 깔끔하다.

### 2. 「앞 단계 완료」 이벤트: key `done:<태스크>`, kind `done`
structure.js 에서 건마다 연속한 두 단계 X → Y 를 볼 때, X 의 결과물 이벤트 중 Y 로 가는 것이 없으면 `done:X`(이름 「X 완료」)와 TRIGGERS `done:X → Y`를 만든다. 간선은 기존 결과물 간선처럼 n · p · split 을 세고 source 'mined'. 다듬기 · 말로 고치기는 그래프가 아니라 프로세스마다 고친 기록(pro_corrections)을 얹은 흐름이므로, 그렇게 이은 길의 `done:X → Y`는 그래프에 쓰지 않고 그 프로세스 흐름에서 만들어 보인다(edgecond.js entryEdgesOf · mapView.js eventGraph, virtual). 길을 끊으면 흐름에서 사라지고, 그 간선에 둔 설정은 「지도에 없는 간선」(stray)으로 남는다.
- 대안: 모든 전환에 「완료」 이벤트 → 결과물 이벤트가 있는 곳에 간선이 둘이 되어, 같은 상황에 조건을 두 군데서 정하게 된다.

### 3. 실행이 읽는 진입 간선
runmode.js gateStep 이 단계 행을 열 때 진입 간선을 정한다.
```
 첫 단계        → (건의 trigger 로 정한 시작 이벤트) → 태스크
                   없으면: 이 건이 건너뛴 바로 앞 단계 P 의 결과물 · done:P → 태스크
 앞 단계 X 뒤   → X 가 이번 건에서 낸 결과물 이벤트 → 태스크, 없으면 done:X → 태스크
 옮기기 · 되감기 → 옮기기 직전 단계를 X 로 보고 위와 같이
```
앞 단계 X 뒤에는 X 가 이번 건에서 실제로 낸 결과물 종류를 가리지 않고, X 에서 이 일로 오는 진입 간선(결과물 · 「X 완료」) 모두를 맞는 간선으로 본다(건마다 결과물 종류를 기록하지 않기 때문). 맞는 간선이 여럿이면 각 간선의 조건을 pickRequirement 로 읽고, 하나라도 required 이면 required. 분류도 같은 간선들에서 읽고, 확정한 「사람이 꼭」이 하나라도 있으면 사람이 맡는다. 조건 행이 없으면 지도대로(null). 결과는 pro_case_steps 의 matched 에 `{edge: {event, task}, rule, …}`로 남긴다.
- 「하나라도 꼭이면 꼭」을 고른 이유: 꼭은 조직이 약속한 품질 단계다. 건너뛰는 쪽으로 잘못 고르는 비용이 더 크다.

### 4. 언제의 설정을 읽는가: 엔진마다 다르다
steprule.requirementsOf 를 `edgeConditionsOf(procKey, { asOf })`로 바꾼다.
- map 엔진: asOf 없이 지금 설정을 읽는다. mapengine.js 의 pinOnStart(꼭 하는 단계가 있으면 map_pin)를 없앤다. 관리자가 건마다 거는 map_pin 은 지도 구조(갈래)에만 쓰이고 설정 읽기에는 쓰이지 않는다.
- bpm 엔진: asOf = 그 인스턴스의 스냅샷을 만든 때. 스냅샷(run.js procGraph)과 단계 열기(gateStep)가 같은 asOf 로 읽어, 스냅샷 구조와 단계의 꼭 · 선택 판단이 어긋나지 않는다. 지금 gateStep 이 bpm 건에서도 단계 규칙을 그때 읽는 것은 이 전제와 맞지 않아 함께 고친다.

### 5. 다음 단계 고르기와 스냅샷
- map 엔진(「지도에서 바로」, mapengine.js): X 가 끝나 후보가 여럿이면, 각 후보 Y 의 진입 간선(결정 3) 조건을 이 건으로 읽어 required 인 Y 를 먼저 고른다. 없으면 지금처럼 배운 조건 → 글로 쓴 갈림길 조건 → 가장 흔한 길.
- 두 엔진 공통(run.js procGraph → withRequirements → edgecond.js edgeRequiredView): 이 프로세스의 간선 조건 중 required 이거나 required 규칙이 있는 간선의 길(앞 일 X → 일 Y)을 `required` 로 표시하고, unfold 는 X 의 갈림길에서 그 길을 지나간다(돌아가는 길은 버린다). 태스크를 고정(pinned)하지 않으므로 같은 일에 다른 길로 오는 건과 다른 프로세스의 스냅샷에는 걸리지 않는다. bpm 엔진은 스냅샷 때의 설정(settingsAt), map 엔진은 지금 설정을 쓴다.
- 다듬기의 AI 분류 제안: 단계마다 만든 제안을 그 단계로 들어오는 간선마다 class.ai 로 남긴다(사람이 확정한 분류 · 꼭 · 선택은 그대로). 「관문」 제안은 분류가 아니라 간선 패널에서 「꼭 하는 단계」로 받는 제안으로 보인다.

### 6. 이전(sql/047 + 한 번 도는 스크립트)
- pro_step_requirements 행 → 그 프로세스 안에서 그 태스크로 들어오는 모든 TRIGGERS 간선(「앞 단계 완료」 생성 뒤)에 같은 행을 복사.
- pro_refine_reviews.classes 의 decided gate → 같은 (프로세스, 태스크)에 단계 규칙 행이 없을 때만 진입 간선 required 로. 있으면 단계 규칙을 따르고 버린 관문을 원장에 남긴다. pinned_here 인 고정은 푼다(pin_reason 이 다듬기의 것일 때만).
- 관문이 아닌 classes 칸(human · ai · drop · skipped, AI 제안 · 확정 여부 포함) → 그 프로세스 안의 진입 간선마다 class 로 복사.
- 이전 뒤 pro_step_requirements 는 읽지 않는다(표는 한 릴리스 동안 남겨 되돌림에 쓴다).

### 7. 「단계 가르기」 · 「단계 규칙」 설정 기능 제거, 값은 간선으로
- refine.js: 단계 가르기 탭의 저장(setClass, pro_refine_reviews.classes 쓰기)과 태스크 고정(pinTask)을 지운다. AI 분류 제안은 그대로 두되 결과를 (프로세스, 진입 간선)마다 pro_edge_conditions.class.ai 에 넣는다. 다듬기 화면에는 바로잡기만 남는다.
- runmode.js responsibleOf: cls 를 classes[task] 대신 진입 간선의 확정 분류에서 받는다(여럿이면 human 우선).
- steprule.js: 단계 단위 설정(requirementsOf · 단계 패널 API)을 지우고 간선 설정 읽기 · 쓰기만 둔다. suggestionOf 는 같은 간선의 분류에서 꼭 · 선택 추천을 만든다. 사안에 따라 규칙 읽기(pickRequirement · amountMatch · readYes)는 그대로 쓴다.
- routes/ontology.js: `/ontology/refine/:proc/classes` 와 단계 규칙 저장 API를 지우고 간선 설정 API 하나로 받는다.
- 이유: 설정하는 곳이 둘 이상이면 서로 부딪쳐 정합성이 깨진다(결함 2).

### 8. 화면
- MapGraph.vue 사건 보기: TRIGGERS 간선을 누르면 간선 설정 패널(꼭 · 선택 · 사안에 따라 편집, 분류와 AI 제안 · 근거 · 확정). 조건이 있는 간선은 보라 굵게(꼭) · 파랑 점선(선택) · 잔 점선(사안에 따라)으로 칠하고, 분류는 기존 단계 가르기 표시를 간선에 붙인다.
- 단계 패널(ProcessMapView.vue): 단계 규칙 설정과 단계 가르기 표시를 지운다.
- OntoRefine.vue · mock-refine.js: 단계 가르기 탭 · 표시를 지운다.

## Risks / Trade-offs

- [간선이 많아져 관리자가 같은 조건을 여러 간선에 반복해 정해야 함] → 간선 조건 패널에서 같은 태스크로 들어오는 다른 간선에 같은 조건을 복사하는 동작을 둔다. 저장은 간선마다 따로 한다.
- [이전 뒤 분류가 진입 간선마다 복사되어, 한 간선만 바꾸면 같은 태스크가 상황에 따라 담당이 달라짐] → 의도한 동작이다(상황별 설정). 패널에서 같은 태스크로 들어오는 다른 간선의 분류를 함께 보인다.
- [그래프를 다시 세면 이벤트 키가 바뀌어 조건이 고아가 됨(태스크 이름 바꾸기 · 합치기)] → 키 변경 시 pro_edge_conditions 의 event · task 를 함께 바꾼다(build.js 의 이름 합치기 경로). 지도에 더 없는 간선의 조건은 지우지 않고 패널에 「지도에 없는 간선」으로 보인다.
- [이력 표가 커짐] → 저장은 관리자가 설정을 바꿀 때만 일어나 양이 적다. 지금 설정 읽기는 (proc_key, event, task, at desc) 인덱스로 한다.
- [「하나라도 꼭이면 꼭」 때문에 선택으로 정한 간선이 무시되는 경우] → 단계 카드와 단계 행 matched 에 어느 간선 때문에 꼭인지 보인다.

## Migration Plan

1. sql/047_edge_conditions.sql(표 생성) 적용.
2. 지도 다시 세기로 「앞 단계 완료」 이벤트 · 간선 생성.
3. 이전 스크립트 실행(결정 6), 결과를 원장과 콘솔에 요약.
4. 되돌림: 새 코드 이전 버전으로 되돌리면 pro_step_requirements · classes 가 그대로 남아 있어 예전대로 동작한다. 풀었던 태스크 고정은 원장 기록으로 다시 건다.
